## 1. 调研目标与方法

对当前主流**重复文件检测算法**与**开源查重工具**进行系统对比，提炼"最佳实践组合"，支撑本项目算法选型。

调研对象：

- 哈希算法：MD5 / SHA-1 / SHA-256 / BLAKE2b / BLAKE3 / xxHash / CRC32
- 去重策略：全量哈希、size 预分组、部分（首尾）哈希、逐字节比对、内容定义分块（CDC / FastCDC）
- 开源工具：czkawka、dupeGuru、rmlint、fdupes、jdupes、rdfind、dupd、rsdedup、file-deduplicator
- 生产系统：百度网盘秒传指纹、Dropbox/rsync/restic/borg 分块方案、BLAKE3 在生产环境的应用

## 2. 哈希算法对比

### 2.1 性能与特性总表

| 算法 | 类型 | 吞吐量（单核参考*） | 输出位宽 | 多核并行 | 抗碰撞（加密级） | 适用性 |
|---|---|---|---|---|---|---|
| CRC32 | 校验和 | 10+ GB/s | 32 bit | 否 | 无 | 完整性校验，不参与去重判定 |
| xxHash64 / xxH3 | 非加密 | 5~15 GB/s（受内存带宽限制） | 64/128 bit | 否 | 弱 | 快速"排除不同"，预筛 |
| MD5 | 加密（已攻破） | ~0.5 GB/s | 128 bit | 否 | 已构造碰撞（2004） | 不推荐 |
| SHA-1 | 加密（已攻破） | ~0.6 GB/s | 160 bit | 否 | 已构造碰撞（2017 SHAttered） | 不推荐 |
| SHA-256 | 加密 | ~0.6~1 GB/s（x86 有 SHA-NI 加速） | 256 bit | 否 | 强，FIPS 合规 | 合规场景唯一选择 |
| BLAKE2b | 加密 | ~1 GB/s | 512 bit | 有限 | 强 | rmlint 默认（blake2b） |
| **BLAKE3** | 加密 | **2~6 GB/s**（SIMD） | 256 bit | **原生 tree hashing 并行** | 强（同 SHA-256 安全级别） | **2026 年去重事实标准** |

\* 吞吐为量级参考（内存中哈希），实际文件去重瓶颈通常在磁盘 IO。

### 2.2 BLAKE3 为何是首选

1. **速度**：比 SHA-256 快 3~6 倍（大文件场景），比 MD5 快数倍，且**支持多线程并行哈希**（Merkle 树结构天然可拆分为并行子任务）；
2. **安全性**：256bit 输出，加密级抗碰撞（不可伪造、无已知碰撞攻击）；
3. **生态**：已被 Vercel、Cloudflare Workers、IPFS、Xet 内容寻址协议等大规模采用，2026 年 npm 月下载量超 800 万，成为去重/内容寻址领域标准（rsdedup、file-deduplicator、czkawka 默认均可用 BLAKE3）；
4. **工程实现**：Go 有成熟实现（见 §2.4），支持流式接口与 tree hash 拼接。

> **结论**：全量内容判定统一采用 **BLAKE3-256**；预筛采用 **xxHash64**（非加密即可，因为预筛只用于"排除不同"，最终判定仍走 BLAKE3）。

### 2.3 碰撞风险分析

- BLAKE3-256 自然碰撞概率 ≈ 2^-128（生日界）量级，即使 10 亿个同 size 文件，误判概率仍趋近于零；
- 为彻底消除极端顾虑：提供 **paranoid 模式**——对已判定的重复组做**逐字节流式比对**后再输出结果（成本仅在最终确认组上）；
- 不采用"多哈希交叉验证"（如 MD5+SHA-1）：不必要地加倍计算量，收益为零。

### 2.4 Go 哈希库选型

| 库 | 说明 | 结论 |
|---|---|---|
| `lukechampine.com/blake3` | Go 生态最成熟的 BLAKE3：stdhash 风格 API、SIMD（AVX2/SSE4.1）、支持 XOF 与 tree hash 拼接 | **选用（全量哈希）** |
| `zeebo/blake3` | 纯 Go 实现亦可，社区活跃度与 API 设计稍逊 | 备选 |
| `cespare/xxhash/v2` | xxHash64 事实标准，极稳定 | **选用（预筛）** |
| 标准库 `crypto/sha256` | 无 SIMD Go 加速时较慢 | 不用 |

> **许可兼容性**：以上依赖（xxhash/blake3：MIT；modernc.org/sqlite：BSD；Wails：MIT）均为宽松许可，与项目 MIT 分发无 GPL 传染，二进制可闭源/商用。

## 3. 去重策略（检测流程）对比

| 策略 | 原理 | 读盘成本 | 精确度 | 代表 |
|---|---|---|---|---|
| 全量哈希 | 每个文件读一遍算哈希再分组 | O(总数据量) | 高 | 老式工具（fdupes 旧版默认） |
| size 预分组 + 全量哈希 | 先按大小分组，再对同 size 哈希 | 仅候选 | 高 | rsdedup |
| size + 部分哈希 + 全量哈希 | 首尾/头部小样本哈希淘汰大部分，再全量 | 远低于候选量 | 高 | czkawka、file-deduplicator、DuoBolt、百度秒传 |
| 逐字节比对 | 候选两两逐字节比较 | 同全量哈希 | 100% | rmlint `--paranoid`、jdupes `--byte` |
| CDC 分块去重 | 内容定义切块，块级去重 | O(总数据量) | 面向近似去重 | rsync、restic、borg |

### 3.1 关键洞察：部分哈希（预筛）为什么有效

对同 size 的两个文件：

- 若它们内容不同，**头部 64KiB 或尾部 64KiB 不同的概率接近 100%**（仅当差异恰好在文件中间且首尾完全一致时才漏过，此时进入全量哈希兜底，正确性不受影响）；
- 因此"首尾哈希"可淘汰 99%+ 的非重复候选，且每个文件只读 ≤128KiB；
- 百度网盘秒传指纹（size + 前 256KB slice hash + 全量 content hash）验证了同一设计思想在生产环境的价值。

### 3.2 本项目的多阶段流水线（最终方案）

```
① 元数据扫描 ──► ② size 分组 ──► ②' 候选组 FileKey 去重 ──► ③ 首尾 xxHash64 预筛 ──► ④ 全量 BLAKE3 ──► ⑤（可选）逐字节确认
   仅元数据        0 读盘          仅候选开句柄(win)          ≤128KiB/文件          仅候选大文件        仅最终重复组
                                                                             （小文件在③一趟完成）
```

**数学期望**（典型目录数据）：

- 阶段 ② 后：只剩 ~5~10% 文件进入候选；
- 阶段 ②' 后：硬链接被剔除（典型 <1%），候选略降；
- 阶段 ③ 后：只剩 ~0.1~1% 文件需要全量读盘；
- 阶段 ④ 后：得到精确重复组。

**净效果**：总读盘量约为"全量哈希方案"的 1/100~1/1000；Windows 额外句柄开销仅落在 <10% 的候选文件上。

### 3.3 为什么不选 CDC（内容定义分块）

| 维度 | 整文件哈希（本项目） | CDC 分块 |
|---|---|---|
| 目标场景 | 找完全相同的文件 | 找"大部分相同"的文件 / 增量同步 |
| 判定精确性 | 完全相同 = 重复（语义精确） | 块级相似（阈值判定，需额外参数） |
| 实现复杂度 | 低 | 高（切块边界、块表、组合判定） |
| 误报可能 | 无（paranoid 模式 0 误报） | 存在（块粒度近似） |

结论：**查重工具的核心价值是"精确找出完全相同的副本"，整文件哈希是充分必要条件；CDC 留给未来的"相似文件"扩展模式**。

### 3.4 边界情况分析（预筛策略的失效面与兜底）

| 边界情况 | 影响 | 处理 |
|---|---|---|
| **小文件（size ≤ 128KiB）** | 首尾样本覆盖全文件，预筛=全量 | 阶段 ③ 一趟完成 xxHash + BLAKE3，跳过阶段 ④；专项测试覆盖 |
| **首尾相同、中间不同** | 预筛判定"疑似相同"，无法淘汰 | 正常进入全量哈希兜底，**正确性无损，仅性能退化**；此类文件极罕见 |
| **同物理文件多路径（硬链接）** | 会被误判为"重复"并重复计空间 | 阶段 ②' 按候选组解析 FileKey（win 此刻才开句柄，见 02 决策 11），只计一次 |
| **重叠扫描根目录**（`a/` 与 `a/b/` 同扫） | 同一文件被收集两次 | 已访问目录集合去重（mac/win 大小写折叠） |
| **缓存失效**（文件重写，mtime 变） | 复用了错误哈希 | 缓存键 (path, size, mtime) 三重校验，任一不匹配即重算 |
| **极小文件（0 字节）** | 全部"相同" | 内置跳过（无清理意义），可选列出 |
| **操作时文件已消失（ENOENT）** | 删除/移动时文件不存在 | 计入 `Skipped`（目标已达成），不算失败、不计释放空间 |
| **扫描中被外部修改** | 哈希与实际内容不一致 | 文件 mtime 在操作前校验中比对；失败进清单不误删 |

## 4. 开源项目调研

### 4.1 czkawka（Rust，MIT）— 性能标杆

- **定位**：综合磁盘清理工具（重复文件/相似图片/空目录/损坏文件），三平台 + FreeBSD；
- **算法**：Rayon 线程池并行；目录遍历并行；按 size 分组；大文件**分块预哈希**（partial hash）淘汰；全量哈希收尾（默认 BLAKE3，可选 CRC32 / XXH3）；SQLite **缓存**支持二次扫描提速；
- **性能数据**（社区基准，8C16T / NVMe）：10 万文件 50GB 数据，16 线程 ≈ 29s，加速比 12.3x；85 万文件 15GB 仓库 ≈ 3.2 分钟；
- **启示**：① 线程池 + 并行遍历成熟可行；② partial hash 预筛是大文件场景的关键；③ 缓存是体验分水岭；
- **不足**：GTK4 界面风格较传统；GUI 功能与 CLI 功能不对等。

### 4.2 dupeGuru（Python + Qt/Cocoa，GPLv3）— 功能标杆

- **算法**：多维度比对（FILENAME / CONTENTS(MD5) / 图片 FUZZYBLOCK 感知哈希 / 音频 TAG）；SQLite 内存缓存；增量扫描；
- **性能**：Python 实现，社区实测明显慢于 Rust 系（13.17GB 数据集对比 Czkawka 慢约 11 倍）；
- **启示**：① 感知哈希用于"相似图片"很有价值（V2 参考）；② 参考目录（reference folder）防误删是优秀安全设计；
- **不足**：语言性能天花板；界面较老派。

### 4.3 rmlint（C，GPL）— 安全与正确性标杆

- **算法**：默认 blake2b；size 分组；partial hash 预筛；`--paranoid` 逐字节确认；输出可执行清理脚本（不直接删文件）；
- **文档精华（Cautions）**：
  - 用 inode 识别同一文件的多个路径（path doubles），防止重叠目录导致"假重复"；
  - 硬链接共享 inode，识别硬链接可避免误删/重复计数；
  - 删除前务必校验、优先移动而非删除、避免文件名特殊字符陷阱；
- **启示**：本项目安全性设计直接继承上述最佳实践（含 Windows FileIndex 按需解析扩展）。

### 4.4 fdupes / jdupes（C）— 经典命令行使

- fdupes：size 分组 → MD5 → 逐字节确认；jdupes 是其性能优化分支；
- **启示**：经典三步法（size → hash → byte）即本项目流水线的雏形，进一步演进为多阶段（加入首尾预筛与按需 FileKey）以降低读盘与句柄开销。

### 4.5 rsdedup / file-deduplicator（Rust）— 最新实践

- **rsdedup**：默认 size+hash 策略，partial 4KB 预筛，BLAKE3/SHA-256/xxHash 可选，持久化缓存，并行哈希；
- **file-deduplicator**：size 预过滤 → BLAKE3 **首尾各 64KiB** 部分哈希 → 全量 BLAKE3；回收站（trash）命令；操作前重新校验；
- **启示**：两者几乎一致地验证了"**size → 首尾 partial → 全量 BLAKE3**"为 2026 年最佳实践；本项目采用完全相同的策略组合。

### 4.6 生产系统指纹（百度网盘秒传）

公开抓包分析：`file_size + slice_md5(前256KB) + content_md5 + crc32`。思想与本项目一致：**先小样本快速筛，再全量确认**。本项目将小样本换为更快的 xxHash64 + 更强的全量 BLAKE3。

### 4.7 调研总结表

| 工具 | 语言 | 多线程 | 预筛策略 | 全量哈希 | 缓存 | 安全设计 | 对项目的借鉴 |
|---|---|---|---|---|---|---|---|
| czkawka | Rust | ✅ Rayon | partial hash | BLAKE3（可选 CRC32/XXH3） | ✅ SQLite | 回收站/硬链接 | 线程池、缓存、分块预哈希 |
| dupeGuru | Python | 弱 | 多维比对 | MD5 | ✅ SQLite | 参考目录 | 感知哈希（V2）、防误删 |
| rmlint | C | ✅ | partial | blake2b | ✅ | paranoid、inode | 逐字节确认、inode/硬链接 |
| fdupes/jdupes | C | 部分 | size 分组 | MD5/SHA | ❌ | 逐字节确认 | 经典三步法 |
| rsdedup | Rust | ✅ | 4KB partial | 可选 BLAKE3 | ✅ | dry-run/trash | 与本文档方案一致 |
| file-deduplicator | Rust | ✅ | 首尾 64KiB | BLAKE3 | 部分 | 操作前校验/trash | **与本文档方案一致** |
| **FileDedup（本项目）** | **Go** | **✅ 全阶段** | **首尾 xxHash64 + 小文件一趟合并 + FileKey 按需解析** | **BLAKE3-256** | **✅ SQLite** | **回收站+校验+paranoid+硬链接+ENOENT 语义** | **综合上述全部优点** |

## 5. 最终算法选型结论

### 5.1 组合策略（为何是"最佳实践"）

| 环节 | 选择 | 一句话理由 |
|---|---|---|
| 预筛哈希 | **xxHash64（首部+尾部 64KiB）** | 极快、零碰撞顾虑（只用于排除不同） |
| 全量哈希 | **BLAKE3-256（lukechampine.com/blake3）** | 加密级强度 + 数 GB/s + 原生并行，事实标准 |
| 过滤顺序 | **size → FileKey 去重 → partial → full →（可选）byte** | 每步淘汰 >99% 候选，读盘与句柄量最小化 |
| 小文件捷径 | **≤128KiB 一趟双哈希** | 预筛样本即全文件，少一次读盘 |
| 硬链接识别 | **FileKey 按需解析（仅候选组）** | Windows 免去每文件开句柄，unix 零成本 |
| 并行模型 | **Worker Pool + 大文件分段** | 多核利用率最大化，任务粒度均衡 |
| 缓存 | **SQLite（path+size+mtime 校验键，批量写回）** | 二次扫描 10x+ 提速 |
| 精确兜底 | **paranoid 逐字节比对（可选）** | 100% 无碰撞疑虑 |
| 失败语义 | **ENOENT → Skipped** | 目标已达成不算失败，避免幽灵失败困扰用户 |

### 5.2 预期的综合性能

| 场景 | 预估表现 |
|---|---|
| 10 万文件 / 50GB（SSD，16 线程） | 首扫 ≤ 30s（对齐 czkawka 水准，Go 实现同级别） |
| 全量哈希吞吐 | ≥ 1.5 GB/s（多核 BLAKE3） |
| 二次扫描 | ≤ 5s（缓存命中） |
| 峰值内存 | ≤ 300MB（流式 + 紧凑结构） |

> 注：以上为设计目标值，需在 `cmd/benchgen` 基准集（01 §12.2）上实测验证，实测数据回填本表。

### 5.3 参考基准（来自调研）

- czkawka（Rust，8C16T/NVMe）：10 万文件 50GB ≈ 29s（16 线程），单线程 ≈ 356s；
- dupeGuru（Python）：同量级数据集慢一个数量级；
- rmlint 对比（历史数据）：dupd 48s / fdupes 65s 级（具体数据集下）。

## 6. 本项目与 czkawka 的差异化定位

同为高性能查重工具，FileDedup 不是 czkawka 的复刻：

| 维度 | czkawka | FileDedup |
|---|---|---|
| 技术栈 | Rust + GTK4/Slint | Go + Wails（Vue3），团队可维护性优先 |
| 界面风格 | 桌面原生控件风格 | 现代 Web 风格（暗/亮主题、虚拟滚动、预览面板） |
| 小文件优化 | 无专门路径 | ≤128KiB 一趟双哈希（预筛即全量） |
| Windows 硬链接识别 | 依赖元数据 | FILE_ID_INFO 按需解析（候选组内） |
| 删除体验 | 基础 | 回收站优先 + 操作前哈希校验 + 保留策略一键化 + ENOENT 语义 |
| 本地化 | 英文为主 | 中文优先，i18n 架构预留 |

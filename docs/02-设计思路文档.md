## 1. 设计目标与原则

本项目的设计围绕五个关键词展开：**快、省、准、美、安**。

| 关键词 | 设计原则 | 落地手段 |
|---|---|---|
| 快 | 最小化读盘与计算 | 多阶段过滤流水线，避免全量哈希无差别扫描 |
| 省 | 内存与 IO 受控 | 流式读取、缓冲池复用、紧凑数据结构 |
| 准 | 结果 100% 正确 | 强哈希 + 可选逐字节比对，防碰撞、防误判 |
| 美 | 现代简洁的交互 | Web 技术栈渲染，暗/亮主题，一屏一任务 |
| 安 | 删除操作零意外 | 回收站优先、操作前校验、二次确认、硬链接识别 |

**总原则**：性能不是靠"堆线程"换来的，而是靠"让每个阶段只做必须做的事"。多线程是放大器，算法设计才是引擎。

## 2. 需求理解与问题拆解

### 2.1 核心问题

> 在一组文件中，找出内容完全相同的文件集合，并协助用户安全地清理冗余副本。

### 2.2 子问题拆解

| 子问题 | 关键难点 | 我们的答案 |
|---|---|---|
| 如何判定"内容相同" | 读整个文件很慢，不读又怕误判 | 多阶段过滤：size → 首尾哈希 → 全量哈希 → 可选逐字节 |
| 如何避免对每个文件都全量读盘 | 候选文件才是少数 | 阶段 1、2 已淘汰 99%+ 候选，只有剩余极少文件需要全读 |
| 如何识别硬链接但不付出全量开销 | Windows 取 FileIndex 要开句柄 | FileKey 按需解析：仅候选组内（<10% 文件）才解析（决策 11） |
| 如何利用多核 | 任务粒度、负载均衡 | Worker Pool + 按文件/分片调度 + 大文件分段并行哈希 |
| 如何防止误删 | 用户操作不可逆 | 回收站优先 + 操作前重算哈希 + 显式保留策略 + ENOENT 明确语义 |
| 如何让普通用户会用 | 技术概念 → 直观操作 | 结果分组卡片、一键保留策略、二次确认弹窗 |

### 2.3 用户画像与场景

- **普通用户**：手机照片备份后出现大量重复、下载目录堆积——需要"一键清重复"，且绝不允许误删；
- **进阶用户**：素材库/工程目录有跨目录重复大文件——需要精确控制保留谁，能看可释放空间；
- **极限场景**：几十万甚至百万级文件的 NAS/备份盘——需要稳定、可暂停、可续扫。

## 3. 关键技术决策与权衡（ADR）

### 3.1 决策 1：查重策略 —— 多阶段过滤流水线（而非单一全量哈希）

**备选方案**：
- A. 每个文件直接全量哈希（MD5/SHA-256）再分组 —— 简单，但所有文件都要读一遍，慢；
- B. 只按文件名/大小判断 —— 快但误判率高，不能满足"内容级精确"；
- C. **多阶段过滤流水线** —— 由粗到细逐步淘汰。

**选择 C**。理由：
1. 统计上，目录中 90%+ 文件的 size 是唯一的（阶段 1 后已无候选）；
2. 剩余同 size 文件中，99%+ 的首尾 128KiB 不同（阶段 2 后仅剩极少数候选）；
3. 只有最终候选才付出"全量读盘 + BLAKE3"成本，读盘量可减少 2~3 个数量级。

**权衡**：实现复杂度高于"全量哈希"方案，但带来数量级的性能收益，值得。

### 3.2 决策 2：哈希算法 —— xxHash64（预筛）+ BLAKE3-256（全量）

**详见 03-算法选择与研究文档**，结论摘要：

- 预筛阶段用 **xxHash64**：非加密但极快，用于"排除不同"，不需要防攻击；
- 判定阶段用 **BLAKE3-256**：加密级强度 + 数 GB/s 吞吐 + 原生多核 tree hashing，是 2026 年去重领域的事实标准；
- 不用 MD5/SHA-1：无性能优势且碰撞安全性存疑；
- 不用 SHA-256：无 FIPS 合规需求时 BLAKE3 全面胜出（3~6 倍吞吐）。

**碰撞风险**：BLAKE3-256 输出 256bit，自然碰撞概率 ≈ 2^-128（生日界），可忽略；对"万一"的顾虑，提供 **paranoid 逐字节比对模式**彻底兜底。全项目口径统一为 BLAKE3-256，不做 128bit 截断。

### 3.3 决策 3：是否采用内容定义分块（CDC / FastCDC）

**结论：V1.0 不采用，设计上预留**。理由：

- 查重的目标是"完全相同的文件"，非增量备份；整文件哈希对完全相同文件是充分必要的；
- CDC 复杂度高（切块边界、块表存储），收益主要面向"近似去重/增量同步"场景；
- 若未来需要"相似内容去重"，可基于 FastCDC 增加扩展模式。

### 3.4 决策 4：多线程模型 —— 固定 Worker Pool + 阶段并行

- 遍历与哈希**阶段内并行、阶段间串行**（保证结果确定性与进度可理解）；
- 哈希阶段任务粒度 = 文件；大文件按 16MiB 切片拆任务，避免"一个 10GB 文件独占线程"；
- 线程数可配 1~逻辑核心数，**默认 max(1, 逻辑核心数-1)**（留 1 核余量给 WebView 渲染与系统调度，避免界面掉帧）；
- 进度统计用原子计数器，500ms 节流推送，UI 不因高频更新而掉帧。

### 3.5 决策 5：缓存策略 —— SQLite 持久化哈希缓存

- 按 `(path, size, mtime)` 作为缓存有效性键：命中则直接复用 BLAKE3，跳过读盘；
  - **为什么不用 inode 做缓存键**：inode 用于"同批次物理文件去重"是内存内行为；跨次扫描时文件可能被重写（inode 变化）或替换（path 复用），path+size+mtime 组合与 czkawka 实践一致，稳定性更好；
- **写回时机**：任务结束（Done/Cancelled/Paused）单事务批量写回——避免边扫边写的锁竞争与写放大；
- **清理策略**：条目上限 50 万，按 last_hit 淘汰；路径消失的条目写回时顺带删除；
- **位置**：`os.UserConfigDir()/FileDedup/cache.db`（平台差异见 01 §5.4）；
- 达到"二次扫描提速 10 倍+"目标；附带能力：断点续扫、扫描历史。

### 3.6 决策 6：技术框架 —— Wails v2（Go + Vue3）

- 满足"跨平台 + 原生体积小 + 高并发后端 + 现代 UI"的完整约束；
- Go 后端即引擎，无 IPC 协议转换负担（wails bindings 直连）；
- **Wails vs Tauri**：Tauri 后端为 Rust，性能同样优秀，但会引入第二后端语言，且用户既有 Go 并发/文件操作经验无法复用，维护成本翻倍；Wails 的 Go 生态（xxhash/blake3/sqlite 纯 Go 驱动）完全满足需求；
- **v2 而非 v3**：v3 尚处 alpha，API 不稳定，不用于生产；引擎层与框架解耦（internal/ 不 import wails），未来可平滑迁移；
- 与用户既有技术栈一致，维护成本低。

### 3.7 决策 7：安全删除策略 —— 回收站优先 + 操作前校验

- 删除 = 移入系统回收站（macOS NSWorkspace / Windows `SHFileOperationW` / Linux 自研 XDG Trash 规范），失败才提示；
  - **不调 `gio trash` 等外部命令**：依赖桌面环境且违背单二进制分发原则；
- 永久删除需用户显式选择并二次确认（输入确认或勾选"我已知晓"）；
- 操作执行前对每个待处理文件**重新计算 BLAKE3** 与结果集比对，防止扫描后文件被修改导致误删；
- **文件已消失（ENOENT）语义**：操作时文件不存在 → 计入 `Skipped`（该副本已不在磁盘，目标达成），**不算失败、不计释放空间**——避免用户被"幽灵失败"困扰；
- 每组保留策略默认建议"路径最短且不在隐藏目录"的文件。

### 3.8 决策 8：小文件阶段合并（≤128KiB）

- 首尾预筛样本为头 64KiB + 尾 64KiB；当 `size ≤ 128KiB` 时，样本已覆盖全文件——**预筛哈希即全量哈希**；
- 因此小文件在阶段 2 直接产出全量 xxHash 指纹并**顺带完成 BLAKE3 计算**（一次读盘，两个哈希同趟完成），阶段 3 对其跳过；
- 收益：海量小文件场景（代码仓库、图标库）少一次完整读盘；
- 该路径需专项单元测试覆盖（小文件去重、小文件与同 size 大文件不混淆分组、恰好 128KiB 边界）。

### 3.9 决策 9：缓存用 SQLite 而非 sled / bbolt / JSON

| 选项 | 结论 | 理由 |
|---|---|---|
| **SQLite（modernc 纯 Go）** | 选用 | 单文件、WAL 并发读、SQL 便于统计（CacheStats）与按 size 索引查询；czkawka 同方案 |
| sled（rsdedup 用） | 否 | Rust 生态库，Go 无官方等价 |
| bbolt | 可行但次优 | 纯 KV，统计与范围查询（按 size）需手写遍历 |
| JSON 大文件 | 否 | 10 万+ 条目全量读写，启动与保存都慢 |

### 3.10 决策 10：物理文件标识的平台抽象（Windows 无 inode）

- macOS/Linux：`syscall.Stat_t` 的 Ino + Dev，**遍历时 lstat 顺带返回，零额外成本**；
- **Windows：没有传统 inode**——获取 FILE_ID_INFO（VolumeSerialNumber + 128bit FileId）必须 `CreateFile` 打开句柄，见决策 11；
- scanner 层定义 `FileKey{VolumeID, FileIndex}` 抽象，按 build tag 分平台实现，供"同物理文件去重 / 可释放空间正确计数 / 硬链接合并"统一使用。

### 3.11 决策 11：FileKey 按需解析（Windows 性能关键）

**问题**：若在阶段 0 对全部文件解析 FileKey，Windows 上等于对 **100% 的文件**额外执行一次 CreateFile/CloseFile——而硬链接去重只对"同 size 候选组"有意义。

**方案**：

| 平台 | 解析时机 | 成本 |
|---|---|---|
| macOS / Linux | 阶段 0 遍历时 lstat 附带 | 零（syscall 本就返回） |
| **Windows** | **阶段 1.5：仅候选组内（同 size ≥2，通常 <10% 文件）** | 90%+ 文件零额外句柄 |

**效果**：独 size 文件（占大多数）完全不付出 FileKey 成本；候选组内开句柄的成本与阶段 2 的文件读取合并优化空间（同一次 open 顺带完成 FileKey + 首尾读取的顺序调度）。

**顺序保证**：阶段 1 size 分组 → 阶段 1.5 候选组 FileKey 去重 →（组内剩 1 个则整组淘汰）→ 阶段 2 预筛。

### 3.12 决策 12：结果集不持久化（仅缓存哈希指纹）

- `DuplicateGroup` 结果仅存内存，保留至下一次扫描或应用退出；
- 理由：分组结果依赖"扫描根目录 + 过滤器 + 时刻"三元组，持久化后极易过期误导用户；而缓存中持久化的"文件→哈希"指纹使二次扫描**秒级重建**分组，体验上等效于"结果恢复了"；
- 缓存损坏的最坏后果 = 退化为首次扫描速度，无正确性影响。

## 4. 核心流程设计推演

### 4.1 扫描流程（阶段 0 / 1 / 1.5）

```
Roots ─→ 并行遍历（目录队列）──→ 收集 FileEntry（size/mtime/path）
          │                       unix：lstat 顺带 FileKey；win：暂不解析
          ├─ 跳过：符号链接、0 字节（内置）、隐藏文件（可选 MinSize 默认 0 = 不限）
          └─ 应用过滤器：扩展名 / 大小区间 / 路径排除
                     ↓
阶段 1：按 size 分组 → 淘汰独 size 组（90%+）
                     ↓
阶段 1.5：候选组内解析 FileKey（win 此时开句柄）→ 硬链接去重
          → 组内剩 1 个 ⇒ 整组淘汰
```

**设计点**：
- 遍历使用 `ReadDir` 批量读取并分发到多个 goroutine 按目录切分；
- 重叠扫描根目录按"已访问目录集合"去重（mac/win 按大小写折叠规则比较）；
- Windows 阶段 1.5 的 FileKey 解析与阶段 2 的首尾读取在同一任务内调度（一次 open 完成两件事）。

### 4.2 哈希调度设计

```
阶段 2（首尾哈希）：
  候选组 ──→ Worker Pool（N=线程数）
            每个任务：open 一次 →（win：顺带解析 FileKey）→ ReadAt 头 64KiB → ReadAt 尾 64KiB
                     → xxHash64 → 关闭句柄
            小文件（≤128KiB）：单次读全文件，同趟完成 xxHash + BLAKE3
  结果 ──→ 按 (size, headHash, tailHash) 分组 → 组内文件数 ≥2 才进入阶段 3
           （小文件已持有全量 BLAKE3，直接参与最终分组）

阶段 3（全量哈希）：
  剩余候选（仅大文件）──→ Worker Pool
             大文件（>512MB）按 16MiB 切片并行 → BLAKE3 tree hash 合并
  结果 ──→ 按 (size, blake3) 分组 → 组内 ≥2 ⇒ DuplicateGroup
```

**设计点**：
- head/tail 在**同一文件句柄上做两次 `ReadAt`**（一次 open，两段定位读取）；
- 文件句柄由 `os.File` 管理，哈希完立即关闭，避免句柄耗尽（macOS soft limit 低）；
- 失败文件（权限/IO 错误）单独记录并上报 UI，不中断整体流程；
- 大文件切片并行时，同一文件的多个切片任务由同一聚合器归并（channel 收集 → tree hash 拼接），保证合并顺序正确。

### 4.3 结果呈现设计

- 结果集以 `DuplicateGroup` 为单位分页，前端虚拟滚动，支持万组级流畅浏览；
- 每组显示：可释放空间（`(n-1)*size`，硬链接已在阶段 1.5 剔除）、文件数、每文件路径/大小/mtime、勾选状态；
- 组内默认保留建议项高亮，其余勾选为"待删除"；
- 顶部工具栏：全选组、清除选择、一键保留策略、执行清理、导出；失败清单独立入口。

## 5. UI/UX 设计思路

### 5.1 为什么用 Web 技术做 UI

- 原生桌面 GUI（Go/Fyne、Qt/Python）在"现代美观、动画流畅、暗色主题、响应式布局"上投入产出比远低于 Web 技术栈；
- 用户偏好"Web 风格布局 + 简洁高效"，Vue3 + CSS 变量可完全定制；
- Wails 前端仍编译进单一二进制，无浏览器依赖。

### 5.2 交互设计原则落地

| 原则 | 具体体现 |
|---|---|
| 渐进披露 | 高级选项（paranoid 逐字节确认、线程数、缓存管理）收进"高级设置"折叠区 |
| 默认安全 | 删除按钮仅在勾选后激活；默认进回收站 |
| 实时可见 | 扫描中显示阶段、速度、剩余时间，可暂停/取消 |
| 结果可复核 | 预览面板 + 打开所在文件夹 + 路径全显示开关 |
| 减少输入 | 目录拖拽添加、保留策略一键式，避免手动勾选每个文件 |

### 5.3 视觉风格

- 主色调：中性灰 + 品牌蓝（亮色）/ 深空黑 + 蓝紫点缀（暗色）；
- 排版：13~14px 系统字体栈，结果表格等高密度信息使用 12.5px；
- 动效：列表过渡 150ms，进度条平滑动画，不过度装饰；
- 组件风格：圆角 8px、1px 描边卡片、悬浮阴影，符合 macOS/Windows 双平台审美。

## 6. 性能设计思路（从 IO 到 UI 的端到端优化）

1. **读盘次数最小化**（核心）：多阶段过滤，让全量读盘只发生在真正的候选上；
2. **句柄开销最小化**：Windows FileKey 按需解析（决策 11），候选任务内一次 open 兼做 FileKey + 首尾读取；
3. **读盘方式优化**：流式大块读（1MiB），避免小缓冲系统调用风暴；`ReadAt` 支持并发分片；
4. **哈希计算最优化**：BLAKE3 tree hash 多核并行；xxHash64 预筛几乎零成本；小文件一趟双哈希；
5. **调度最优**：Worker Pool 与线程数解耦（goroutine 数可大于 worker 数），IO 等待时自动让出；
6. **内存受控**：sync.Pool 复用缓冲区；结果集只存 ID；进度推送节流；
7. **缓存复用**：二次扫描 10x 提速；增量扫描只处理 mtime/size 变化的文件；
8. **UI 不阻塞**：后端全部异步调用，UI 只订阅事件流，主线程零重活。

## 7. 风险与取舍记录

| 决策 | 放弃的选项 | 放弃理由 | 未来回退条件 |
|---|---|---|---|
| 阶段间串行 | 全流水线并行 | 进度/结果不确定性高，且磁盘并发冲突反而变慢 | 数据量级别验证有收益时 |
| 不做 CDC | 增量相似去重 | 复杂度高，非本阶段核心需求 | 扩展"相似文件"模式时引入 FastCDC |
| 不做图片相似度（V1） | dupeGuru 式感知哈希 | 扩大范围，影响 V1 交付质量 | V2.0 候选 |
| BLAKE3 而非 SHA-256 | FIPS 合规 | 桌面消费级工具无合规需求 | 企业版需求出现时 |
| 自研 XDG Trash | 调 `gio trash` | 依赖桌面环境，违背单二进制 | 无（自研是一次性成本） |
| SQLite 而非 bbolt | 纯 KV | 需要按 size 索引与统计查询 | 无 |
| 结果不持久化 | 结果落库 | 分组依赖扫描范围/过滤器/时刻，极易过期 | 若用户强需求"会话恢复"再议 |
| FileKey 延迟解析（win） | 遍历时全量解析 | 每文件多一次 open，得不偿失 | 无 |

## 1. 产品概述

FileDedup 是一款**按内容识别重复文件**的桌面工具，核心保证是：

- **内容级判定**：只有完整内容完全一致的文件才会被分为一组，文件名相似但内容不同的一律不报。
- **操作前校验**：任何清理动作执行前都会重新校验文件内容，扫描后文件被修改过则拒绝操作。
- **默认可回滚**：默认走系统回收站，永久删除需要显式二次确认；清理动手前先写"写前账本"，回收站（macOS/Linux）/移动/硬链接/软链接可在应用内逐项回撤（**Windows 回收站与永久删除不可应用内回撤**，见 §6.7）。账本写不进时，承诺可回撤的操作直接拒绝执行。

内置行为（不可关闭）：

| 行为 | 说明 |
|---|---|
| 跳过符号链接 | 不跟随链接，避免环路与重复计数 |
| 跳过 0 字节文件 | 空文件无内容语义，不参与分组 |
| 硬链接只计一次 | 同一物理文件（同 inode/FileId）的多个路径不会互相判为重复 |
| 跳过工作临时文件 | `.fdd-tmp` / `.fdd-old` 等合并过程残留不参与分组（见 §6.3.1）。计数见 `fdd-cli` 的 `stats.skipped_work_temp_files` / 扫描完成事件的 `skippedWorkTempFiles` |
| 跳过系统保护目录与伪文件 | 卷元数据目录整棵不进入：`$Recycle.Bin`、`System Volume Information`、`lost+found`、`.Spotlight-V100`、`.fseventsd`、`.Trashes`、`.DocumentRevisions-V100`、Time Machine 本地快照；Linux 另认绝对路径 `/proc` `/sys` `/dev` `/run`；macOS 另认 `/System` 整棵，以及 `/private` 下**系统自己的八棵子树**：`/private/etc`、`/private/var/db`、`/private/var/log`、`/private/var/root`、`/private/var/spool`、`/private/var/at`、`/private/var/empty`、`/private/var/run`。用户级临时区 `/private/tmp` 与 `/private/var/folders`（你自己的缓存与临时文件）**不在这份清单里**——以 `/` 或 `/private` 为根扫描时这两片照常进入，因为里面是真实的可去重数据而不是系统元数据。Windows 盘根的 `pagefile.sys` / `hiberfil.sys` / `swapfile.sys` / `DumpStack.log.tmp`、以及保留设备名（`CON` / `PRN` / `AUX` / `NUL` / `COM1-9` / `LPT1-9`，含带扩展名的写法）同样跳过 |
| 跳过云端占位文件（**可关闭**） | OneDrive / iCloud Drive 这类同步盘在本地放的"只有元数据、内容还在云端"的文件不参与去重：macOS 认 `st_flags` 的 dataless 位，Windows 认 `RECALL_ON_DATA_ACCESS` / `RECALL_ON_OPEN` 两个属性位；Linux 没有统一占位语义，**这一条在 Linux 上恒不触发**。计数见 `fdd-cli` 的 `stats.skipped_cloud_files` / 扫描完成事件的 `skippedCloudFiles`。要照常处理它们见 §8 的 `-allow-cloud-hydration` |

**这条为什么不可关闭，唯一的例外是什么**：上面那些位置里装的是"已删除待清理的副本"或"卷与内核的元数据"，收进语料的后果不是噪声而是真实伤害——回收站里那份副本会和原位残留或其他卷的同内容文件配成重复组，用户照着结果再删一次；ACL 拒绝的目录则把失败清单灌满，真正读不了的文件被淹没。因此清单不受任何设置影响。唯一的通道是**你显式把被保护的目录（或它内部的某个子目录）设为扫描根**：这时按你的指名照常扫描，但这一轮会记下"哪些根已脱离系统保护"（`unprotectedRoots`，随扫描完成事件下发；结果页横幅属后续版本，界面当前不呈现）。点名一个**指向**被保护目录的符号链接同样算点名——真身也会被问一次清单（M84），而记下的仍是**你点的那条形**，遍历与展示路径不换成解析后的真身。计数在命令行报告里可见：`fdd-cli` 的 `stats.protected_dirs` / `stats.protected_files`。

**上一表里只有"云端占位"这一条是可以关的**：保护清单挡的是误伤，占位挡的是"你以为在省空间、其实先替自己下了一遍"。开启 `-allow-cloud-hydration` 后占位文件按普通文件参与去重，代价是**按需下载真的会发生**（哈希阶段要读文件首尾样本），且这一档下 `skipped_cloud_files` 恒为 0——没有跳过这件事，就不报跳过的数。

## 2. 快速上手

### 2.1 启动

```bash
cd /Volumes/fx/Object/FileDedup && wails dev     # 开发模式
# 或使用构建产物直接运行
```

窗口默认 1180×780，最小 920×620。

### 2.2 一次完整清理流程

1. **添加扫描目录**：点击选择目录，或直接把文件夹拖入窗口（支持多根目录；重叠根会自动去重，只扫描外层）。
2. **设置过滤器**（可选）：按扩展名 / 大小区间 / 排除路径缩小范围。
3. **开始扫描**：进度条分阶段推进（扫描目录 → 预筛哈希 → 全量哈希 → 可选逐字节确认），支持暂停 / 恢复 / 取消。
4. **阅读结果**：按"可释放空间 / 单文件大小 / 文件数"排序，按扩展名筛选，分页加载。
5. **落定保留项**：应用一键保留策略（路径最短 / 最新 / 最旧 / 指定目录优先级），保留项受后端保护、任何操作都不会动它；未应用策略时界面上的星标只是**建议**（§6.2）。清理对象则按组逐项勾选（`⌘A` 可全选当前已加载的冗余项）。
6. **执行清理**：回收站（默认）/ 永久删除 / 移动到指定目录 / 硬链接合并。
7. **查看反馈**：操作结果分 OK / 失败 / 跳过 / 已取消四类逐项列明，失败项进入统一失败清单。

## 3. 检测算法详解

整个检测是一条**多阶段漏斗**（`internal/dedup/pipeline.go`），每一层都只淘汰"不可能重复"的文件，逐层把读盘量压到最低：

```
全部文件
  │ 阶段 0  元数据扫描（并行遍历目录）
  ▼
按文件大小分组 ── 独享大小的直接淘汰（大小不同内容必不同）
  │ 阶段 1
  ▼
候选文件（大小 ≥2 个的组）
  │ 阶段 1.5  FileKey 去重（硬链接只保留一个路径）
  ▼
按 (size, 4 点采样指纹) 分桶 ── 采样唯一桶直接淘汰
  │ 阶段 2  四点 xxHash64 预筛
  ▼
同采样桶内成员 ≥2 的文件
  │ 阶段 3  全量 BLAKE3-256（只补算缺失者）
  ▼
按 (size, 全量哈希) 聚合 → 重复组
  │ 阶段 4（可选 paranoid）逐字节比对最终确认
  ▼
输出结果
```

### 3.1 阶段 0：并行目录扫描（`internal/scanner`）

- 固定 worker 池遍历，worker 既是消费者也是生产者（发现子目录继续入队）；采用**无界目录队列 + 条件变量**，从根上消除有界队列的死锁风险。
- 大小写折叠去重：重叠根（如同时选了 `a` 和 `a/b`）只保留外层；判定"A 与 a 是否同一目录"**按卷实测**而不是照编译目标猜（`internal/fscase`）——在目标目录写一个混合大小写的临时隐藏文件 `.fdd-case-probe-<序号>`，换一种大小写去 Lstat，命中即该卷不敏感；探测结束立即删除，只读卷 / 无写权限 / 目录不存在时**先问卷型**（M85，2026-09-22 裁定「按卷型分岔」）：卷型名是 `msdos` / `fat` / `exfat` / `ntfs` 之一，就算**确证**该卷不区分大小写（这类卷天生不分，排除模式随之放宽，§5.2）；★ 这一档的读数目前**只有 macOS 有**（走 statfs），Windows / Linux 上卷型名恒为空 ⇒ 跳过这一档直接退回平台默认（darwin/windows 不敏感、其余敏感），且这一格如实记为**未确证**。**确证**与**退默认**是两格，不合并成"探测不到"一句话。★ 这一圈探测**听取消**（2026-09-23，第四轮全仓审查补，R2-2）：探测是写盘动作，网络卷与死挂载（拔走的 SMB、硬挂载的 NFS）上可以长时间不返回，改前扫描停在"扫描目录"这一步**取消不掉**（只能杀进程）；现在扫描启动前那次探测会立即让路，并且本轮**不**带着没问全的折叠继续扫——宁可停在这一步，也不拿"猜出来的不敏感"去合并两棵真不同的树。如实的边界：那次磁盘查询本身仍停在原地直到系统返回（内核态不可中断），变化的是扫描不再陪着它等。探测只对**多根扫描的每个根**、**"保留指定目录"的每个目录**，以及**写了排除路径的单根扫描**各做一次（结论按目录缓存）；**单根且没写排除路径时既不写探测文件、也不做大小写折叠**——此时遍历里每个目录只会以唯一拼写出现（根按原样入队，其后每个路径都是"父路径 + 目录项原名"拼出，链接/junction 已跳过），没有可并之物，折叠只可能把大小写不同的两棵**不同**目录误并成一棵，在大小写敏感卷上表现为"其中一棵子树整棵不见、且没有任何失败记录"。单根那次探测只为排除路径的按卷大小写放宽服务（§5.2），不改变上面"折叠不做"的结论。问卷过但拿不到确证结论的根数计入 `fdd-cli` 的 `stats.case_probe_unproven`；这个数为 0 只说明"本轮没有需要卷语义而探不到的根"，不说明"该卷已实测"。
- 目录级剪枝：命中排除模式的目录**整棵子树不再进入**（详见 §5.3），"排除"不仅省结果，更省遍历时间。
- 每个文件记录：路径、大小、mtime（纳秒）、小写扩展名、平台 FileKey（unix 由 lstat 顺带取得，Windows 仅对候选文件按需解析）。

### 3.2 阶段 1 / 1.5：大小分组与硬链接去重

- **大小分组**：大小不同 → 内容必不同，这一层零读盘淘汰绝大多数文件。
- **FileKey 去重**：同一物理文件（unix: 设备号+inode；Windows: 卷序列号+FileId）出现在多个路径时只保留一个代表（路径较短者），然后重新检查各组是否还剩 ≥2 个成员。因此**硬链接的多个路径永远不会互判为重复**，"可释放空间"统计也因此不含虚数。

### 3.3 阶段 2：四点采样预筛（`internal/hasher`）

对每个候选文件按采样点最多读 **4 × 64 KiB = 256 KiB**：

| 文件大小 | 做法 |
|---|---|
| ≤ 128 KiB（小文件） | 读全文件，**一趟**同时算出采样指纹与 BLAKE3-256（预筛即全量，后续无需再读） |
| > 128 KiB（大文件） | `ReadAt` 读 4 个 64 KiB 采样点，各算一个 xxHash64：**头部**（偏移 0）、**中段** `size/2`、**后段** `3size/4`、**尾部**（`size − 64 KiB`；不足处钳制） |

分桶键为五元组 `(size, head, mid1, mid2, tail)`。设计依据：内容不同的文件在大小与 4 个分散采样点同时撞车的概率可忽略；而内容相同的文件五者必然相同——**保证零漏报**。中段采样还使"首尾相同、仅中间被改"的篡改可被指纹识别，这是缓存命中比对可信的前提（§4.3）。

### 3.4 阶段 3：全量 BLAKE3-256

只对"同采样桶内成员 ≥2、且还没有全量哈希"的文件读全文件：

- ≤ 512 MiB：1 MiB 块顺序流式哈希。
- > 512 MiB：**16 MiB 分段预取流水线**——后台协程按段预读（深度 2），主协程按段序喂入单一 BLAKE3 Hasher，IO 与计算重叠；段缓冲用 depth+1 环形池复用，分配次数与文件大小解耦。结果与顺序读取**逐位一致**（由等价性测试保证）。

最终按 `(size, BLAKE3-256)` 聚合出重复组。BLAKE3-256 的碰撞概率在工程上视为 0，因此**哈希相同即认定内容相同**；对不可容忍任何理论风险的用户，可开启 paranoid 模式（§3.6）。

### 3.5 并发与资源模型

| 项 | 默认 | 上限 | 说明 |
|---|---|---|---|
| 扫描线程数 | 0 = 自动 | 64 | 自动 = 核数 − 1；检测到扫描根在机械盘/网络卷时自动降至低并发档（避免寻道抖动互相拖累） |
| 读缓冲 | `sync.Pool` 复用 | — | 1 MiB 流式缓冲 / 128 KiB 小文件一趟缓冲 / 64 KiB 采样缓冲 / 16 MiB 段缓冲各自成池，杜绝分配风暴 |
| 清理操作并发 | 4 | 4 | 单文件元数据 syscall 延迟主导，有界并发缩短大批量耗时 |

### 3.6 paranoid 模式（逐字节确认）

开启后，每个重复组内的所有文件与代表文件做**逐字节流式比对**（256 KiB 双缓冲，整趟只分配一对）。任何不一致者移出组并计入失败清单。适用于内容正确性要求极高的场景（如备份核对），代价是结果阶段多一趟全量读盘。

## 4. 哈希缓存：存放位置与复用策略

缓存模块：`internal/cache/cache.go`（SQLite + WAL）。缓存的唯一目的是**加速二次及以后的扫描**——首次扫描全量计算，之后未变化的文件直接复用上次的哈希，跳过全量读盘。缓存丢失只影响速度，不影响结果正确性。

### 4.1 存放位置

缓存与设置都存放在系统配置目录下的 `FileDedup/` 文件夹（`os.UserConfigDir()`）：

| 平台 | 路径 |
|---|---|
| macOS | `~/Library/Application Support/FileDedup/` |
| Windows | `%AppData%\FileDedup\` |
| Linux | `~/.config/FileDedup/` |

目录内容：

| 文件 | 说明 |
|---|---|
| `cache.db` | SQLite 哈希缓存主库 |
| `cache.db-wal` / `cache.db-shm` | WAL 模式伴随文件 |
| `history.db` | 扫描历史 + 清理账本（回撤依据），与缓存库物理隔离，见 §6.6 / §6.7 |
| `history.db-wal` / `history.db-shm` | 同上 |
| `settings.json` | 应用设置（线程数、主题、语言、默认过滤器） |
| `*.broken-<时间戳>`（含 `-wal`/`-shm` 后缀） | 库影像确证损坏时的隔离残留，见 §4.7 |

配置目录不可用时的回退：退到家目录 `~/.filededup/`（而非只读风险更高的当前工作目录）。

### 4.2 数据结构

```sql
-- 主表：每行 = 一个文件的哈希记录
CREATE TABLE hash_cache (
    path     TEXT    NOT NULL PRIMARY KEY,  -- 文件绝对路径
    size     INTEGER NOT NULL,              -- 文件大小（字节）
    mtime_ns INTEGER NOT NULL,              -- 修改时间（纳秒）
    partial  BLOB    NOT NULL,              -- 32 字节：4 采样点 xxHash64（小文件=全文件哈希）
    full     BLOB,                          -- 32 字节 BLAKE3-256；NULL = 未算过全量
    last_hit INTEGER NOT NULL DEFAULT 0,    -- 最近命中时间（LRU 依据）
    dev      INTEGER NOT NULL DEFAULT 0,    -- 物理身份：设备号（unix）/ 卷序列号（Windows）；0 = 未解析
    ino      INTEGER NOT NULL DEFAULT 0,    -- 物理身份：inode / 64 位文件索引
    ctime_ns INTEGER NOT NULL DEFAULT 0     -- 物理身份：状态变更时间（Windows 取不到时为 0）
);
-- 索引
CREATE INDEX idx_cache_last_hit ON hash_cache(last_hit);
-- 元信息表
CREATE TABLE cache_meta (key TEXT PRIMARY KEY, value TEXT);  -- 记录算法语义版本
```

注意：**大文件预筛淘汰后只缓存采样（partial），full 为 NULL**——它从未被全量读过，自然没有全量哈希可存。

### 4.3 命中判定（复用条件）

一次扫描中，某文件的缓存行被复用必须**同时满足四道检查**：

1. **元数据一致**：`path` 存在，且当前 `size` 与 `mtime_ns` 与缓存行完全一致；
2. **物理身份一致**：当前文件的 `(dev, ino, ctime_ns)` 与缓存行记录一致。unix 侧取自 `fstat`（设备号 / inode / ctime）；Windows 侧取自文件句柄的**卷序列号 + 64 位文件索引**（两者任一为 0 即视为该卷不给稳定索引、按未解析处理），change time 由另一次句柄查询补充、取不到时只丢这一重证据（记为 0），不影响身份成立（算哈希本来就要开句柄，这里无额外开档开销）。路径同、时间戳同但已被换成另一个文件（覆盖写、COW 恢复、换盘）会被这一道拦下。**任一侧未解析到身份时（卷不提供稳定索引、句柄查询失败、旧行身份列为 0）这一道无从比对、直接放行**，正确性退回第 1、3 道承担——详见下面的分卷说明。另注意 ctime 参与比对：`chmod` / 写 xattr 等推进 ctime 的合法元数据操作会让该行按未命中重算，只多花一次读盘，不影响正确性；
3. **采样一致**：即使前两道一致，应用仍会重读 4 点采样（≤256 KiB）并与缓存中的采样指纹比对——防止 `cp -p`、COW、FAT 2 秒粒度、原地改写保 mtime 等情况造成"内容变了但时间戳没变"的假命中；
4. **采样非全零**：采样为全零的行视为脏行（历史版本缺陷遗留），一律不信任、重算。

四道全过才信任缓存中的 `full`，**免除阶段 3 的全量读盘**；任何一道不过即当作未命中重新计算。采样比对的开销极小（每文件最多 256 KiB），换来的是**足够强的防误判**——但结论强度必须按卷分开讲：

- **身份确实解析成功的卷与文件**（本地 NTFS/ReFS、ext4/xfs/APFS 等，且本次查询成功）：第 2 道在**它自己的职责范围内**给出硬保证——缓存行只对**它当初读过的那个物理文件**有效，路径被换成另一个文件即失效。它管不了"同一个文件被原地改写且 mtime 保持不变"，那一类由第 3 道兜；
- **身份缺位的卷与记录**（FAT/exFAT 等不给稳定文件索引的卷、部分网络共享，以及身份列为 0 的旧行）：第 2 道形同跳过，正确性只由第 1、3 道（元数据 + 四点采样）承担。采样全等而内容其实不同，理论上仍可能（两个文件恰好在头尾与两个中点各 64 KiB 窗口内一致），这类卷上缓存是**加速手段而非等价证明**；拿不准时关掉缓存或跑一次 `-paranoid` 全量比对。

### 4.4 写回策略

- **批量 UPSERT、单事务**：整个任务（含取消的任务）结束时一次性写回所有新算哈希，避免逐条提交的 IO 放大。取消的任务不浪费——已算出的哈希照常入缓存。
- **原位补全**：大文件阶段 2 先写采样行，阶段 3 算完全量后**原位更新**该行的 full 字段（而非追加新行），避免覆盖把采样清零。
- **命中续期（LRU 语义）**：命中的文件在任务结束时批量刷新 `last_hit`，保证高频访问的热文件不被淘汰。
- **写入防御**：UPSERT 时若新采样为全零则保留旧采样。

### 4.5 版本控制与失效

缓存行内含算法语义版本（当前 `blake3-256+xxh64-4pt+id-v3`）。以下任一变化都会 bump 版本：哈希算法或长度、采样点数与采样参数、字段语义、表结构。**版本不符（含旧库无版本标记）时整表作废重建**——防止旧语义的缓存行继续命中、造出错误分组。

身份列（`dev`/`ino`/`ctime_ns`）随 v3 一起引入，因此无需额外开关：v3 之前写入的行身份三列全为 0，与解析成功的当前身份必然不符，第一次扫描按未命中重算并顺手补齐，之后即正常参与比对。代价是一次重算，收益是不留下"新证据被零值行架空"的窗口。

### 4.6 容量与淘汰

- 条目上限：**500,000** 条（`cache.MaxEntries`）。
- 每批写回后检查，超限即按 `last_hit` **最旧优先淘汰**到上限以内（配合命中续期，即标准 LRU），淘汰条数记入缓存统计的 `lastEvicted`。

### 4.7 损坏自愈与维护

- **只有确证损坏才重建，且只改名不删除**：打开失败时，先判定错误是否确指「库文件本身不是一份可用影像」（`file is not a database` / `database disk image is malformed` / `page N is never used` 等强指征）。判定为损坏时把 `cache.db` 连同 `-wal`/`-shm` **改名隔离为 `cache.db.broken-<时间戳>`** 后重建，原始影像仍在原地可找回；最坏退化为一次首扫速度。
- **暂时性故障绝不删库**：`SQLITE_BUSY`（另一进程占用）、磁盘满、目录只读、权限不足等一律直接报错、不动任何文件，本次运行退化为"无缓存全量重算"。判定保守——认不准就当暂时故障，宁可功能暂时不可用，也不拿一次误判换整表缓存丢失。
- 缓存不可用不阻塞应用：只在启动时于 stderr 留痕一次。
- 手动清空：设置里的"清空缓存"（`CacheClear`）只清哈希表，不动元信息。该按钮是**两段式**：第一下把后果写在原处（"下次扫描将退化为首次扫描速度"）并给出「确认清空 / 取消」，第二下才真的清——不存在弹系统对话框那一步（M154 批次 R3-5，2026-09-23；改前这里用的是浏览器原生 `confirm()`，样式与键盘行为都不受应用控制，在 webview 里还可能被静默挡掉，表现为"点了没反应"）。
- 隔离残留（`*.broken-*`）不会被自动清理或再次读取，确认无需找回后可自行删除。
- 体积参考：macOS 正常运行时主库约 16 KB 起，随文件数增长（每条约 100+ 字节）。

### 4.8 CLI 场景的缓存复用

`fdd-cli` 默认禁用缓存；传 `-cache <db路径>` 启用。可让 GUI 与 CLI 共用同一个 db，或给 CLI 单独指定一个长期缓存路径，实现跨次运行复用。

## 5. 扫描过滤器详解

过滤器在扫描前一次性**预编译**（扩展名集合小写归一；≥12 项时建哈希 map 查表，短列表走线性比较），逐文件判定零热路径开销。

### 5.1 可用过滤条件

| 条件 | 语义 |
|---|---|
| 包含扩展名 | 空 = 全部；如 `.jpg`（大小写不敏感） |
| 排除扩展名 | 命中即跳过 |
| 最小/最大大小 | 0 = 不限 |
| 包含隐藏文件 | 默认排除 `.` 开头的文件与目录 |
| 排除路径（glob） | 见下 |

上表都是"命中即丢弃、不额外报数"的过滤条件。**云端占位不在其列**：它排在这些过滤之前，
且单独计数（§1、§8），因为"被规则挡掉"和"在云端没下载"是两件需要分开说的事。
命令行开关是 `-allow-cloud-hydration`，界面暂无对应控件。

同理，**应用自己的工作临时文件也不在其列**：名字判定排在上述全部过滤之前，单独计入
`stats.skipped_work_temp_files`（§1 表、§6.3.1）。这个数因此不随你调过滤条件而变——
它数的是"盘上有多少这类名字的文件"，不是"有多少本可以进语料"。

### 5.2 排除路径 glob 语义

| 模式形态 | 匹配范围 |
|---|---|
| `node_modules`、`*.tmp`（不含 `/`） | 任意路径段（目录名或文件名）命中即排除 |
| `a/b`、`a/b/`（字面前缀，无通配） | 该目录及其**全部后代** |
| `a/b/**`（末尾递归） | 同上，跨任意层 |
| `a/b/*`（末尾单 `*`） | 仅 `a/b` 的**直接子层**，不含更深后代 |
| `*/build`、`a/**/b` 等（通配在中间） | 精确按模式匹配相对路径，不向后代传播 |

分隔符统一按 `/` 处理：模式里写 `a\b` 与 `a/b` 等价，三平台匹配结果一致。`*` 只匹配单层、`**` 跨任意层（故 `a/b/*` 不会命中 `a/b/c/d`）。

**大小写（M105）**：在**已确证不敏感**的卷上，排除模式不分大小写——你写 `Temp` 就能挡住盘上那棵 `TEMP`；
其余情形区分大小写。卷语义来自按卷实测（§3.1，含 M85 的卷型档：只读 / 无写权限的 exFAT、FAT、NTFS 卷由卷型确证；★ 那一档目前**只有 macOS 有读数**，§3.1）。
**探针与卷型都拿不到**而退回平台默认时**不放宽**，
排除范围不随证据缺失而扩大（要放宽就得确证，确证的载体就是 `stats.case_probe_unproven` 那一格）。
多根扫描按**每个条目所属的那根**各自判定：同一轮里外置 NTFS 盘上的 `TEMP` 被排掉、
机内大小写敏感卷上的 `TEMP` 照常扫，两者不会互相串用读数。
目录级剪枝与文件级判定走同一条口径（§5.3），不存在"文件排了、整棵目录没排"的分裂。

**语法无效的模式（2026-09-23 第四轮全仓审查补，R2-4）**：一条模式只要语法无效
（Go 的 `path.Match` 报 `ErrBadPattern`，典型写法是漏了右方括号，如 `build/[`、`node_modules/**[a-`），
它**整条不生效**——不是"排除范围变小"，是一个文件、一个目录都排不掉。方向是安全的
（少排除 = 多扫，不会多删），但扫描不再对它沉默：这一轮会在**失败清单**里留下
一条「排除模式语法无效（path.Match: bad pattern），这一条整条未生效，已按未排除处理」，
路径列就是你在过滤器里敲的那一条原文。

★ 三条如实的边界：
- **报的是归一之后的死活**。模式里的 `\` 会先统一换成 `/`（上面那条分隔符规则），
  所以 `mydir\[` 会被判为无效——它归一后是 `mydir/` 加一个空段的 `[`，在那个世界里本就永不命中，
  不是误伤。
- **只报语法错，不报"语法对但永不命中"**。`a/[z-a]`（倒着写的字符区间）在 Go 里是合法语法，
  扫描照常排除不到任何东西，也不会在失败清单里留痕；判断这一类要重实现一遍 glob 语义，
  本工具刻意不做。写复杂模式后请用结果页核对排除是否真的生效。
- **失败项计数含这些条目**（"失败项 N" 会 +1），且随扫描记录进历史，便于事后追溯是哪一轮、哪条模式。

### 5.3 目录级剪枝

为让"排除"真正省时间，满足以下条件之一时，命中的**目录**会被整棵剪掉（不再进入遍历）：

- 模式不含 `/`（如 `node_modules`）；
- 模式是字面前缀式（`a/b`）或末尾递归式（`a/b/**`）。

其余形态（通配在中间、末尾单 `*`）只做文件级判定——因为按它们剪枝可能误删本该保留的深层文件，结果正确性优先。

## 6. 结果阅读与清理操作

### 6.1 重复组

每组列出：组内文件（路径、大小、修改时间）、单文件大小、**可释放空间 = (文件数 − 1) × 单文件大小**。结果默认按可释放空间降序，其次按组号；也可按文件大小 / 文件数排序，或按扩展名筛选。分页默认 100 组/页，上限 500。

### 6.2 保留策略（一键决策）

| 策略（界面文案） | 规则 |
|---|---|
| 路径最短（默认） | **先比"是否在隐藏目录"**：不在的优先；同等情况下取路径最短者（`ops.pickShortest`，与界面默认建议同一份实现） |
| 最新 | mtime 最大者 |
| 最旧 | mtime 最小者 |
| 指定目录优先级… | 支持添加**多个目录并排序**（↑/↓ 调整优先级，越靠上优先级越高）。按优先级取**首个命中目录**下的那份；同一目录命中多份时保留路径最深者（深层匹配更精确）。目录写法对**大小写**不敏感（按该目录所在卷的语义折叠后比对，§3.1）；**分隔符**那一腿只在 Windows 成立（M63 起按平台取）——那里 `\` 与 `/` 混写等价，macOS / Linux 上 `\` 是文件名里的普通字符，`foo\bar` 不会被当成 `foo/bar` |

> 后端另有一个 `manual`（"按前端已有勾选"）策略值，界面下拉里没有它——目前只能靠上述四种策略落定决策，没有"逐组手动指定保留者"的入口。

**「指定目录」的未匹配组（必须知道）**：某组内**没有任何**重复文件落在所列目录下时，该组不会标出保留者，因而**完全不受"保留项不可清理"的保护**。应用策略后界面会显式弹警告「n 组没有任何重复文件位于保留目录，未标出保留项、不受保护…」——看到它就意味着对这些组仍需手动勾选或改用其他策略，不能当它没发生。

**保护生效时机（重要）**：每组有一列「保留 / 冗余」标记，星标「保留」项在界面上**复选框直接置灰、不可勾选**（组内全选与 `⌘A` 同样跳过它）。但要分清这个标记的两层含义：

- **未应用过策略的组**：星标只是**默认建议**（与"路径最短"策略同一条规则：优先非隐藏目录、再取路径最短）。它只在界面上挡勾选，**后端不认它**——真正执行时保护与否取决于有没有落定决策；
- **执行过"应用保留策略"的组**：星标是**已落定的保留决策**，后端硬拦截任何清理操作（逐个报「保留文件不可操作」）。「重置」清掉决策，星标退回默认建议形态。

关键含义：**星标指向哪个文件会随策略改变**。应用「保留最新」等策略后，原先被建议保留的那份就从「保留」翻成「冗余」并变为可勾选。所以别把星标当成"这一份绝对安全"的承诺：**先选定策略并应用，再执行清理**，清理前浏览一遍每组的星标落点。

### 6.2.1 处理策略（只处理指定文件夹里的文件）

保留策略回答"**留下哪一份**"，处理策略回答"**动哪些项**"。两者相互独立。

工具栏第二行有一个「处理策略」下拉：

| 选项 | 行为 |
|---|---|
| 全部勾选项（默认） | 勾了什么就处理什么，不加任何限制 |
| 仅勾选文件夹内的文件… | 实际处理范围收窄为 **勾选项 ∩ 位于所列文件夹内的文件**（含子文件夹） |

选中第二项后会出现文件夹列表，可添加多个（多选其一命中即算，**不区分顺序**）。

**三个必须知道的性质：**

1. **它不改变你的勾选。** 处理策略只在**执行的那一刻**做过滤，勾选框的选中状态原样不动。显式勾选是用户的明确表达，一个策略设置不该悄悄改写它。
2. **它只能让操作做得更少，不会更多。** 它是在勾选集合内部做减法，不可能处理到任何你没勾的文件。
3. **保留策略永远优先。** 这是**结构性**保证，不是靠优先级裁决：保留项在执行层被硬拒绝，所以即使某个保留文件正好落在优先文件夹内，它也不会被处理。**你不需要在两者冲突时做任何选择。**

**"仅本次结果集"**：优先文件夹列表**不写入设置文件**，仅对当前结果集有效。切换扫描结果、打开另一条历史记录、或重新扫描时，列表自动清空，回到「全部勾选项」。

**计数怎么读（三层，必须分清）**：

| 位置 | 显示 | 含义 |
|---|---|---|
| 保留策略行右侧 | 已选 **N** 项 / 共 X | 你勾选的项数与总字节数 |
| 同上（收窄时追加） | 其中 **M** 项在优先文件夹内 / 共 Y | 真正会被处理的数量与字节数 |
| 确认框 | 将处理 **M** 个文件（已勾选 N 项，其中 N−M 项不在优先文件夹内，本次不改动） | 点「确认」后实际发生的范围 |
| 操作按钮 | 按 M 判定禁用 | **M = 0 时所有操作按钮灰化**——宁可点不动，也不让你以为点了会做 |

> **为什么要显示两个数**：若只显示「已选 40 项」而实际只处理 12 项，你会在操作完成后去核对时发现"对不上"，进而怀疑应用漏做了。落差必须写在明面上。

**问不到数时会明说，不会一直演"正在算"**（2026-09-23 补）：确认框里那两个数来自后端的一次实时判定。
如果这一次问失败了（例如后端在那一刻不可用），确认框会直接显示失败原因并给一颗「重新计算」按钮——
而不是停在"正在核算实际处理范围…"上不动。两种状态的差别值得说清楚：

| 界面说什么 | 实际发生了什么 | 你能做什么 |
|---|---|---|
| 正在核算实际处理范围… | 判定还在途中（通常是几十毫秒） | 等一下，数会自己出来 |
| 命中数没算出来：〈原因〉 + 「重新计算」 | 那一次判定**失败**了，不会自己变好 | 点「重新计算」再问一次 |

两种状态下确认按钮都是灰的：宁可不说数，也不说一个猜出来的数。

**文件夹内没有可处理文件时会明确告知**：如果某个优先文件夹里一个可处理的重复文件都没有（通常是路径写错了），列表下方会点名该文件夹：

> ⚠ 这些优先文件夹内没有可处理的重复文件：`D:\Photos` ——请检查路径是否写对。

执行时如果**所有**勾选项都落在范围外（交集为空），操作会被**直接拒绝**并给出原因，不会静默执行 0 项：

> 所选文件均不在「优先处理的文件夹」范围内（已选 40 项，命中 0 项；其中 1 个文件夹内没有任何可处理的重复文件（可能写错了路径）），已取消操作，未改动任何文件。请调整优先文件夹，或清空该设置后重试。

**典型用法**：

- 只想清理**备份盘**上的副本、保留工作盘不动 → 优先文件夹填备份盘路径；
- 想先清理**下载目录**里的重复下载 → 只填下载目录；
- 想确认某个目录里到底有没有重复文件 → 只填该目录，看计数是否为 0。

### 6.3 五种清理操作

| 操作 | 行为 | 安全机制 |
|---|---|---|
| 移入回收站（推荐默认） | macOS 经 Finder（osascript：路径走 argv 无转义面，每 100 个一批、单批 2 分钟超时防 Finder 无响应挂死）；Windows 系统回收站 API；Linux **自研 XDG Trash**（零外部依赖，不依赖 `gio`；写规范 trashinfo，重名按 `.2/.3` 递增且设有界上限） | 批量失败自动退化为逐文件执行并隔离错误项；可随时取消；Windows 上网络/不可回收卷**直接拒绝**，且会**复核文件是否真的进了回收站**（见 §6.3.3——"回收站删除"在无法回收时会被系统静默变成永久删除） |
| 永久删除 | `os.Remove` 直接删除，**不可恢复** | 后端强制要求显式确认标志，无确认拒绝执行 |
| 移动 | 同卷走 `os.Rename`（原子）；跨卷（EXDEV）为**复制 → 字节数校验 → fsync → 还原权限与 mtime → 删源**，任何一步失败**保留源文件**（此时可能留下"已复制但删源失败"的两份并存，会明确报错，并把那份副本的**实际路径写进提示**「（数据已在 …）」——2026-09-22 第 3 轮 M89/M138：改前执行腿把已复制出的落点丢掉，只留一句错误文本，多出来的那份既不进账本也看不见；回撤腿同一件事第 2 轮已修，见 §6.7）。重名自动递增（`name_1.ext`） | 目标目录必须是本会话内经目录选择器**显式授权**的路径（后端校验，拒绝任意路径）；**串行执行**——并发移动同目录同名文件会产生覆盖竞态，安全优先于速度。注意：跨卷复制只校验字节数，不重算内容哈希（内容级校验发生在操作前的 S1 复核，见 §6.4）；属主与 xattr/ACL 不还原 |
| 硬链接合并 | 用保留源与重复文件合并为同一物理文件，释放目录项占用 | 保留源与目标各自校验内容与物理身份（inode），防"校验后被替换"反向覆盖。**仅同卷可用**（文件系统级限制，跨卷必失败） |
| 软链接合并（跨卷） | 冗余路径替换为指向保留源的**符号链接**，磁盘只保留一份数据，原路径仍可访问 | 与硬链接同等的五步安全流程 + 终局复核；**跨卷专用入口**（同卷不显示，见 §6.3.2）；需要管理员权限且有悬空风险，见 §6.3.2 |

#### 6.3.1 合并后的残留文件

硬链接/软链接合并都会在目标位置留下一份以 `.fdd-old` 结尾的**合并前原始备份**，成功后立即删除。若因文件被占用等原因删不掉：

- 结果条会以「提示 N」告知（鼠标悬停可见逐条明细），**不影响操作本身的成功判定**——链接已经建好了；
- 这类文件名已被扫描器**无条件忽略**，因此不会在下一次扫描里冒出来变成"幽灵重复文件"；本轮跳过了多少个可在命令行报告里看到（`stats.skipped_work_temp_files`，见 §1 表与 §5.1）。
  注意这个数按**名字形态**统计，分不出"我们的残留"与"恰好这样命名的文件"：你自己命名的一个 `报告.pdf.fdd-old` 同样会被算进这个数、同样不会参与去重。想确认是不是残留，看它的内容是否与某个保留源逐字节相同；
- 可以手动删除，也可以留着（它会占一份空间，但数据与保留源完全相同）。

#### 6.3.2 软链接合并（跨卷去重）

**什么时候会出现**：当一个重复组里的文件分布在**不同的磁盘卷**上时，工具栏才会出现「软链接合并（跨卷）」按钮，并在按钮下方显示一条常驻风险说明。同卷的组不显示——同卷用硬链接是严格更优的选择。

**为什么需要它**：硬链接是文件系统级的同卷操作，跨卷必然失败。此前跨卷的重复文件只有两种处置：都留着（不省空间），或删掉一份（原路径消失，依赖该路径的程序找不到文件）。软链接正好补上这个缺口。

**它做了什么**：把冗余路径替换成一个很小的"指针文件"，内容就是保留源的路径；数据只保留一份，打开链接会被系统自动重定向到保留源。

**代价（务必理解）**：软链接指向的是**路径**，不是数据。因此——

| 情况 | 后果 |
|---|---|
| 删除/移动保留源文件 | 所有链接失效（打不开） |
| 保留源所在磁盘未接入（如移动硬盘没插） | 所有链接失效 |
| 保留源所在盘符被重新分配 | 链接可能指向错误的文件 |

硬链接没有这个问题：它是同一份数据的第二个名字，删掉任何一个名字，数据都还在。

**使用建议**：

1. 把**不会移动的磁盘**上的那一份设为保留项（可先用「保留策略」指定目录优先级）；
2. 同卷的文件优先用硬链接（零权限要求、有引用计数保护、无悬空风险）；
3. 合并后如需还原，在「记录」页对该条目点「回撤」即可——**即使链接已经失效也能回撤**（备份仍在，回撤不依赖链接是否有效）。

**权限要求（Windows）**：创建符号链接需要 `SeCreateSymbolicLinkPrivilege`，普通权限默认不具备。任选其一：

| 方案 | 说明 |
|---|---|
| 以管理员身份运行 | 右键程序图标 → 「以管理员身份运行」 |
| 开启开发者模式 | 「设置 → 系统 → 开发者选项」→ 开启「开发者模式」（开启后普通权限即可创建） |
| 改用硬链接合并 | 仅适用于同卷文件；零权限要求 |

三者都不满足时，操作会整体失败，并且**结果条只给出一条汇总指引**（而不是每个文件一条重复的长文案）。失败时不会有任何文件被改动。

**支持的文件系统**：NTFS / ReFS 支持；FAT / exFAT **不支持**（会报"目标位置所在卷不支持符号链接"）。

**如何发现链接已失效**：在「记录」页展开该笔操作的明细，失效的条目会整行标红并显示「链接已失效」标记，悬停可看到目标路径与处置建议。应用**不会自动修复**失效链接——链接失效是你环境变化的结果，自动"修好"可能指向错误的地方，因此只提示、由你决定。

#### 6.3.3 「移入回收站」为什么要复核（Windows）

Windows 上"移入回收站"调用的是系统 Shell 接口（`SHFileOperationW` + `FOF_ALLOWUNDO`）。这个接口有个**官方文档未写明**的性质：**当文件无法进入回收站时，系统不是报错，而是直接永久删除，并返回"成功"**。

这意味着如果不加防备，会出现最坏的结果——**文件从原位置消失了，回收站里却什么都没有，而界面上显示一切正常**。典型触发条件：

| 触发条件 | 说明 |
|---|---|
| **单文件超出回收站配额** | 回收站默认上限约为卷容量的 **5%**。跨硬盘去重的重复文件往往是几十 GB 的镜像/视频/安装包，**一个文件就超过整个回收站容量**——这是本应用用户最可能遇到的场景 |
| 回收站被系统策略禁用 | 注册表 `NukeOnDelete != 0` 时删除**直接永久生效**、不进回收站。**两处都要看**（2026-09-21 补，此前只写了一处）：**全局** `HKCU\…\Explorer\BitBucket\NukeOnDelete`，和**按卷** `HKCU\…\Explorer\BitBucket\Volume\{卷 GUID}\NukeOnDelete`——后者是"在回收站属性对话框里对单个盘勾掉'把文件移到回收站'"时系统写的键，**只看全局键看不到它**（旧版正是因此放行，整批文件被永久删除**之后**才由事后复核报出）。读数取**三态**：`on`（值非 0）→ 拒绝；`off`（键或值确实不存在＝未启用，全新账户的常态）→ 放行；`unknown`（键被 ACL 拒绝、类型不是 `REG_DWORD` 等**读不出**的情形）→ **不据此拒绝**——"未知"不等于"已知禁用"，误拒会让正常用户一个文件都删不掉，该情形改由下面的事后复核兜底 |
| 该卷 `$Recycle.Bin` 不可用 | 被安全软件接管/清理、权限异常等 |

**本应用的两道防线**（`internal/ops/trash_windows.go` + 平台无关的判定层 `recycle_policy.go`）：

1. **事前预检**：逐文件检查卷类型、回收站是否被策略禁用（全局 + 该卷两处）、**单文件是否超过该卷回收站容量上限**。任一不满足即**整批拒绝**，并在提示里说清原因，建议改用「移动」或自行确认后「永久删除」。
2. **事后复核**：调用返回"成功"之后，再独立核对两件事——**源路径确实消失了**（判据 1），且**该卷回收站条目数增量 ≥ 本轮预期入站数**（判据 2，`SHQueryRecycleBinW`）。验不过即报错。
   > **判据 2 有一条已知的退化边界（如实告知）**：它需要**事前**能查到该卷的条目数作基准。事前查不到（移动盘当时休眠/拔线、卷未挂载、权限异常）时，该卷**本轮不参与判据 2**——此时只靠判据 1，"源消失了但回收站里没有"这一类静默永久删除**检不出来**，界面会显示成功。已挂载且可查的卷不受影响；该缺口挂账在 04 §6.6.3（F 组），未修。
   > 事前可查、事后查不到时同样跳过该卷（无从比对，硬判会误报数据丢失）。

因此你可能看到这类**失败**提示（属于保护行为，不是故障）：

> 文件已从原路径消失，但未能确认其进入回收站；可能已被直接删除，请立即到回收站核实（若不在回收站，请停止后续操作并考虑用数据恢复工具找回）

**看到这条提示时该怎么办**：立刻打开系统回收站确认。文件在里面 → 用右键「还原」取回，然后改用「移动」操作；不在里面 → 停止后续清理，尽快用数据恢复工具抢救（写入新数据会降低恢复成功率）。

> **建议**：跨硬盘处理大文件时，优先用「移动」到目标目录，或先手动调大回收站容量（右键回收站 → 属性 → 自定义大小，设为大于最大单文件的数值）。这类操作的成功率取决于系统配置，而不是应用能完全控制的。

### 6.4 操作前内容校验（核心安全机制）

每个待操作文件在执行前都会重新校验（`internal/ops/verify.go`）：

1. 文件已消失（ENOENT）→ 记为**跳过**（目标已达成），不计失败；
2. 打开后**立即 fstat**，当前大小与扫描时不一致 → **拦截**（文件已非扫描时那份）；
3. 其余情况**在同一个已打开的文件句柄上重算全量 BLAKE3** 与组哈希比对：一致才放行（例如仅 touch/chmod 过），不一致一律拦截——哈希所依据的就是随后被操作的那份打开内容，因此"校验与执行之间文件被换掉"只剩一种无害残余：换成**另一份内容完全相同**的文件（删它不丢数据，只是"释放空间"统计偏乐观）。窗口不可能进一步归零，除非独占文件锁，而那不是通用清理工具该做的事；
4. 真正执行删除/移动/合并前，再确认路径上现在的物理身份（`(dev, ino)`，不含 ctime——chmod 等合法元数据操作会推进它）仍是校验时那份文件；已被换成另一个文件则**拦截**。身份一律经 `fsid.FromPathNoFollow` 取得：**不跟随符号链接**，因此"路径被换成链接/目录/改名换 inode"都能识破。两个平台都真实生效——Unix 走 `lstat`，**Windows 走 `CreateFileW` 带 `FILE_FLAG_OPEN_REPARSE_POINT` 的句柄查询**（卷序列号 + 文件索引）。取不到身份即**拦下**：路径打不开（不存在/权限/被独占）拦、原先能解析而现在解析不出（卷行为异常、或位置被换成不提供稳定索引的对象）也拦——宁可拦一次让你重扫，不放行一次可能覆盖他人文件的操作。
   拦截提示的措辞分两格（2026-09-22，第 2 轮审查 M114）：**确证**被换成另一个文件时报「文件在扫描后被替换（inode 已变化），已拦截」；而"读不出身份/原先能解析现在解析不出"这类**我们不知道**的情形报「无法确认文件仍是扫描时那个对象（<底层原因原样带出>），已拦截」——两种都拦，处置完全相同，只是不再把"不知道"说成"确认被替换"。★ 覆盖面（2026-09-22 第 3 轮 M114-a 扩了两处）：这条区分现在落在**清理/移动/回撤前的那道统一复核**、**硬链接合并**（`move.go` 的 `HardlinkMerge` 两道守卫）、**创建软链接**（`symlink.go` 同位两道守卫）三处；「硬链接合并」「创建软链接」两处改前各写死一句「…在校验后被替换（inode 已变化），已拦截（S1）」，现在与统一复核同一把尺子，**拦截方向一字未动**（确证那一格的句子逐字节相同，只是"不知道"那一格不再冒充确证）。★ 还剩三处措辞没跟上：`move.go:72`（跨卷复制期间）、`undo.go:173`、`symlink.go:117`（回撤/建链的第 5 步复核）〔2026-09-23 更正坐标：`undo.go` 那一处因 R2-1（§6.7 规则 2 的顺序补正）新增了一道**已经按四格说法写**的同卷复核，老的那处 `identityStill` 现在在 `undo.go:225`；M149 登记的仍是老那处，未随本批扩面〕——那三处调的是 `identityStill` 这个布尔判据，它把"消失"和"读不出"一起折成 `false`，所以句子仍写成"被替换"；**拦截行为同样是对的**，只有措辞过度声明（已登记为 M149，本批不修，不在此承诺时间）。
   唯一的放行情形是**留底时就未解析**（FAT/exFAT 一类卷不给稳定索引）：那时"我们本来就没有可比的身份"，强行判否会让这些卷完全无法操作，实际防线仍是第 3 道的内容哈希。

   > **口径变更记录**（2026-09-21）：本节此前写"Windows 的 `lstat` 不提供 inode，该平台上这一道恒通过、只能靠第 3 道兜住"。那是旧实现的状况——它正是 2026-09-20 全仓审计的 **AS-H1**（Windows 上五处身份复核与软链接保留项守卫全部空转），修于 `verify.go` 改用 `FromPathNoFollow`。**现在 Windows 与 Unix 在这一道上等价**。（更早的"缓存命中判定走另一条句柄路径、因此 Windows 有效而本道无效"的区分也已消失：两条路仍各有入口（缓存走 `FileKey`/`FromFile`，本道走 `FromPathNoFollow`），但**底层是同一份句柄查询实现**，两个平台都解析得动。）

   **动作前再读一次内容（2026-09-22，M91 补）**：上面第 4 道那次身份复核**通过之后、真正动手之前**，
   永久删除 / 硬链接合并 / 创建软链接这三条会销毁数据的腿还会把该文件的内容**重读并重算一遍哈希**，
   与组哈希比对。为什么非要多读这一遍：`(dev, ino)` 只能区分**同时存活**的两个对象，而"同一个对象被
   就地改写"（编辑器写回、下载器续写）在身份层完全隐形；把 ctime 拉进来也救不了——合并流程自己的
   改名就会推进 ctime。所以那一格只能靠内容闭合。处置与第 1~3 道同一把尺子，只是话要说清拦它的是哪一道：
   **被改过**记失败（「动作前复核失败：文件在扫描后被修改，已拦截：盘上未做任何改动，请重新扫描」）、
   **已消失**记跳过（不计失败）、**读不动**记失败但**不**说"被修改"。**移动与回收站不接这一道**
   （移动不销毁 dup 的内容、回收站随时可回撤）⇒ 这两条腿没有这次额外读盘。★ 代价如实告知：每个待处理的
   重复文件多读多算一遍，实测 32 MiB 两臂 **2.06×** 的校验耗时（吞吐几乎不掉），外推清理 100 GiB 冗余
   约多花 **36 秒**——这是那道"看得见才动手"的保险的价格，不是回归。★ 一处边界：在会回收 inode 号的
   卷上，"先删后建"仍能让身份层点头（本机的 APFS 不还号，那一档本机造不出来），兜住它的正是这同一遍
   内容复核（还来的号上内容必与组哈希不同 ⇒ 拦截），但**不把它说成"竞态已消除"**。

   **顺序补正（2026-09-23，第四轮全仓审查补）**：上面第 4 道承诺的"真正执行删除/移动/合并前，
   再确认路径上现在的物理身份"，在**永久删除**这一条腿上原先排在 M91 那一道内容复核**之前**——
   先问身份，随后是一次可能跑上秒到分钟级的全量重算，算完才按路径删。哈希绑的是打开那一刻的
   文件句柄，重算期间若有人把这个路径改名顶替掉，两道判据照样都点头，而删掉的其实是**顶替者**
   （永久删除没有回收站、不能应用内回撤，是全流程里唯一不可逆的一条腿）。现在永久删除这一条腿
   在内容复核**之后、真正删除之前再问一次身份**，问的是"我刚哈希过的那个对象此刻还在不在这个路径上"。
   措辞与第 4 道同一把尺子，分三格：确证换成了另一个对象报「内容复核通过后、删除前文件被替换
   （inode 已变化），已拦截」；那个位置上的对象**已经没了**（比如你自己删了它）记**跳过**，
   不算失败、也不说"被替换"；读不出身份报「内容复核通过后无法确认文件仍是那个对象（<底层原因
   原样带出>）」。三格都不动盘上一字节。★ 边界如实写：留底身份本就未解析（FAT/exFAT 一类不给
   稳定索引的卷）时这一格放行，兜住它的仍是 M91 那道内容复核——这不是新增漏洞，但也不是全覆盖。
   ★ 另外四条腿本次不涉及，它们的守卫本来就紧贴各自的破坏性动作：回收站在逐个派发前又复核一次、
   移动在跨卷删源前复核、硬链接与软链接合并在改名前一行各自复核。

5. **Windows 专有：NTFS 备用数据流（ADS）防护**（`internal/ads`，2026-09-21 新增）。动任何文件之前，先枚举它在文件系统里的**全部**数据流；只要出现默认流（`::$DATA`，等价写法 `:$DATA`）以外的流，整项**拒绝**并记**失败**（阶段标为 `ads`），文案「文件含备用数据流，去重会丢失备用流内容，已拒绝操作」。理由很直接：删除与合并只带走默认流，`报告.docx:Zone.Identifier`、`f.txt:note` 这类流会随文件一起消失且无处找回。这道守卫对五种操作（回收站 / 永久删除 / 移动 / 硬链接合并 / 软链接）一视同仁。**非 Windows 平台无此语义，这道恒放行**；枚举**读不出**（拒绝访问、未知错误码）时同样拒绝——同第 4 道"宁可拦一次让你重扫"的取舍；文件已不存在、或该卷不支持流（FAT/exFAT 等）则放行，交给正常流程判定。

   > **两条边界（如实告知）**：判据只看"有没有命名流"，**不看命名流内容**——两个默认流相同、命名流不同的文件**仍会被报成重复组**（只是清理被拒，不是没被报重复，挂账 04 §6.8.8 **M35**）；至于 Windows 侧的验证进度，〔2026-09-22 M100 更正〕**结构偏移那一半已有真机读数**（CI 的 windows 真机腿跑绿，run `35642706382`），但**"确实有一个真命名流被拦住"的端到端读数仍未取到**（那条用例有合法跳过出口，CI 不打印跳过明细，分不出真绿与跳过）。挂账 04 §6.8.8 **M32**：与云端占位同族，整体仍是"代码已改、真机未完全兑现"，不按"已验证"读。

> 特别说明：这里**不做"时间戳没变就放行"的捷径**——实测同一时钟刻度内的原地改写可以让 mtime/ctime 逐纳秒不变（FAT32/exFAT 甚至 2 秒内都不变），时间戳无法证明内容未变。代价是大批量清理时多一趟读盘，换取"绝不误删被改过的文件"。

### 6.5 操作结果四态

| 状态 | 含义 |
|---|---|
| OK | 执行成功。**字节数按操作类型分栏，不都算"释放空间"**：永久删除与"移出本卷"计入 `Reclaimed`；回收站计入 `TrashedBytes`（文件仍在盘上，同卷只是一次改名）；硬链接计入 `LinkedBytes`（当期不释放，最后一次链接删除时才释放）；软链接计入 `SymlinkedBytes`。⚠️ 同卷"移动"目前也进 `Reclaimed`，那是已登记的假账（04 §6.8.8 **M40**），修前请按"改名"理解 |
| Skipped | 执行时文件已不存在（视为目标已达成） |
| Failed | 校验拦截或系统错误，逐项注明阶段与原因 |
| Cancelled | 取消后未派发的条目，不会从结果集中移除 |

> **口径变更记录**（2026-09-21，本轮审查 G1）：本表 OK 行原写"执行成功，计入释放空间"。
> 那句话与 `internal/ops/executor.go` 的分栏实现矛盾——M22（2026-09-21）把回收站从
> `Reclaimed` 里拆出去之后，"OK 就算释放"已经不再成立，而照原话读 `Reclaimed` 会把
> 回收站清理的字节当成已释放空间去核对（结果必然对不上，因为文件还在盘上）。

成功/跳过的文件会从结果集中移除，组内不足 2 个时整组消失。

### 6.6 扫描历史

每次**成功完成**的扫描会自动保存一条结果快照到「记录 → 扫描历史」（`history.db`，与哈希缓存 `cache.db` 分离，上限 20 条，超出淘汰最旧）：

- **恢复**：把历史结果重新载入为当前结果集，可直接继续清理——即使相关应用会话早已结束。载入不遍历磁盘，陈旧文件安全由操作前逐文件校验兜底（§6.4）：已被修改的拦截、已消失的按跳过处理。结果页顶部会显示「当前为历史结果」横幅。
- **重扫**：按该条历史的配置（目录/过滤器/线程数/paranoid）重新发起扫描，过滤器数值自动换算回界面 KB 口径。
- **联动裁剪**：在恢复的历史结果上继续清理后，该历史行的文件数与可释放空间同步更新（原始快照数保留展示为「已清理 n」），下次恢复看到的是修剪后的存量。
- 保留决策（含「保留指定目录」结果）随历史持久化，恢复后建议标记不丢。
- 删除/清空历史只影响账本，不影响磁盘文件与当前结果集。
- 入口提示：扫描页顶部有「上次扫描 <时间>」横幅（存在历史时），直接给 恢复 / 查看历史 两个快捷按钮；恢复出的结果页顶部会挂「当前为历史结果（保存于 …），清理前会逐文件校验内容」提示条。

### 6.7 清理记录与回撤

每个清理操作在**动手之前**先把完整计划写入账本（写前日志，`history.db`），执行中逐条收口实际去向。由此：

- 应用若在执行中崩溃/被强杀，重启后残留「待处理」条目会收口为**中断**徽标，提示去文件系统核对现状；
- 回撤同样**写前落账**：条目先标「回撤中」再动文件。若恰好死在两者之间，重启后收口为**回撤失败**并写明「结果未落账」，点「重试回撤」即可——后端会按文件系统现状复核，文件确实已回家就记为已回撤，不会误报「已不存在」；
- 「记录 → 清理记录」列表展示每次操作的时间、类型、条数、已回撤数与回收空间，点「明细」可逐文件查看状态与失败原因。

**账本不可用时的行为（不对称，刻意为之）**：`history.db` 打不开或写不进账本时——

- **承诺过可回撤的操作（回收站 / 移动 / 硬链接合并 / 软链接合并）一律拒绝执行**，报错「清理账本不可用，已拒绝执行」。没有账本就没有回撤与追溯，不能让你按本节预期去清理却事后无从恢复；
- **本就不承诺应用内回撤的操作（永久删除、Windows 回收站）照常执行**，同时在界面上弹出一条明确的留痕提示、stderr 记一行（绝不静默）。这类操作账本故障前后能力等价，一并拒绝反而会把你逼向唯一可用的破坏性路径；
- 因此遇到「清理账本不可用」时，正确处置是**先修库**（见 §4.7 的隔离/重建同样适用于 `history.db`，重启应用即可自愈），而不是改用最危险的永久删除。

**可回撤范围**：

| 操作 | 应用内回撤 | 说明 |
|---|---|---|
| 移入回收站 | macOS / Linux 支持 | 从回收站落点搬回原路径；Windows 回收站 API 拿不到可靠落点映射，记录标注「不可回撤」，请用「打开系统回收站」手动还原 |
| 移动 | 支持 | 从新位置搬回原目录（重名自动递增，不覆盖） |
| 硬链接合并 | 支持 | 拆除链接、恢复独立文件，并从保留源重建内容 |
| 软链接合并 | 支持 | 删除链接、把合并前的原始备份改回原路径。**链接已失效（悬空）时同样可回撤**——数据在备份里，与链接是否有效无关 |
| 永久删除 | **不支持** | 文件已不在磁盘上，无从恢复 |

**回撤的两个入口**：

- **全部回撤**：记录行点「回撤」（二次确认），一次恢复该记录全部「已执行」条目；
- **单项回撤**：点「明细」展开，逐行点「回撤」只恢复该文件；「回撤失败」的条目显示「重试回撤」，修正外部状态后可单独再试。若该行**根本没被受理**（例如账本正在跑上一条），它会立刻回到「回撤」而不是留在"执行中…"（2026-09-23 修，M154 批次 R3-4：改前那一行会永久挂着"执行中…"，看着像一个还在跑的任务，实际什么都没发生）。

**回撤的安全规则**（与正向操作同等严格）：

1. 只处理「已执行」条目；已回撤/失败/跳过的项不重复动。回撤失败的项会留痕原因，可在明细中单项「重试回撤」（天然幂等）。
2. 回收站/移动回撤前提：落点文件仍在且大小与记录一致；**原位置已被占用时不覆盖**，改以 `名称.fdd-restored.扩展名` 落地。落点已空但原位置存在一份尺寸、时间、内容哈希全部吻合记录的文件时，判为「上次回撤已生效、只是没记上账」，直接记成功而非报错。★ 移动回撤若在"已经复制回来、随后删不掉原处的文件"这一步失败，盘上会短暂出现两份：失败提示会**把那份副本的实际路径写出来**（「（数据已在 …）」），而不是只报一句"失败"让你自己找（2026-09-22，第 2 轮审查 M113）。
   > **顺序补正（2026-09-23，第四轮全仓审查补，R2-1）**：上面那句"落点文件仍在且大小与记录一致"
   > 校验的是**动手之前**的那一刻，而把文件搬回原位的是**之后**的一次改名。现在在改名之前紧贴动作
   > 再复核一次落点身份（与 §6.4 清理侧同一把尺子，四类结论同一种分格说法）：
   > 「确证被换成另一个文件」报「…在校验后被替换（inode 已变化），已拦截」，「已经不在」报「…在校验后消失」，
   > 「读不出身份」报「无法确认…仍是校验时那个对象（<底层原因>）」——三种都拦，**原位未做任何改动**，
   > 应用顺手抢下的临时占位也会一并还回去。为什么内容哈希不够：等长且内容相同的另一份副本被改名顶进
   > 回收站落点时，哈希照过，搬回家的却是第三方那份。
   > 边界照旧：账本没有内容证据（升级前的旧记录）或卷不提供稳定索引（FAT/exFAT）时无从留底，
   > 这一道复核按"与确认同一个"同口径放行，行为与该格改前相同。跨卷回退那条链（复制前留底 → 删源前复核）
   > 自 AS-H4 起就在，本项不动它。
3. 硬链接回撤三重防线：目标必须仍是指向保留源的那个 inode（被换成别的文件即拦截；但若它已独立成文件且内容等于记录哈希，同样判为已回撤）；从保留源复制出的内容必须全量 BLAKE3 等于扫描时组哈希（源被篡改即拦截）；全部通过才原子替换，失败时目标现状分毫不动。
3. 硬链接回撤三重防线：目标必须仍是指向保留源的那个 inode（被换成别的文件即拦截；但若它已独立成文件且内容等于记录哈希，同样判为已回撤）；从保留源复制出的内容必须全量 BLAKE3 等于扫描时组哈希（源被篡改即拦截）；全部通过才原子替换，失败时目标现状分毫不动。
4. 软链接回撤：目标位置必须仍是**指向原保留源的符号链接**（你把链接删掉换成自己的文件即拦截，避免误删第三方文件）；备份（`原名.fdd-old`）必须存在；然后删链接、把备份改回原位。由于数据本体一直在备份里，**不需要**从保留源复制内容回来，也就不存在"源被篡改导致恢复出错误内容"的风险面。链接悬空时照常回撤。
5. 回撤不冲销执行账本（「已执行」计数保留），也不自动改动结果集——恢复完成后建议**重新扫描**刷新。
6. 「清空记录」会连带丢弃回撤能力，二次确认时会明确警示；**清理/回撤进行中一律拒绝清空**（账本此刻正在逐项落账，整表删除会让一个仍在动文件的操作失去全部记录），按钮在执行期直接置灰。
7. 执行中改保护集同样被拒：清理/回撤进行中，「应用保留策略」「重置保留决策」「开始扫描」「回撤」共用一道互斥门（后端 `opsRunning`），前端按钮同时置灰——避免出现"界面以为已重置、文件系统仍按旧保留集执行"两套事实。

## 7. 界面功能说明

| 功能 | 说明 |
|---|---|
| 暂停 / 恢复 | 停止派发新工作、在途最小单元完成后挂起：目录遍历按**目录边界**停、预筛与全量哈希按**文件边界**停、paranoid 逐字节比对按**组边界**停；恢复回到原阶段继续 |
| 取消 | 与暂停走**同一批边界**（两行的"粒度"是同一件事，不是两套机制）：遍历在取目录前中断（不再对剩余目录读盘）、预筛/全量哈希在**每个文件之前**过闸、paranoid 比对在**组间、组内逐文件、以及每 256 KiB 块之间**过闸。**要点**：`hasher.HashFull*` 不接 ctx，所以**没开「逐字节确认」时，一个正在全量哈希的大文件只能等它这一趟读完才停得下来**；开了之后才有块粒度的中断点（`verifier.group` / `verifier.equal`，一对 10 GiB 文件也不会拖住取消）。已算哈希照常写缓存（任务结束统一 defer 写回，含取消路径），不浪费。取消中断的文件**不计入失败清单** |
| 内部故障 | worker panic 被拦截并转为**失败（Failed）**状态上报（错误信息含故障阶段），不再伪装成"已取消"，也不再有单个 panic 拖垮整任务或进程 |
| 进度 | 文件数 + 字节数双口径、速度与 ETA；分阶段总量自动切换（预筛读量 / 全量读量），不虚满 |
| 结果预览 | 图片 → 512px JPEG 缩略图（源 ≤20MB、解码 ≤16M 像素防炸）；文本 → 前 4KB（Markdown 扩展名默认**渲染**呈现，可一键切回源码核对）；二进制 → 前 256B HEX |
| 预览 / 定位 | 每行两个图标按钮：**预览**（即上一行的预览面板）与**打开所在文件夹**（系统文件管理器中定位并选中该文件） |
| 记录页 | 两个标签：**扫描历史**（恢复/重扫/删除/清空，§6.6）与**清理记录**（明细/回撤/重试回撤/打开系统回收站/清空，§6.7）。结果页另有一个「打开回收站」按钮，执行完清理后可直达回收站。**无记录时整页给出「暂无清理记录」提示**而非空白（2026-09-20 修正：此前空列表被序列化成 `null`，前端取值即抛错，整页渲染中断） |
| 处理策略 | 结果页工具栏第二行的「处理策略」下拉：把本次操作的处理范围收窄到指定文件夹内（勾选项 ∩ 优先文件夹）。只做执行时过滤、不改勾选；保留策略始终优先（§6.2.1） |
| 设置 | 线程数（0=自动，钳制到 1–64，与引擎同一口径）、主题 light/dark/system、语言 |

**快捷键**（仅在结果页、且无浮层/确认框时生效；焦点在输入框内不拦截）：

| 键 | 作用 |
|---|---|
| `空格` | 预览当前悬停/聚焦项 |
| `⌘A` / `Ctrl+A` | 全选当前已加载结果（保留项照旧不可勾） |
| `Delete` / `Backspace` | 清除选择 |
| `Esc` | 关闭预览面板或失败清单抽屉 |

**关窗口的两段式拦截**：扫描或清理在途时，第一次点关闭**不会退出**——应用先请求中止在途任务，并提示"待其停下后再点一次即可退出"；第二次关闭立即结束进程。硬退出是可接受而非理想的：账本是写前的，未落账条目留在 `planned`，下次启动统一标为**中断**（§6.7），看得到、可追溯。**中止不会回滚已完成的清理部分**。不无限等待是因为一次卡住的回收站/网络卷调用会让窗口永远关不掉。

**结果放量上限**：结果页不无界追加 DOM，初始加载 2000 组，点「继续加载」每次放量 +1000；切换排序/筛选、开始新扫描或载入历史都会重置回初始档并清空勾选。

**语言项现状**：设置里的 `English（M5）` 可以选中并持久化，但界面文案尚未接入 i18n，选择后界面仍为中文。

**操作互斥（一处真相）**：清理或回撤执行期，下列 8 个后端绑定**统一拒绝**（`opsRunning` 互斥门，app.go），前端对应按钮同时置灰：`StartScan`、`ApplyKeepPolicy`、`ClearKeepDecisions`、`LoadScanHistory`、`ExecuteOperation`、`UndoOperation`、`UndoOperationItem`、`ClearOpRecords`。目的是避免出现"界面以为已重置/已换结果集、文件系统仍按旧保留集执行"两套事实（§6.7 规则 6）。

## 8. 命令行工具 fdd-cli

冒烟/批量场景使用，输出 JSON 报告：

```bash
fdd-cli [选项] 目录...

  -threads N        worker 数（0 = 默认 核数-1）
  -paranoid         逐字节确认
  -min-size N       最小文件大小（字节）
  -max-size N       最大文件大小（0 = 不限）
  -exclude LIST     排除扩展名，逗号分隔，如 .tmp,.log
  -hidden           包含隐藏文件
  -allow-cloud-hydration
                    允许读取云端占位文件（会触发按需下载，见 §1）
  -o FILE           输出到文件（默认 stdout）
  -cache PATH       哈希缓存 db 路径（空 = 禁用缓存）
```

报告含统计（文件总数 / 失败数 / 组数 / 可释放字节 / 重复文件数 / 系统保护跳过数 / 云端占位跳过数）、全部分组与失败清单。

**云端占位的计数怎么读**：`stats.skipped_cloud_files` 是这一轮**没参与去重**的云端文件数
（内容还在云端，读它就会下载）。它为 0 有两种含义——盘上确实没有占位文件，或者你加了
`-allow-cloud-hydration`（那一档下照常读取、不计数）。这个数字**不计入**"文件总数"，
也不算失败：它是一笔主动放弃，就像 `protected_files` 一样需要单独看得见。

**可释放空间在这里有两个口径**（`stats.reclaimable_bytes` 与 `stats.reclaimable_bytes_actual`）：
前者按文件**逻辑大小**计（历史数字与既往报表的参照，语义不变），后者按**磁盘实占**计，
也就是清掉这些副本真正能腾出的量。两者的差来自稀疏文件、压缩卷与预分配文件——
一个 8 GiB 的稀疏磁盘镜像可能只占 120 MiB，按逻辑计会把收益报成几十倍。
实占**可以大于**逻辑大小（按块对齐、预分配），所以后者不封顶，不是笔误。
`reclaimable_actual_known=false` 表示这个卷读不到实占（部分网络盘/FUSE），
此时实占只是逻辑口径的回退值，**不要当成实测结果**。结果页目前只显示逻辑口径，
双数显示属后续版本。

## 9. 使用建议与最佳实践

**操作安全**

1. 首选**回收站**而非永久删除；确认无误后再清空回收站。
2. 重要数据扫描时开启 **paranoid** 模式，用多一趟读盘换零风险。
3. 执行前浏览一遍结果；结果页的"保留建议"是路径最短（优先非隐藏目录）者，不一定符合你的意图，逐组确认或用"保留指定目录"策略。
4. **硬链接合并的前提**：与保留源在同一文件系统（跨设备会失败）；合并后修改任何一个路径的内容会影响所有路径——只对"纯占用、永不再单独修改"的副本使用。
5. **软链接合并的前提**：仅用于**跨卷**场景（同卷请用硬链接）；把**不会移动的磁盘**上的那一份设为保留项，否则链接会失效。删除/移动保留源、拔掉它所在磁盘都会让链接打不开；失效后可从「记录」页回撤，数据不会丢。

**扫描效率**

5. 善用排除路径剪枝 `node_modules`、`.git`、`build`——目录级剪枝能整棵跳过，比逐文件过滤快得多。
6. 用包含扩展名/大小下限缩小候选（如只查 `.mp4`、≥100MB），预筛阶段读盘量按比例下降。
7. **第二次扫描才体现缓存价值**：同根目录反复扫描时，未变化文件直接复用哈希，通常只重算变更部分。缓存命中依旧会重读 4 点采样做安全比对，所以不会为了速度牺牲正确性。
8. 机械盘/网络卷不用手动调参，自动并发已按介质降档；SSD/NVMe 保持默认（核数 − 1）即可。

**缓存维护**

9. 大规模增删文件后（如迁移目录树、路径批量改名），路径是缓存主键——旧路径条目会随 LRU 自然淘汰；想立即回收空间可在设置里清空缓存。
10. 缓存文件损坏无需处理：应用下次启动会把损坏的库**改名隔离**（`cache.db.broken-<时间戳>`）再重建（§4.7），原始影像留在原地可找回。确认无需找回后，可自行删除这些 `.broken-*` 残留。
11. 疑似误报时优先怀疑缓存以外的问题（如文件正在被写入）；缓存侧已有四道命中检查兜底，正常使用无需手动清理。
12. 看到扫描根或"保留指定目录"里闪过一个 `.fdd-case-probe-<数字>` 隐藏文件属正常（大小写语义按卷实测，§3.1），探测结束即删除；只读卷上不会创建它。若因异常退出留下残留，可直接删除。

## 10. 常见问题 FAQ

**Q：为什么 0 字节文件和符号链接不出现？**
内置跳过，防止空文件假组与链接环路，不可关闭。

**Q：我扫 OneDrive / iCloud Drive，结果比文件数少，报告里还出现了一个"云端跳过"的计数？**
那些是**占位文件**：本地只有元数据，内容还在云端。去重要读内容，读它就等于你替自己下一遍
（一个几百 GB 的云盘目录能在几分钟内把流量跑满）。所以默认跳过并**单独计数**：扫描结果
JSON 字段 `skippedCloudFiles`、命令行报告的 `stats.skipped_cloud_files`（§8）。
**界面上目前没有"已跳过 N 个云端占位文件"这条横幅**——新增计数的呈现属 M8（前端体验），
本轮后端交付；现在要看这个数只能看 JSON 或命令行报告（2026-09-21 审查 G2 更正：
本段原先写"单独报『已跳过 N 个云端占位文件』"，那是把计划中的界面文案写成了现状）。
想连它们一起处理：命令行加
`-allow-cloud-hydration`（§8），代价是确实会产生下载流量与耗时。Linux 上的
rclone/gvfs 挂载没有统一占位语义，这一条恒不触发，按普通文件处理。

**Q：报告里的 `skipped_work_temp_files` 是什么？我并没有做过合并啊？**
它是"按名字形态判为**工作临时文件**、因此没参与去重"的文件数：`.fdd-tmp` / `.fdd-old` /
`.fdd-undo-tmp` 这些结尾，以及名字里插着 `.fdd-restored` 的形态（含重名递增的 `_1`），
它们是硬链接/软链接合并与回撤过程中的中间产物（§6.3.1）。合并成功后应用会立刻删掉它们，
删不掉时结果条会以「提示 N」告知——所以这个数不为 0，通常是上次合并的残留还留在盘上
（文件被别的程序占着）。但判据只看名字：你自己命名为 `报告.pdf.fdd-old` 的文件也会被算进
这个数，并且同样不参与去重。两类来源无法区分，删除对应文件即可。

**Q：Windows 上提示「文件含备用数据流，去重会丢失备用流内容」是什么意思？**
那个文件带 **NTFS 备用数据流（ADS）**：除了看得见的正文（默认流），同一个文件名下还挂着
`f.txt:note`、`报告.docx:Zone.Identifier` 这类附属数据块。删除与合并只搬正文，这些流会随之
消失且无处找回，所以应用在动手前把该项整项拒绝（记**失败**，阶段 `ads`），**文件分毫未动**。
这是保护行为，不是故障。想处理只能手工来：先用 `dir /r` 看清流列表、确认内容确实不再需要，
把要留的导出、再用系统工具删流，然后重新扫描。这道检查是**逐文件在动手前**做的，
且只看"有没有命名流"——两个正文相同、备用流不同的文件**仍会被报成重复组**（只是清理被拒）。
非 Windows 平台没有这个语义，这道恒不触发。

**Q：两个文件内容一样但大小不同，为什么没判为重复？**
按内容判定要求大小也一致（这是分桶第一层）。大小不同说明内容必然不同——多半是行尾/编码/元数据差异，FileDedup 不做"近似重复"判定。

**Q：文件被我修改过但 mtime 没变，会不会被误删？**
不会。操作前会重算全量哈希比对内容（§6.4），时间戳不参与放行判断；扫描阶段缓存命中也要求采样指纹一致（§4.3）。

**Q：扫描很慢，第二次会快吗？**
会。缓存命中可跳过全量哈希；只有新增/修改过的文件需要重算。首次扫描全量计算属预期。

**Q：缓存放在哪？能删除吗？**
见 §4.1。可以安全删除，应用会自动重建，仅损失二次扫描加速。

**Q：硬链接的多个路径为什么只显示一个？**
同一物理文件只计一次（阶段 1.5），否则"可释放空间"会是虚数。想为它们节省空间时用"硬链接合并"处理的是**内容相同的不同文件**。

**Q：结果说可释放 8 GB，为什么清完磁盘只少了 300 MB？**
因为界面上的"可释放"按**逻辑大小**计，而磁盘真正减少的是**实占**。两者对不上是正常物理现象，不是漏算：
- **稀疏文件**：一个"8 GiB"的虚拟机磁盘可能只落了 120 MiB，逻辑口径会把收益报成几十倍；
- **压缩卷**（NTFS 压缩）与**预分配**文件同理，方向相反：实占也可能**大于**逻辑大小（按簇/块对齐、预留空间），所以实占口径不封顶。

命令行报告里两个数都给（`reclaimable_bytes` 与 `reclaimable_bytes_actual`，见 §8），
后者就是"清掉真正能腾出多少"。结果页目前只显示逻辑口径，双数显示在后续版本；
历史记录的数字（含旧库恢复）一律是逻辑口径，且恢复时**不显示**实占——库里没存过这个口径，
不拿逻辑值冒充实测。

**Q：为什么我的重复文件里没有「软链接合并」按钮？**
该按钮**只在已加载的重复组中存在跨卷组时才出现**（判定依据是扫描时解析出的真实卷标识，不是盘符字符串）。同卷文件不显示是有意为之：同卷用硬链接是零权限要求、删除任一名字数据都还在的严格更优解，给一个"能用但更差"的选项只会误导。若你确信存在跨卷组而按钮未出现，可能是该组的卷标识未能解析（部分文件系统不提供稳定索引），此时应用选择不显示而不是冒险猜测。

**Q：软链接合并报「需要权限」怎么办？**
Windows 创建符号链接需要 `SeCreateSymbolicLinkPrivilege`。任选其一：① 以管理员身份运行程序；② 在「设置 → 系统 → 开发者选项」开启「开发者模式」；③ 这些文件若在同一磁盘卷内，改用硬链接合并（无任何权限要求）。结果条只会给出一条汇总指引，不会每个文件重复一条。**失败时不会有任何文件被改动**。

**Q：软链接合并后，我删掉了保留文件，链接指向的文件打不开了，数据丢了吗？**
没丢。软链接只是**指向保留源路径的替身**，数据本体一直在保留源那里（或已被你删除）。两种情况分别处置：
- 保留源还在别处（移动/改名了）：把链接删掉、或到「记录」页对该条目点「回撤」恢复独立文件即可；
- 保留源确实被删了：数据已不存在，但**该条目仍可回撤**——合并前的原始备份也在，回撤后你会拿到一份合并前的完整文件。

**Q：怎么知道哪些软链接已经失效了？**
「记录」页 → 展开该笔操作 → 失效条目会整行标红并显示「链接已失效」，悬停可看目标路径与处置建议。应用**不会自动修复**（链接失效源于你的环境变化，自动"修好"可能指向错误的地方）。

**Q：软链接合并后，下次扫描会把它当成重复文件吗？**
不会。扫描器跳过符号链接（避免环路与重复计数，不可关闭），失效链接同样跳过。

**Q：移动操作为什么比其他操作慢？**
移动是唯一串行执行的操作——并发移动会产生目标重名覆盖竞态（静默数据丢失），安全优先于速度。

**Q：取消扫描后刚才算的哈希白算了吗？**
没有。取消路径同样会批量写回缓存（§4.4），下次扫描直接复用。

**Q：回撤成功后，为什么结果页还显示那些文件？**
回撤只动磁盘文件，不反改当前结果集（结果集是扫描时的快照，回撤恢复也可能是另名落地）。看到「回撤完成」提示后重新扫描一次即可刷新。

**Q：为什么有的清理记录标着「不可回撤」？**
两种：永久删除（文件已不在磁盘，无从恢复）；Windows 的回收站操作（系统 API 不返回可靠落点，只能到系统回收站里手动「还原」，界面上有「打开系统回收站」按钮）。

**Q：用「移入回收站」删了文件，回收站里却找不到，文件也没了？**
这正是本应用要防的最坏情况，见 §6.3.3。最可能的原因是**单个文件超过了回收站容量**（默认约为卷容量的 5%）——跨硬盘去重的重复文件往往是大文件，一个就超限。Windows 在无法回收时会**静默永久删除并报告成功**。本应用已加两道防线（事前预检配额 + 事后复核回收站条目数），因此正常情况下你会先看到一条**拒绝执行的明确提示**，而不是文件无声消失。

已经发生了怎么办：**立刻**打开回收站确认（应用结果页有「打开系统回收站」按钮）。在里面就用右键「还原」；不在里面就**停止一切写入操作**，尽快用数据恢复工具抢救——往该磁盘写入新数据会降低恢复成功率。之后跨硬盘处理大文件请改用「移动」，或先调大回收站容量。

**Q：跨硬盘操作回收站时提示「单文件超过该卷回收站容量上限」，怎么办？**
三种处理方式，按推荐顺序：① 改用「移动」到目标目录（不受回收站配额限制）；② 右键回收站 → 属性 → 选中该盘 → 自定义大小，设为大于最大单文件的值后重试；③ 确认这些文件确实不再需要，再用「永久删除」（需二次确认，**不可恢复**）。不建议直接忽略该提示——系统层面对超配额文件的处理就是永久删除。

**Q：提示「文件已从原路径消失，但未能确认其进入回收站」是什么意思？**
这是事后复核发现了不一致：文件不在原位置了，但回收站条目数没有相应增加。可能是文件已被直接删除，也可能是别的原因。请**立即到回收站核实**（§6.3.3），不要假定它在回收站里。应用把它报成失败而不是「跳过」，就是为了避免让你误以为文件安全。

**Q：历史恢复出来的结果安全吗？**
安全。载入历史不碰磁盘，之后每个清理动作仍走 §6.4 的操作前全量内容校验——文件在扫描后被修改过会被拦截、已消失的按跳过处理，不会误操作。

**Q：「处理策略」和「保留策略」有什么区别？**
保留策略决定**留下哪一份**（每组选一个"保留者"，其余为冗余）；处理策略决定**动哪些项**（限定本次操作只处理某几个文件夹里的文件）。两者作用域不同，可以同时使用。冲突时**保留策略优先**——这是结构性保证（保留项在执行层被硬拒绝），不需要你手动取舍。详见 §6.2.1。

**Q：我加了「优先处理的文件夹」，但操作按钮变灰了，为什么？**
说明你勾选的项**没有一个**落在这些文件夹里（交集为空）。按钮灰化是刻意的：宁可让你点不动，也不让你点下去以为做了事。请检查文件夹路径是否写对——若某个文件夹里一个可处理的重复文件都没有，界面会直接点名它。也可以把处理策略切回「全部勾选项」。

**Q：处理策略会改变我的勾选吗？**
不会。它只在**执行时**做过滤（`勾选项 ∩ 优先文件夹内的文件`），勾选框状态原样不动。「全选」仍然选中全部冗余项，不受处理策略影响。

**Q：优先文件夹列表为什么切到别的页面就没了？**
它是"仅本次结果集"的设置，刻意**不写入配置文件**——它描述的是"这批结果想怎么处理"，换一批结果就失去意义。切换结果集、打开历史记录或重新扫描都会清空它。

**Q：清理时报「清理账本不可用，已拒绝执行」怎么办？**
回收站/移动/硬链接/软链接这类**承诺可回撤**的操作，账本写不进就一律拒绝（§6.7）。先重启应用让 `history.db` 自愈（损坏时会被改名隔离后重建），再重试；不要因为"急着清理"改用永久删除——那正是唯一还放行的路径，且不可恢复。

**Q：想让界面变成英文？**
目前只有中文文案。设置里可以选 `English（M5）` 并保存，但界面文案尚未接入 i18n，选择后仍显示中文（§7「语言项现状」）。

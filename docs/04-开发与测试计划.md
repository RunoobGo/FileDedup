## 2. 实现面现状（代码事实）

### 2.1 模块构成

| 层 | 内容 |
|---|---|
| Go 引擎（`internal/`，12 包） | `scanner` `filter` `hasher` `dedup`（流水线 + 状态机 + gate）`cache` `history` `ops` `fsid` `fscase` `dbfile` `media` `progress` `model` |
| 应用层 | `app.go`（Wails 绑定 + 状态机 + 视图装配）、`main.go`（窗口与 `go:embed frontend/dist`） |
| CLI | `cmd/fdd-cli`（JSON 报告冒烟）、`cmd/benchgen`（数据集 A/B/C 合成 + manifest） |
| 前端 | Vue 3 + Pinia + Vite 5；`views/`（Scan / Result / Records / Settings）+ `components/`（GroupCard / PreviewPanel / FailedDrawer / Logo 等）+ `stores/scan.ts` |

引擎层不 import Wails，可脱离 GUI 单测与基准。

### 2.2 数据面（3 个落盘文件）

| 文件 | 位置 | 内容 | 损坏处置 |
|---|---|---|---|
| `cache.db` | `os.UserConfigDir()/FileDedup/` | `hash_cache`（v3：path 主键 + size/mtime + `dev/ino/ctime_ns` + partial/full + `last_hit`）、`cache_meta`（`AlgoVersion`）；WAL | 判定为损坏 → 写标记 + 改名隔离（`.broken-<ts>`，含 -wal/-shm），下次以空库启动；**瞬时故障（锁/繁忙）不隔离** |
| `history.db` | 同上 | `scan_history` + `hist_groups` + `hist_files`（扫描快照）、`op_records` + `op_items`（写前账本） | 同上；**账本不可用时，可回撤类型（回收站/移动/硬链接）的清理操作被拒绝**，永久删除不受影响 |
| `settings.json` | 同上 | 线程数、主题、语言（**无消费者**）、paranoid 等；后端单一事实源 | 读失败退默认值 |

`AlgoVersion` 与建表语句不一致即整表作废（`DROP TABLE`）——升级哈希口径时改常量即可，不做迁移。

### 2.3 契约面

- **绑定方法 31 个**（`grep -c '^func (a \*App) [A-Z]' app.go` = `frontend/wailsjs/go/main/App.d.ts` 的 `export function` 数，两侧一致）；`main.go` 用 `Bind: []interface{}{app}` 反射绑定**全部**导出方法，因此 01 §3.2 的封闭清单不构成契约；
- **事件通道 10 个**：`app:ready`、`scan:progress`、`scan:stage`、`scan:done`、`scan:cancelled`、`scan:error`、`ops:progress`、`ops:done`、`ops:error`、`ops:undo:done`；
- 返回值字段名以 Go struct 的 `json` tag 为准（Wails 用 `json.Marshal`），前端 TS 类型须逐字对齐；
- **无自动契约校验**：TS ↔ `json` tag 漂移目前只能靠 `vue-tsc` 在调用点报错 + 人工比对（§6 B 组）。

### 3.7 性能基准（L6）现状

- 数据集：`benchgen -dataset A|B|C -scale <f>` 可复现（固定种子 + manifest）；
- **无 CI 门禁**：`go test -bench` 不进任何工作流，`-bench` 也不在 `smoke-cli.sh` 内；
- **红线未落地**：V1.2 §3.7「数据集 C 总耗时劣化 >10% 需附说明」从未成为机制；
- **01 §5.3 / 03 §5.2 的指标从未回填**：首扫 ≤30s、二扫 ≤5s、RSS ≤300MB、吞吐 ≥1.5GB/s 四项均无对应实测记录（M4 当时只验了"二扫 ≥10x"这一相对量，实测 21.4x）；
- 结论：**性能类改动目前只能靠 `smoke-cli.sh` 保证结果不变，不能保证速度不退**。这是当前最大的验收空洞（§6 B 组）。

### 3.8 UI 验收（人工）

核心旅程：拖入目录 → 配过滤器 → 扫描（观察阶段/暂停/恢复/取消）→ 应用"最短路径"保留 → 预览抽查 → 移入回收站 → 清理记录里回撤 → 系统回收站核对。附加：主题切换、放量闸「继续加载」、失败清单入口、关窗两段式拦截。

自动化限制（已知）：macOS 上以窗口自动化驱动 Wails 应用时，键盘事件不投递给 webview、`NSOpenPanel` 的无障碍树不稳定、瞬时操作无法观察——因此 §3.5 的 M 项靠"改脚本 + 读账本"取证，而非靠界面断言。

### 3.9 缺陷管理

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 误删 / 数据损坏 / 崩溃 | 立即修复，阻塞发布 |
| P1 | 主流程功能失效 | 当前迭代内修复 |
| P2 | 体验问题（卡顿 / 文案） | 排期修复 |
| P3 | 瑕疵 | backlog |

审查轮的编号实践（近三轮）：`D*`（M1~M4 开发期）→ `R*/Y*/C*`（09-16）→ `R*/C*/Y*` 第二轮（09-17）→ `C*`（严重）/ `I*`（重要）/ `B3-*`（第 3 批工程门禁）（09-18/19）。三态记法：**已修 + 回归测试**／**未实施（无热点证据，留待重估）**／**已否决（附实测依据）**。修复必须配一个"在修复前必然失败"的探针测试，且回归判据是"探针红过、修后绿"。

## 4. CI/CD 现状

### 4.1 `ci.yml`（PR 与 main push，阻断）

`check` job（ubuntu）按序：

1. gofmt 检查（必须无输出）
2. `scripts/check-version-sync.sh`（5 处版本号声明位互相对齐）
3. 前端类型检查 `npm ci && npm run typecheck`（`vue-tsc --noEmit`；同时是 `npm run build` 的 prebuild）
4. 前端构建 `npm run build`（**必须先于 Go 步骤**：`go:embed frontend/dist`）
5. `go vet` ×3：本机 linux / `GOOS=windows` / `GOOS=darwin`
6. `go test -race -count=2 ./...`
7. `go test -race -count=4 .`（根包多压两轮，覆盖 App 层状态机时序）
8. `bash scripts/smoke-cli.sh`（C×0.02 三跑一致 + manifest 对账）

`windows` job（windows-latest）：`bash scripts/test-windows-quarantine.sh` —— **白名单式隔离**，清单内 5 条暂不执行且逐条注明症状与未定性原因，**清单外任何失败一律阻断**（原先整个 Windows job 是 `continue-on-error: true`，等于该平台不设防）。该腿跑 `-count=1` 且**无 `-race`**。

### 4.2 `build.yml`（`v*` tag 或手动触发）

- 首步：tag 必须等于 `AppVersion`，否则发布构建立即失败（历史上出现过 `v1.0.0` 发布物对应 0.5.0 产品的错位）；
- 矩阵：linux-amd64 / windows-amd64 / macos-arm64 / macos-amd64，`wails@v2.16.0` CLI（与 go.mod 锁定的库版本一致，防 CLI 静默改写依赖）；
- Windows 腿改用与 `ci.yml` 同一份白名单门禁；linux 腿加跑 CLI 冒烟；
- release job 生成 **`SHA256SUMS.txt`** 随产物发布。

### 4.3 仍未纳入 CI

eslint / vitest（前端未配工具链）、契约 diff 校验（TS ↔ `json` tag）、nightly 基准归档、二进制体积门禁、macOS 真实回收站与 GUI 端到端（人工）。

### 4.4 版本号口径（2026-09-19 已决）

首次按新门禁发布时暴露：`v1.0.0`（2026-09-17）对应的产品版本其实是 **0.4.0**——1.0.x 标签
序列与 0.x 版本序列从第一天起就错位，而它当初能发出去只是因为那时这道门禁还不存在。
用户裁定（2026-09-19）：**回到 0.x 线，标签名逐字等于版本号**，据此打 `v0.5.0`；
不追溯改历史 tag/release。因此"发一个 v1.0.1"在工程上不再可选——除非同步把 5 处声明位
升到 1.0.1（`check-version-sync.sh` 会拦，见 §3.3）。这是发布决策，此后每次打标签前仍需用户明确版本号。

### C 组 — 本轮审查发现、尚未修

1. **`fscase` 单根探测缺口（数据正确性）**：按卷大小写探测只在 **≥2 个根**时执行（`internal/scanner/scanner.go:300-320` 单根直接返回 `fscase.Default()`，注释理由"单根无从判重"），但 `folder.fold` 同时把关 `visited` 子目录去重（`scanner.go:224-233`）。后果：单根扫描在**大小写敏感**卷（macOS 区分大小写卷、Linux 挂载的 case-sensitive 卷）上可能因平台默认值（darwin=不敏感）折叠掉一个子树而**静默漏扫**；在 **casefold/CIFS** 卷上可能把同一目录收两遍，**虚增重复组与可释放空间**。最小修法：无条件对每个根探测。未修原因：需真机/特定挂载验证，且改动会影响所有扫描的启动路径——待用户确认优先级；
2. **`language` 字段无消费者**：设置可存但界面不随之变化（与 A 组 3 同批决策）；
3. **报告导出**（M5-T01）为空桩，且 09 手册已如实标注"未交付"——UI 里不留入口，属有意状态，但计划项仍未闭环；
4. **Windows 缓存身份少一层（2026-09-19 CI 实测）**：GitHub windows runner 上文件的 change time 恒为 0——`GetFileInformationByHandleEx(FileBasicInfo)` 不给这一项（它记在父目录索引项里，卷可以不维护），属平台行为而非解析失败：身份 `(卷号, 文件索引)` 仍然成立。后果：缓存命中的第 ① 层（ctime 须一致）在 Windows 上不提供区分力，"原地改写内容 + 拨回 mtime"只剩第 ② 层四点采样兜底，**采样四点未覆盖的区间内改动仍可能沿用旧哈希**。用例已改为 best-effort 断言并在日志留证（`internal/fsid/fsid_windows_test.go`）；真机上是否普遍为 0、以及是否需要把第 ② 层的采样点加密度，待 §3.5 的 Windows 真机一轮一起结论。

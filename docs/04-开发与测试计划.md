## 2. 实现面现状（代码事实）

### 2.1 模块构成

| 层 | 内容 |
|---|---|
| Go 引擎（`internal/`，14 包） | `scanner` `filter` `hasher` `dedup`（流水线 + 状态机 + gate）`cache` `history` `ops` `fsid` `fscase` `dbfile` `media` `progress` `model` `worktemp`（工作临时文件识别与残留治理） |
| 应用层 | `app.go`（Wails 绑定 + 状态机 + 视图装配）、`main.go`（窗口与 `go:embed frontend/dist`） |
| CLI | `cmd/fdd-cli`（JSON 报告冒烟）、`cmd/benchgen`（数据集 A/B/C 合成 + manifest） |
| 前端 | Vue 3 + Pinia + Vite 5；`views/`（Scan / Result / Records / Settings）+ `components/`（GroupCard / PreviewPanel / FailedDrawer / Logo 等）+ `stores/scan.ts` |

引擎层不 import Wails，可脱离 GUI 单测与基准。

### 2.2 数据面（3 个落盘文件）

| 文件 | 位置 | 内容 | 损坏处置 |
|---|---|---|---|
| `cache.db` | `os.UserConfigDir()/FileDedup/` | `hash_cache`（v3：path 主键 + size/mtime + `dev/ino/ctime_ns` + partial/full + `last_hit`）、`cache_meta`（`AlgoVersion`）；WAL | 判定为损坏 → 写标记 + 改名隔离（`.broken-<ts>`，含 -wal/-shm），下次以空库启动；**瞬时故障（锁/繁忙）不隔离** |
| `history.db` | 同上 | `scan_history` + `hist_groups` + `hist_files`（扫描快照）、`op_records` + `op_items`（写前账本） | 同上；**账本不可用时，可回撤类型（回收站/移动/硬链接）的清理操作被拒绝**，永久删除不受影响 |
| `settings.json` | 同上 | `Settings`（`app.go:138-143`）四个字段：线程数、**默认过滤器** `filtersDefault`、主题、语言（**无消费者**，仅存回磁盘） | 读失败退默认值；**字段类型错**不半吞半成品而是回默认并留痕（M10） |

> **paranoid 不在 `settings.json`**（2026-09-21 实测更正）：它是**每次扫描的入参**
> （`model.ScanConfig.Paranoid`，`app.go` 的 `StartScan` 透传），持久化位置是
> `history.db` 的 `scan_history.paranoid` 列（用于「恢复上次扫描配置」），
> 前端把它放在 store 里而**不落设置页**。原表述"线程数、主题、语言、paranoid 等"
> 会让人去 `Settings` 里找它而找不到。

`AlgoVersion` 与建表语句不一致即整表作废（`DROP TABLE`）——升级哈希口径时改常量即可，不做迁移。

### 2.3 契约面

- **绑定方法 34 个**（`grep -c '^func (a \*App) [A-Z]' app.go`；2026-09-21 重数，较上一版 +2 = `FilterInDirs`（AS-H6/D-1，路径判据收回后端）与 `GetStartupNotice`（M12，启动期隔离提示改拉取）；构建时由 Wails CLI 生成 `frontend/wailsjs/go/main/App.d.ts`，该目录已 gitignore，故两侧一致性由 CI 的 `npm run build` 隐式保证而非源码内可见）；`main.go` 用 `Bind: []interface{}{app}` 反射绑定**全部**导出方法，因此 01 §3.2 的封闭清单不构成契约；
- **事件通道 13 个**（`grep -rho 'emit([^,)]*, *"[^"]*"' --include="*.go" . | grep -o '"[^"]*"' | sort -u`）：`app:ready`、`app:error`、`app:quit-blocked`、`scan:progress`、`scan:stage`、`scan:done`、`scan:cancelled`、`scan:error`、`ops:progress`、`ops:filtered`（处理策略过滤反馈，本轮新增）、`ops:done`、`ops:error`、`ops:undo:done`；
- 返回值字段名以 Go struct 的 `json` tag 为准（Wails 用 `json.Marshal`），前端 TS 类型须逐字对齐；
- **无自动契约校验**：TS ↔ `json` tag 漂移目前只能靠 `vue-tsc` 在调用点报错 + 人工比对（§6 B 组）。

## 6.6 本轮新增：空记录页空白修复 + 处理策略（2026-09-20）

### 6.6.1 缺陷：无清理记录时记录页整页空白

**症状**：清理记录为空（或扫描历史为空）时，点进记录页看到**完整空白**——没有题头、
没有标签栏，也没有"暂无清理记录"的提示。

**根因（已用实证钉死，不是推测）**：Go 的 **nil slice 序列化成 JSON 是 `null`，不是 `[]`**。

```go
var out []OpMeta            // 空表时保持 nil
json.Marshal(out)           // → "null"    （而 []OpMeta{} → "[]"）
```

前端拿到 `null` 后执行 `opList.length` → **`TypeError`** → Vue 的组件渲染函数**整体中断**，
于是页头、标签、空态提示**全都没渲染**。

> **关键澄清**：空态提示的模板（`RecordsView.vue` 的空态分支）**一直都在**，
> 它只是**永远没能被执行到**。所以这个缺陷不是"漏写了空态"，而是"渲染提前抛错"。
> 排查时若只盯着模板找"缺的那段文案"，会一直找不到——**要先看有没有渲染，再看渲染了什么**。

**修法（两侧同时收紧，缺一不可）**：

| 侧 | 改动 | 理由 |
|---|---|---|
| 后端 | `internal/history/oplog.go`（`ListOps` / `GetOp`）、`scan.go`（`ListScans`）、`app.go`（`keepPathsLocked`）改用 `make([]T, 0, n)` | 空列表的正确形状是 `[]`。数据形状由生产方保证，不该让每个消费方各自防御 |
| 前端 | `stores/scan.ts` 三处赋值加 `?? []` | 兜底：即使后端将来又漏了，界面降级成"空列表"而不是整页白屏 |

**顺带发现并一并修掉的 3 处同类隐患**（用户未报告，属主动排查）：`GetOp` 的空明细会让
**记录详情展开**后同样整块白屏；`ListScans` 会让**扫描历史标签页**在无历史时白屏；
`keepPathsLocked` 语义上就是"路径列表"，返回 nil 徒增调用方判空负担。

**回归测试**：`internal/history/emptyslice_test.go`（新增，4 条）。与其他测试只断言
`!= nil` 不同，这里断言的是**JSON 契约本身**——把结构体序列化后要求结果**逐字等于 `"[]"`**：

```go
func marshalIsEmptyArray(t *testing.T, name string, v any) {
	b, _ := json.Marshal(v)
	if got := string(b); got != "[]" { t.Fatalf(...) }
}
```

只查 `!= nil` 是查不出问题的：`nil` 与 `[]T{}` 在 `!= nil` 口径下都能过，
但它们在**跨语言边界上**是完全不同的两样东西。**变异验证**：把 `make(...)` 退回
`var out []OpMeta`，测试立刻失败并打印 `…的空列表应为 JSON "[]"…实得 null`。

### 6.6.2 需求：处理策略（保留策略之上）

**需求原文**：*"目前仅有保留策略，在此基础上增加处理策略，选择优先执行指定文件夹的移动、删除等重复文件操作。保留策略与处理策略冲突时，优先执行满足保留策略。"*

**用户裁定的三条设计边界**：

| # | 决策 | 含义 |
|---|---|---|
| 1 | **只作为执行时的过滤器** | 不改变用户的勾选。显式勾选是用户的明确表达，策略设置不该悄悄改写它 |
| 2 | **仅本次结果集** | 不写入 `settings.json`；结果集变化即清空（与 `keepDirs` 同生命周期） |
| 3 | **未命中时明确提示并指出原因** | 沿既有 `unmatched` 机制，回显用户**输入的原文** |

**★ 关键结论：「保留策略优先」不需要新写裁决逻辑，它是结构性的。**

这一点是整个设计的地基，值得写清楚推导链：

1. **待操作集合完全由前端决定**——`stores/scan.ts` 取 `selectedFiles.map(f => f.id)`
   放进 `OpRequest.FileIDs`，后端**不推导**它；
2. **`keepIDs` 是纯拒绝名单**——`executor.go` 对保留项硬拒绝（`保留文件不可操作`），
   它只做**减法**，从不往集合里**加**任何东西；
3. 处理策略做的事是 `FileIDs ∩ 优先文件夹`，即**在勾选集合内部再做一次减法**；
4. 两次都是减法 → **处理策略无论如何都不可能让保留项被动**。

所以"冲突时保留策略优先"不是"两个策略比大小"，而是**能力边界**：处理策略连
"动保留项"这个能力都不具备。**没有裁决逻辑，就没有裁决逻辑写错的可能。**

> **变异的实证**：把 `app.go` 里传给执行器的 `KeepIDs` 改成 `nil`（移除硬拒绝），
> `TestProcessPolicyNeverOverridesKeepPolicy` 立刻失败（保留者被删）。
> 也就是说这条保证**被测试真实钉住了**，不是注释里的承诺。

### 6.6.3 缺陷：跨硬盘「移入回收站」后文件被静默永久删除（2026-09-20）

**缺陷原文**：*"扫描出跨硬盘重复文件，操作移动到回收站后，文件已移走，但回收站无文件，疑似被直接删除。"*

**这是数据丢失级缺陷**，也是本项目迄今最严重的一条——其余缺陷是"操作没生效"或"界面不对"，
这一条是**文件真的没了**。

**根因（已用多方证据确认）**：Windows 的 `SHFileOperationW` + `FOF_ALLOWUNDO` 是
**尽力而为（best-effort）而非保证**。当文件**无法**进入回收站时，Shell 的行为是：

> **永久删除该文件，然后返回 0（成功）。**

MSDN 对此**只字未提**——文档只说 *"Setting that flag sends the file to the Recycle Bin"*，
仿佛必然成功。该降级行为由实测与社区一致确认
（[SO: Send File to RecyleBin, big file get permanent delete](https://stackoverflow.com/questions/21406508/send-file-to-recylebin-big-file-get-permanent-delete)，
另有 [MSDN Magazine 2001/04](https://learn.microsoft.com/en-us/archive/msdn-magazine/2001/april/c-q-a-why-returns-a-reference-accessing-the-recycle-bin-when-to-use-stl) 确认 `FOF_ALLOWUNDO` 的"神秘"性质）。

于是原实现在 `r0 == 0` 时把**每一项**记为"成功移入回收站"，而文件其实已从磁盘彻底消失、
回收站里什么都没有。用户看到的就是"文件已移走，回收站无文件"。

**为什么原有的三道防线都没拦住**：

| 防线 | 覆盖范围 | 为何无效 |
|---|---|---|
| `unsafeDriveReason` 卷类型预检 | 网络盘 / 可移动盘 / 光碟 / RAM 盘 | **固定盘（`DRIVE_FIXED`）返回 `""` 放行**——跨硬盘场景两个盘都是固定盘，直接通过 |
| `buildPathList` 双 NUL 修正 | 路径列表解析 | 只解决"只处理第 1 个"，与"是否真进回收站"无关 |
| 执行器 `r0 == 0` 判成功 | 返回值 | **`r0 == 0` 恰恰是缺陷本身**——静默删除时它照样返回 0 |

代码注释里其实**早已承认**这个残余风险（`trash_windows.go` 原文）：
"固定盘单文件超过回收站配额时 Shell 也可能直接删除，配额可编程查询的接口冗杂
（IQueryRBInfo/SEP2），暂以文档提示兜底。" —— "以文档兜底"意味着**代码层完全没有防护**。

**触发条件**（按本应用用户的实际情况排序）：

| # | 条件 | 说明 |
|---|---|---|
| 1 | **单文件超出回收站配额**（最可能） | 回收站默认上限约为卷容量的 **5%**。跨硬盘去重的重复文件往往是几十 GB 的镜像/视频/安装包，**一个就超过整个回收站容量** |
| 2 | 回收站被策略禁用 | 注册表 `NukeOnDelete=1` 时所有删除都不进回收站 |
| 3 | 该卷 `$Recycle.Bin` 不可用 | 被安全软件（如本机安装的北信源防病毒）接管/清理、权限异常 |
| 4 | 提权进程的 SID 差异 | 以管理员运行时回收站归属不同 SID，表观上"回收站里没有" |

**修复：两道防线（`trash_windows.go` + `recycle_policy.go`）**

| 道 | 时机 | 内容 |
|---|---|---|
| 一 | 事前 | `recyclableReason` 逐文件预检：卷类型 → 回收站策略（`NukeOnDelete`）→ **单文件 vs 该卷回收站配额**（`SHQueryRecycleBinW` + 注册表 `MaxCapacity`，卷 GUID 经 `GetVolumeNameForVolumeMountPointW` 解析）。任一不满足即**整批拒绝**并说清原因 |
| 二 | 事后 | `verifyRecycled`：`SHFileOperation` 返回 0 后，独立复核**源路径确实消失**且**该卷回收站条目数真的增加**。验不过即报错 |

同时补 `fofNoErrorUI`（0x400）：不设它，Shell 会弹「文件太大，无法放入回收站，是否永久删除？」——
用户点「是」就变成永久删除，而本应用承诺的是"移入回收站"。我们自行判定并报错，不把这个
选择权交给一个措辞具有误导性的系统弹窗。

**★ 设计要点：把纯逻辑下沉，让防线进入 Linux CI 的可测范围**

`trash_windows.go` 带 `//go:build windows`，其测试**只能在 Windows 上跑**。本项目上一轮的
教训正是"只写在 Windows 文件里的防线从来没被任何自动化测试执行过"（`unsafeDriveReason`
的盘根缺陷就是这样溜过去的）。因此本次把可判定的部分抽到 **`recycle_policy.go`（无 build tag）**：

- `checkRecycled(stillExists, before, after)` —— 事后复核的**判定**（平台无关纯函数）
- `capacityReason(fileSize, capBytes)` —— 配额判定（平台无关纯函数）
- `humanSize` / `sortedKeys`

`trash_windows.go` 只负责**采集平台数据**（哪些源还在、各卷条目数）再委托给它们。
这样核心防线在 **Linux CI 主门禁**里就会被执行。

**★ 修复过程中发现的次级隐患（差点把警报重新按下去）**

执行器的批量失败回退（C6）里有一条旧推断："源已不在 → 记 `Skipped`（目标已达成）"。
在静默永久删除的场景下这**会变成帮凶**：`verifyRecycled` 刚检出问题并返回错误，
回退逻辑随即看到 `os.IsNotExist(p)` 成立，就把该项记成 `Skipped`——
**刚亮起的数据丢失警报被重新按了回去**，用户看到的仍是一个无害的「跳过」。

判据缺陷在于：`os.Stat` 只能证明"文件不在了"，**无法区分"进了回收站"与"被永久删除"**。
故引入 `Options.TrashVerifiesRecycle` 声明平台能力，把契约分成两支：

| 平台能力 | "源消失 + 无落点"的处置 | 理由 |
|---|---|---|
| **能验证**（Windows，`true`） | 记 **Failed** 并给出核实指引 | 平台承诺"没报告落点就不算成功"，此形状即数据丢失 |
| 不能验证（darwin 等，`false`，**默认**） | 维持 C6/S8 记 `Skipped` | darwin 的 Finder 落点解析可能配对失败返回空 dstMap，此时文件**确实**已进回收站，记 Failed 属误报 |

**回归测试**

| 文件 | 条数 | 说明 |
|---|---|---|
| `internal/ops/recycle_policy_test.go` | 15 用例 | **平台无关，Linux CI 执行**。核心是 `TestCheckRecycledSilentPermanentDelete`。（上一版记 20——把后加的 AS-R4 等同类用例一并算进本文件却没同步重数，2026-09-21 `grep -c '^func Test'` 实测 15） |
| `internal/ops/executor_panic_test.go` | 4 用例（其中 1 项属 H6） | `TestTrashFallbackStrictFailsUnverifiedGone` —— **端到端**断言最终状态码为 Failed |
| `internal/ops/trash_windows_recycle_test.go` | 12 用例 | Windows 专属（卷 GUID、`SHQueryRecycleBinW` 布局、快照、`driveRoot`、按卷 `NukeOnDelete` 三态） |

**★ 四重变异验证（证明测试是真门禁，不是装饰）**

| 变异 | 预期失败 | 实测 |
|---|---|---|
| 删除判据 2（只看源是否消失，即缺陷版逻辑） | 三个静默删除用例 | ✅ 全部失败 |
| `>` 写成 `>=`（恰好等于上限变成拒绝） | "恰好等于上限_放行" | ✅ 失败 |
| `capBytes<=0` 改为拒绝（误拒正常用户） | 两条"上限未知_放行" | ✅ 失败 |
| `sortedKeys` 不排序（map 顺序漂移） | 两条稳定性用例 | ✅ 失败（`F:\` 抢在 `D:\` 前） |

**新增开放项**：

- **E 组补：回收站复核的真机验证未执行**。需在 Windows 真机确认：① 正常大小时回收站
  操作成功且文件确实出现在回收站；② 把某盘回收站配额设为极小（如 1 MB）后对一个更大
  文件执行「移入回收站」→ 应看到**明确的拒绝提示**（含容量对比数字），而非文件消失；
  ③ 同上场景勾选多个文件（部分超限）→ **整批拒绝**，一个都不删；④ 用
  `NukeOnDelete=1` 模拟策略禁用 → 应拒绝并指名策略原因。
  **注**：`SHQueryRecycleBinW` 的结构体布局（`Pack=4`，`cbSize=20`）已在
  `TestQueryRecycleBinSystemDrive` 中静态断言，但真实返回值语义需真机确认。
- **F 组补：回收站配额预检在"事后复核不可用的环境"下退化为放行**。若 `SHQueryRecycleBinW`
  调用失败（老系统/沙箱/被安全软件拦截），判据 2 自动跳过，仅剩判据 1（源必须消失）。
  此时"源消失但被永久删除"**无法被检出**。这是刻意的保守取舍（宁可漏判也不误拒），
  但构成一处真实的保护缺口，需在文档（`docs/09` §6.3.3）向用户说明。

**处置：补齐元素，让提交信息事后成真（而非改写历史）**

依据 [MSDN 最大路径长度限制](https://learn.microsoft.com/zh-cn/windows/win32/fileio/maximum-file-path-limitation)：

> 要为每个应用程序启用新的长路径行为，必须满足两个条件。**必须设置注册表值，应用程序清单
> 必须包含 `longPathAware` 元素。**
> ```
> <application xmlns="urn:schemas-microsoft-com:asm.v3">
>   <windowsSettings xmlns:ws2="http://schemas.microsoft.com/SMI/2016/WindowsSettings">
>     <ws2:longPathAware>true</ws2:longPathAware>
>   </windowsSettings>
> </application>
> ```

即 `longPathAware` 是长路径支持的**必要前提之一**（另一个是注册表）。原 manifest 已有
`<asmv3:application><asmv3:windowsSettings>` 块，故按官方写法在其内追加一行即可。已完成：

```xml
<ws2:longPathAware xmlns:ws2="http://schemas.microsoft.com/SMI/2016/WindowsSettings">true</ws2:longPathAware>
```

声明后以下本产品用到的 API 不再受 MAX_PATH 限制：`CreateFileW`、`DeleteFileW`、`MoveFileW`、
`GetFileAttributesW`、`CreateHardLinkW`、`CreateSymbolicLinkW`、`FindFirstFileW`、`File` 系列等。

**两点必须同时说清，否则用户会误以为"声明了就一定行"**：

| # | 前提 | 说明 |
|---|---|---|
| 1 | **注册表 `LongPathsEnabled=1`** | `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled`（DWORD=1）。**只声明元素不设注册表仍然按 MAX_PATH 截断**——这是本项最大的误解来源 |
| 2 | 该值**每进程首次调用受影响的 API 后缓存**，进程生命周期内不再重读 | 改注册表后**需重启**才对所有已启动进程生效 |

因此 §3.5 #4 的状态是：**元素已交付，但整条链路仍标注"真机未复测"**——因为：
① 未在 Windows 真机上用 >260 字符的路径跑过一次扫描→去重→删除；
② 也未确认目标环境（本机 Win11 + 北信源）的 `LongPathsEnabled` 取值。

**另注**：本产品还有一个 **`SHFileOperationW` 不受 `longPathAware` 保护**的边界——
Shell 的 `SHFileOperationW` 不在"opt-in 后解除 MAX_PATH"的 API 清单里，且代码明确不用 `\\?\`
前缀（`trash_windows.go:255` 有注释说明 SHFileOperation 不支持该前缀）。所以即使长路径全面开启，
**回收站路径**（跨盘移入回收站）在超长路径上仍可能失败——但本轮的回收站防线（§6.6.3）会把它
报成显式失败而非静默删除，不会造成数据丢失。这是一处**已知且被防线兜住**的边界。

> **教训（供下轮审查复用）**：`git log` 的提交信息**不是证据**，只有 `git show` 的 diff 才是。
> 本条差异是靠"把文档断言与文件内容对账"发现的，如果只信提交信息，就会得到"T04 已交付"的错误结论。

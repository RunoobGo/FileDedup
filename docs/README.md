# docs 索引 · 该读哪一份

本目录分**三层**，性质不同、维护规则不同。找错层会得到过期结论，所以先选层再读。

## 一、按目的选文档

| 你想确认的事 | 读这一份 | 备注 |
|---|---|---|
| 这个软件能做什么、参数含义、安全性边界、已知限制 | `09-用户手册.md` | **功能口径唯一真源**，与代码同步维护 |
| 工程现状：哪些交付了、哪些门禁真的拦得住、还有什么没做 | `04-开发与测试计划.md`（V2.0 现状版） | §6 开放项是**唯一权威待办清单** |
| 当初为什么这么设计、备选方案与否决理由 | `01` / `02` / `03` | 冻结档案，**先读页首勘误表再读正文** |
| 某次代码审查发现了什么、怎么修的、留了什么回归测试 | `archive/代码审查与修复编年史.md` | 只增不改 |
| 界面/品牌怎么演进到今天 | `archive/UI-视觉与品牌编年史.md` | 截图证据 `archive/ui-review-2026-09-16/` |
| 某个里程碑当时交付了什么 | `archive/里程碑开发与测试报告.md` | 当时的验收记录，此后不回填 |
| `M{n}-T{nn}` 任务号出自哪份计划 | `archive/04-计划原文-V1.2-2026-09-17快照.md` | 04 的 V1.2 逐字原文 |
| 0.5.0 那批功能的设计与实施细节 | `superpowers/specs/`、`superpowers/plans/` | 带页首偏差说明，勿据此实现新功能 |

## 二、三层结构与维护规则

### 活文档（内容随实现更新）

- `09-用户手册.md` — 面向使用者。**版本号声明位之一**（`scripts/check-version-sync.sh` 校验
  「适用版本：」，共 5 处声明位必须对齐）。
- `04-开发与测试计划.md` — 面向工程。**V2.0 起是现状与质量门禁文档，不再是计划**：
  §1 交付总览、§2 实现面现状、§3 测试体系、§4 CI 现状、§5 门禁约束力、§6 开放项、附录 A 发布清单。
  文件名与 §3.5/§3.6/§4/附录 A 的编号保持不变，因为它们被 `README.md`（§3.5、附录 A）、
  01 §12.1（§3.6）、`internal/ops/ops_test.go:3`（§3.6）、`ci.yml:1`（§4）按号引用。

> 任何"现在的行为是什么"的结论只写进这两份。写进第三份（下面的冻结档案）就是制造第二个事实源。

### 冻结档案（正文不改，只往页首勘误表加行）

- `01-项目设计文档.md`（V1.4，2026-09-17 定稿）
- `02-设计思路文档.md`（V1.2，2026-09-15）
- `03-算法选择与研究.md`（V1.2，2026-09-15）

三份各有一份**日期化勘误表**在页首，列出已核对的实现偏差（含"结论被反转"级别的分歧）。
维护规则：发现新偏差 → 勘误表加一行（带日期 + 代码锚点），**不编辑正文、不删旧行**。
勘误表自身声明「此表未穷尽」——它不是完备 diff，读到与代码不符处应当场补行，而非默认无记载即正确。

### 编年史档案（`archive/`，只增不改）

- `代码审查与修复编年史.md` — 5 篇：2026-09-16 全量审查 / 缺陷修复 / 优化项+G1–G12 台账 /
  2026-09-17 全面审查 / 2026-09-18–19 数据安全与工程门禁。
- `UI-视觉与品牌编年史.md` — 3 篇：设计系统审核 / 修复与验证 / Logo 重设计。
- `里程碑开发与测试报告.md` — 4 篇：M1 / M2 / M3 / M4。
- `04-计划原文-V1.2-2026-09-17快照.md` — 计划原文。
- `ui-review-2026-09-16/` — 46 个截图与放大证据文件（随第 1 篇从 `docs/` 根目录迁入）。

合并规则（2026-09-19 起）：**一次性的日期化报告不再留在 `docs/` 根**，直接以「第 N 篇」并入对应
编年史（或另起一份编年史），截图证据用同名目录随迁。正文**逐字保留**，只允许两种改动：
① 篇首加「现状标注」；② 把指向已删除文件的**可点击链接**改写为「第 N 篇」文字。

> 因此编年史正文里仍会出现 `docs/code-review-2026-09-16.md`、`docs/05-M1开发与测试报告.md`
> 之类已删除的文件名。那是历史原文，指向本篇对应篇，**不是断链，不要去"修"**。
> 每篇开头的 `> 原文：…（源文件已删除，正文完整并入本篇）` 即该映射的权威说明。

## 四、给改文档的人

1. 改功能 → 同步 `09`（必需，`check-version-sync.sh` 会查版本号）+ `04`（若影响交付状态/门禁/开放项）。
2. 在 `01`–`03` 读到与代码不符 → 页首勘误表补一行，别改正文。
3. 写了一份日期化审查/审核报告 → 归档前直接并入 `archive/` 对应编年史，不要在 `docs/` 根留下第 12 份散档。
4. `docs/superpowers/` 是 superpowers 工作流产物（计划 + 设计成对），保留原位仅供追溯，
   顶部已标注它与现行实现的偏差；新工作可以直接看 `04` §6。

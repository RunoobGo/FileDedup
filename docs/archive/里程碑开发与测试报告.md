### 3. 开发过程缺陷与修改记录（重要）

以下为开发-测试循环中发现并修复的问题，含 2 个**引擎真实缺陷**、3 个**测试设计缺陷**、2 个**工具链问题**：

#### D1（严重·引擎）：scanner v1 —— send on closed channel panic

- **现象**：`go test -race` 中 `panic: send on closed channel`
- **根因**：worker 处理目录时动态投递子目录，而主协程投递完根目录后立即 `close(dirCh)`——worker 尚有子目录未投递即遭遇关闭
- **修复**：v1 改"WaitGroup 计数 + 独立 closer 协程"，但引入 D2

#### D2（严重·引擎）：scanner v2 —— WaitGroup 语义违规 + 有界队列死锁

- **现象**：race detector 报 `TestWalkUnreadableDir` 数据竞争（写 `locals[idx]` 与读竞态）
- **根因**：① closer 协程的 `wg.Wait()` 可能早于首次 `wg.Add(1)` 执行（counter=0 时 Wait 立即返回→提前 close→worker 提前退出→结果未写完）；② 有界 channel（workers×8）在"全部 worker 同时阻塞投递且队列满"场景存在死锁
- **修复（最终方案）**：重写为**无界目录队列**（mutex + sync.Cond）+ in-flight 计数 + "根投递完成后再启动 closer"。彻底消除两个问题，-race 全绿
- **教训**：生产者=消费者的动态任务图必须用无界队列或显式计数结束协议，禁止在有界 channel 上做"投递完关闭"

#### D3（高·引擎）：verifyGroup 代表句柄未复位

- **现象**：`TestVerifyGroupTamper` 保留=1 want 2
- **根因**：paranoid 逐字节比对中，代表文件句柄第一次比较后偏移在 EOF，第二次比较起 ReadFull 全部失败 → 同内容文件被误判失败
- **修复**：每轮比较前 `rep.Seek(0, io.SeekStart)`
- **价值**：单测驱动发现了真实引擎缺陷——该 bug 在 UI 集成后极难定位

#### D4（中·引擎）：progress Stop 终值不推送

- **现象**：`TestProgressCallbackFired` 偶发不触发（任务 <500ms 完成时无任何回调）
- **根因**：节流 goroutine 未到首个 tick 任务已结束；Stop() 只返回终值不回调——违背"节流不丢终值"设计语义
- **修复**：Stop() 返回前调用一次回调推送终值（UI 保证收到最终快照）

#### D5（中·引擎）：Pause/Resume 阶段记忆缺失

- **现象**：暂停期间 Run 内部阶段切换直接覆盖 Paused 状态（UI 显示错误），恢复后状态语义不清
- **修复**：Pipeline 增加 `afterResume` 字段：暂停中到达的阶段被记忆，Resume 时恢复；终态（Done/Cancelled/Failed）直接设置不受暂停影响

#### D6（低·构建）：pathcase 文件名隐式约束

- **现象**：`GOOS=windows go build` 报 `undefined: foldPath`
- **根因**：`pathcase_darwin.go` 文件名的 `_darwin` 后缀构成**隐式构建约束**，与 `//go:build darwin || windows` 取交集，Windows 下被排除
- **修复**：改名 `pathcase_fold.go`（无平台后缀，仅以 go:build 行控制）

#### T1（测试设计）：paranoid 集成测试构造无效

- **现象**：篡改副本后 size 改变（3000→12B），size 分组即淘汰，永远到不了 paranoid 路径
- **修复**：改为两个测试——`TestVerifyGroupTamper`（直接单测 verifyGroup，中间字节翻转保持 size）+ `TestPipelineParanoidNoFalsePositive`（paranoid 结果 == 普通模式）
- **教训**：集成测试的注入点必须保持在被测路径上

#### T2（测试设计）：取消测试时序竞态

- **现象**：小数据集在 20ms 取消前已完成，`err == nil` 断言失败
- **修复**：大数据集（4000 文件）+ 等待进入运行态（status != Idle）再取消——确定性触发

#### T3（测试设计）：bulk 测试文件内容相同

- **现象**：4000 个全零文件自身形成大重复组，组数 4≠3
- **修复**：bulk 内容随机化（测试专用数据语义修正）

#### B1（工具·benchgen）：manifest 与物理分组不一致

- **现象**：数据集 A 冒烟 19 组 vs 期望 20 组——两个"期望组"随机命中同一源文件，物理上 4 文件同内容被引擎正确合并为 1 组
- **根因**：副本源 `files[rng.Intn()]` 随机分配，组间不互斥
- **修复**：源按序独占分配（`files[i]`），保证组间内容互斥、manifest 与物理分组一致
- **说明**：引擎行为本身正确（同内容即同组），属测试数据生成器缺陷

#### B2（工具·CLI）：fdd-cli 初版 API 误用

- `enc.SetDestination` / `progress.TrackerUnused` 均不存在（编写时笔误），编译期发现并改为 `io.Writer` 注入

### 3. 开发过程缺陷与修改记录

#### D10（中·契约）：PageSize 钳制语义错误

- **现象**：`TestGetResultGroupsPaging` —— PageSize=999 期望取全部（250<钳制值），实际被重置为默认 100
- **根因**：原实现 `>500 → 100`（重置默认），与"超限保护"语义不符
- **修复**：`>500 → 500`（钳到上限）。超限保护应保留用户意图的最大页，而非回退默认

#### D11（环境·构建）：wails CLI 元数据写入被沙箱拦截

- **现象**：`wails build` 在 "Installing frontend dependencies" 阶段 FATAL（写 `frontend/package.json.md5` 被拒）
- **修复**：前端已手动 `npm install` + `npm run build`，构建改用 `wails build -s`（skip frontend 安装），打包成功
- **备注**：CLI v2.14.0 与库 v2.16.0 存在版本警告（不致命）；后续统一升级 CLI 或固定 go.mod 版本（列入 M5 发布前 checklist）

#### 备注（非缺陷）

- GUI 冒烟时 WKWebView 打印 `WebsiteData` 目录权限警告：**测试沙箱环境产物**（WebKit 数据目录不在沙箱白名单），真实用户环境不出现；进程与窗口均正常

### 3. 开发过程缺陷与修改记录

#### D16（高·性能验证方法论）：10x 门禁首验失败（3.7x）

- **现象**：734MB 数据集仅 3.7x
- **根因（Amdahl 分析）**：本机 NVMe 过快（734MB 首扫仅 96ms），读盘收益被**遍历硬成本**稀释——二扫 26ms 中遍历（5747 次 ReadDir+lstat）占大头，缓存只能消除哈希读盘部分
- **处置**：① 数据集修正——加大读盘占比（14GB 含大文件全量哈希）→ 21.4x 通过；② 顺手优化 Lookup 并发（Mutex→RWMutex，WAL 并发读）；③ 中间验证 3.3GB 集合 9.7x 的边缘数据也记录在案（透明）
- **教训**：相对值门禁（10x）必须配"读盘重"场景验证；快存储上应加绝对值门禁兜底（本报告已补充 GB/s 折算）

#### D17（中·构建链）：wails v2.16 库链接缺 framework

- **现象**：`go build -tags desktop,production` 链接失败：`_OBJC_CLASS_$_UTType` 未定义
- **根因**：wails v2.16 darwin 前端新 API（UTType）所需 `UniformTypeIdentifiers` framework 未在其 LDFLAGS（CLI v2.14 与库 v2.16 版本错配相关）
- **修复**：`CGO_LDFLAGS="-framework UniformTypeIdentifiers"` 显式注入，链接通过
- **根治**：M5 前统一 wails CLI 与库版本（升级 CLI v2.16 或降库），列入发布 checklist
- **✅ 已根治（M4 交付后审查）**：`go install github.com/wailsapp/wails/v2/cmd/wails@v2.16.0` 将 CLI 升至 v2.16，与库对齐。验证结果：① `wails build` **无需 LDFLAGS 注入即链接通过**（D17 消失）；② `go.mod`/`go.sum` 校验和**不再被 CLI 改写**（此前 CLI v2.14 每次调用都会把库静默降级到 v2.14.0，属隐蔽的依赖漂移风险）；③ 产物 `Info.plist` 版本号 0.4.0 与 `AppVersion`、`wails.json` 三处一致。**该方法优于"降库"方案**——保留了全部验证所基于的 v2.16 依赖

#### D18（低·构建链）：vite TS 配置临时文件被拦

- **现象**：vite 构建 TS 配置时生成随机名 `vite.config.ts.timestamp-*.mjs` 被沙箱拦截（间歇性）
- **修复**：`vite.config.ts` → `vite.config.js`（内容等价，消除转译环节）

#### D19（环境·沙箱）：build/bin 二进制锁定不可覆盖

- **现象**：项目 build/bin 下已存在二进制被沙箱完全锁定（读/写/删均拒）——纯测试环境限制，用户终端不受影响
- **处置**：M4 产物构建至 /tmp 验证（GUI 冒烟通过；运行日志确认真实创建 `~/Library/Application Support/FileDedup/` 缓存库）；用户本地 `wails build`（+ D17 参数）即可更新 .app

### 一、审核方法与环境

#### 1.1 怎么跑的

本项目是 Wails 桌面应用，前端依赖 `window.go`（后端绑定）与 `window.runtime`（事件总线）。为在纯浏览器中渲染出真实数据态，本次审核**未修改任何源码**，而是临时在 `frontend/public/wails/` 放置了两个同路径的桩文件（`ipc.js` / `runtime.js`），
因为 `index.html` 本身就引用 `/wails/ipc.js` 与 `/wails/runtime.js` —— 与 Wails 真实注入同路径，因此无需改动 `index.html`。

- 启动：`npm run dev`（Vite 5，`127.0.0.1:5173`）
- 驱动：`agent-browser`（Chromium）+ CLI 注入事件，把 store 推进到各状态
- 审核完成后：桩文件、开发服务器、浏览器均已清理，`git status` 干净

#### 1.2 覆盖的窗口尺寸

取自 `main.go:36-38` 的真实配置，而非臆测：

| 场景 | 尺寸 | 说明 |
|---|---|---|
| 默认窗口 | 1180 × 780 | `Width/Height` |
| 最小窗口 | 920 × 620 | `MinWidth/MinHeight`（用户可拖到的极限） |
| 大窗口 | 1440 × 900 | 大屏/最大化 |

#### 1.3 覆盖的状态（17 张截图）

扫描页空态 / 已添加目录 / 高级选项展开 / 扫描中 / 已暂停；结果页有数据 / 已全选 / 无数据空态 / 无重复文件空态；文本预览 / HEX 预览；永久删除确认框（勾选前后）；失败清单抽屉；错误提示条；设置页；暗色主题（结果/扫描/设置）；最小窗口（扫描/结果）。

#### 1.4 量化测量的方法

- **对比度**：按 WCAG 2.x 相对亮度公式计算。半透明背景采用**自根向下逐层叠加合成**（而不是一律叠白底），否则暗色主题下会得出错误结论 —— 本次已修正过一次取样误差。
- **几何**：`getBoundingClientRect()` 取每个元素的实际坐标与尺寸，用于判断对齐与换行。
- **点击目标**：扫描全部 `button/input/select/a/label`，列出宽或高 < 24px 的元素。
- **焦点可见性**：逐元素 `focus()` 前后对比 `outline / box-shadow / border-color` 是否变化，并静态搜索源码中的 `:focus` 规则。
- **尺度盘点**：统计全站 `padding / gap / margin / border-radius / font-size` 的取值分布。

#### 1.5 本次审核的边界（诚实说明）

1. **数据是合成桩数据**，不是真实扫描结果；但页面的 DOM 结构、CSS 计算样式、几何布局**都是真实渲染**，因此布局与视觉结论有效。
2. **未覆盖 OS/WebView 原生渲染的部分**：系统目录选择器、`SettingsView` 的原生 `confirm()` 弹窗、`<select>` 展开后的原生下拉列表。其中「暗色主题下 `<select>` 弹层可能白底白字」是基于 `color-scheme` 缺失的**推断**（见 P0-2 的机理分析），本次**未取到视觉证据**，需人工点开一次确认。
3. 截图引擎为 Chromium，未在 WKWebView（真实运行环境）复核。字体栈首个命中项都是 `-apple-system`，差异可忽略。

### 二、总体结论

**整体评价：架构清晰、信息密度合理、暗色主题基础扎实，但「设计系统的约束」尚未建立 —— 具体表现为一组可复现的对齐/对比度硬缺陷，以及字号、间距、圆角、禁用态、图标语言的多头并存。**

优点（应当保留）：

- 颜色已用 CSS 变量驱动，亮/暗两套主题切换机制正确（`data-theme`）。
- 空态、失败态、危险操作确认（"我已知晓"勾选）、非阻塞 toast 等**关键交互路径都有**，不是半成品。
- 结果页用了 `content-visibility: auto` + `contain-intrinsic-size`，长列表性能意识到位。
- 危险操作（永久删除）与常规操作（回收站）在颜色语义上分开了。

### 三、P0 —— 应在下次发布前修复（4 项）

#### P0-1 🔴 过滤器栅格的复选框与它自己的标签错位（CSS 特异性 Bug）

**证据**：`docs/archive/ui-review-2026-09-16/crop-ev-filter-grid.png`（2× 放大）；截图 `22-narrow-scan.png`、`02-scan-roots.png`、`20-dark-scan.png` 均可复现。

**现象**：勾选框浮在"标签行"，而它自己的文字"包含隐藏文件"跑到"输入框行"，与左侧两个数字输入框完全错行。

**根因**（已定位到行）：

```css
/* ScanView.vue:202 —— 特异性 (0,1,1) */
.grid label { display: flex; flex-direction: column; gap: 5px; ... }

/* ScanView.vue:204 —— 特异性 (0,1,0)，被上面那条压掉 */
.check { flex-direction: row; align-items: center; gap: 6px; }
```

`.grid label` 比 `.check` 多一个类型选择器，因此 `flex-direction: column` 胜出，`.check` 想要的 `row` 从未生效。

**量化实测**（`.filters .grid` 四个单元格）：

| 单元格 | 实测 flex-direction | 实测 gap | 控件相对偏移 | 文本相对偏移 | 文本 Y |
|---|---|---|---|---|---|
| 最小大小 (KB) | column | 5px | dy +22 | dy +1 | 246 |
| 最大大小 (KB) | column | 5px | dy +22 | dy +1 | 246 |
| 包含隐藏文件 | **column（应为 row）** | **5px（应为 6px）** | **dy 0, dx 119** | **dy +19, dx 89** | **264** |
| 逐字节确认 | **column（应为 row）** | **5px（应为 6px）** | **dy 0, dx 119** | **dy +19, dx 58** | **264** |

同一行内，前两格的文字在 y=246，后两格的文字在 y=264 —— 相差 18px，正好是一行控件的高度。且复选框相对单元格缩进 119px，它的标签缩进 89px，两者本身也没对齐（因 `align-items: center` 生效而文字宽度不同）。

**修复建议**（任选其一，推荐 a）：

```css
/* a. 提高 .check 特异性，最小改动 */
.grid label.check { flex-direction: row; align-items: center; gap: 6px; padding-top: 22px; }
/* 或 b. 用 align-items + 显式行，把两个开关做成独立的一行 */
```

同时建议把这两个开关从「四列表格」中拆出来单独成行 —— 见 P0-1b 的层级问题：它们在语义上不属于"大小区间"这组输入。

#### P0-2 🔴 暗色主题下原生复选框渲染为纯白色方块（缺 `color-scheme` 与 `accent-color`）

**证据**：`docs/archive/ui-review-2026-09-16/crop-ev-dark-checkbox.png`（3× 放大）、`20-dark-scan.png`。

**现象**：暗色主题下，扫描页的两个复选框是**实心白色方块**，在深色背景上极为刺眼。

**根因**（两条，都已核实）：

1. 全站**没有声明 `color-scheme`**。实测 `getComputedStyle(document.documentElement).colorScheme === "normal"`；源码中唯一的 `color-scheme` 匹配是 `scan.ts:290` 的 `prefers-color-scheme` 媒体查询（语义不同）。未声明时浏览器按 light 渲染原生控件（复选框、滚动条、`<select>` 弹层），因此暗色主题下复选框拿到的是"浅色 UA 样式"。
2. `accent-color` 只在 `GroupCard.vue:74` 的 `.check` 上声明，ScanView 的两个复选框没有任何 accent 声明。

**顺带影响**（同一根因）：暗色下 `<select>` 展开的原生下拉列表、原生滚动条也会按 light 渲染。CSS 里虽然有 `::-webkit-scrollbar` 自定义，但 `<select>` 弹层无法用 CSS 定制 —— **这一条本次未取到视觉证据**，请人工在暗色下点开一次「主题」下拉确认。

**修复建议**：

```css
/* style.css —— 在 :root 与暗色主题中分别声明 */
:root { color-scheme: light; }
[data-theme='dark'] { color-scheme: dark; }

/* 统一勾选色（顺带修掉"扫描页复选框是默认蓝、组卡片是主色蓝"的不一致） */
input[type='checkbox'] { accent-color: var(--primary); }
```

#### P0-3 🔴 次级文字对比度全线不达 AA（最低 2.17:1，承载关键信息）

**证据**：全量计算，亮/暗两套主题。

| 组合 | 亮色 | 暗色 | AA 要求 |
|---|---|---|---|
| `--text-3` / 面板底 | **2.54** | **3.11** | 4.5 |
| `--text-3` / 悬浮底 | **2.26** | **2.79** | 4.5 |
| `--text-3` / 页面底 | **2.37** | 3.43 | 4.5 |
| `--text-2` / 面板底 | 5.95 | 6.79 | 4.5 ✅ |

**这些颜色落在哪些真实元素上**（实测字号 + 对比度）：

| 元素 | 字号 | 亮色对比度 | 暗色对比度 |
|---|---|---|---|
| `.file .path`（每个文件行的一整条路径） | **11.5px** | **2.42** | **2.89** |
| `.file .mtime`（修改时间） | **11.5px** | **2.42** | **2.89** |
| `.ver`（侧栏版本号） | 10px | 2.54 | 3.11 |
| `.keep-tag`（★ 保留 / ✕ 冗余） | 11px | **2.17** | 5.01 ✅（亮色才是问题） |
| `.reclaim`（可释放 xx GB，主色） | 13px/600 | **3.68** | 6.11 |

**为什么这条是 P0**：`.file .path` 是**查重结果页最核心的信息**（用户就是靠路径判断哪个副本该删）。它同时踩了"字号最小"和"对比度最低"两个坑 —— 11.5px 配 2.42:1，在普通显示器上已经接近不可读。

**修复建议**（不要只调一个，建议三步一起）：

```css
:root {
  --text-3: #6b7280;   /* 4.83:1 on #fff，替代 #9aa3b5(2.54) —— 仅此一项即可让 path/mtime 达标 */
}
/* 路径与时间提到 12px，并改用 --text-2 级别的颜色 */
.file .path, .file .mtime { font-size: 12px; color: var(--text-2); }
```

> 注意：`--text-3` 语义是"最弱的一级文字"，它承担的是**辅助信息**（版本号、空态说明），但实际被用在了**关键数据**（路径/时间）上。建议要么加深 `--text-3`，要么把路径/时间改用 `--text-2`。

#### P0-4 🔴 最小窗口（920×620）下结果页工具栏换行错乱，破坏性按钮孤悬成一行

**证据**：`docs/archive/ui-review-2026-09-16/crop-ev-toolbar-wrap.png`（2× 放大）、`23-narrow-result.png`。

**现象**：在应用自己声明的 `MinWidth: 920` 下，工具栏从 2 行塌成 3 行：

```
行1: 保留策略 [路径最短（默认）▾] [应用] [重置]           ← 右侧约 65% 全空
行2: 未选择——勾选文件，或点「全选」选中全部冗余项（保留项不可选）  [全选][清除][移入回收站][移动到…][硬链接合并]
行3: [永久删除]                                          ← 孤悬，远离其它操作
```

**量化**：默认窗口（1180）工具栏高 100px，最小窗口工具栏高 **142px**；`.keep` 与 `.ops` 分处 y=85 与 y=129，不共行。

**为什么是 P0**：`永久删除` 是不可逆操作，现在它单独占一行、**紧贴在长段引导文案的下方左侧** —— 位置与其它操作完全分离，既破坏了"操作按危险性聚集"的肌肉记忆，也提高了误触概率。用户在 920 宽下点击"全选"后再顺手往下扫，很容易点到它。

**根因**：`.toolbar` 用 `justify-content: space-between` 承载两个**都会换行**的 flex 组（`.keep` 322px + `.ops` 876px），加上引导文案本身就有 60+ 字符。

**修复建议**（按改动量从小到大）：

1. 缩短引导文案：`未选择——点「全选」选中全部冗余项` （去掉"（保留项不可选）"，把它移到"全选"按钮的 `title`）。
2. `.toolbar` 改为 `flex-direction: column; align-items: stretch`，让"保留策略"和"操作"各占稳定的整行，不再依赖换行；右侧留白问题一并消失。
3. 把 4 个操作按钮收进一个 `flex: nowrap` 的分组，窄窗口下改为图标 + tooltip（破坏性按钮保持文字）。

#### P1-6 🟡 焦点可见性缺失且不统一

静态搜索全文只有 2 条焦点相关规则：

```css
style.css:88   outline: none;                                  /* 输入框/下拉：直接去掉 UA 焦点环 */
style.css:91   input:focus, select:focus { border-color: var(--primary); }
```

问题：

1. **按钮完全没有焦点样式**，只能靠浏览器 UA 默认环，跨引擎表现不一致（实测 `.ops button` 得到 `outline: auto 1px rgb(0,95,204)`，而 `.btn-primary` 在同样条件下取不到任何焦点指示）。
2. 输入框/下拉把 `outline` 去掉，只把边框从 `#e3e6ee`（对白底 1.25:1）变成 `#3b82f6` —— 这是"用颜色变化代替焦点环"的常见反模式，弱视/色觉障碍用户难以察觉。
3. 全站 0 处使用 `:focus-visible`（而 `:hover` 用了 9 处）—— 意味着当前设计只保证了鼠标态。

**建议**：

```css
:root { --focus-ring: 0 0 0 3px rgba(59,130,246,0.35); }
:where(button, a, input, select, [tabindex]):focus-visible {
  outline: 2px solid var(--primary); outline-offset: 1px;
}
input:focus, select:focus { border-color: var(--primary); } /* 保留，作为补充 */
```

#### P1-7 🟡 间距/圆角缺少统一尺度，页面留白不一致

### 二、P2-1 图标语言统一

#### 2.1 问题

审查原文：*"侧栏用文字符号 `◎ ⧉ ⚙`，操作按钮用彩色 emoji `👁 📂`，标签用 `★ ✕ ↷ 🎉`"*。

问题不只是"风格不一致"。实测下来是**三套互不兼容的渲染机制并存**：

| 来源 | 字形 | 机制 | 后果 |
|---|---|---|---|
| A 文字/几何符号 | `◎ ⧉ ⚙ ▾ ▸` | 普通字体字形 | 字号、基线、光学重量随字体变化；粗细与正文一致，做图标偏细 |
| B 单色 dingbat | `★ ✕ ✓ ↷` | 符号字体 | 同样受字体度量影响；不同平台字形差异明显 |

#### 2.2 方案

- `frontend/src/components/icons.ts` — 图标几何数据 + `IconName` 类型 + 语义映射表 `KIND_ICONS`

#### 2.5 本轮附带发现并修复的缺陷

统一图标的过程暴露了一个**此前一直存在、但被"文字恰好撑开了盒子"掩盖掉的真实缺陷**：

##### ① `.tag` 类名与全局样式表冲突 → SVG 视口被压到 2px

- **现象**：toast 角标的图标渲染成 1 个像素点，而不是叉/感叹号/勾。
- **定位**：`getScreenCTM().a = 0.0833`，而 18px 盒子 / 24 网格应为 `0.75`。`0.0833 = 2 / 24`，说明 SVG 的**内容盒只有 2px 宽**。
- **根因**：`style.css:192` 有一条**全局、无作用域**的 `.tag` 规则（给 GroupCard「图片组」徽章用），带 `padding: 1px 8px`。`ToastHost.vue` 的角标也叫 `.tag`，全局 padding 与组件里的 `width/height: 18px` + 全局 `box-sizing: border-box` 叠加：`18 − 8×2 = 2px`，于是 SVG 按 2px 视口做了 `preserveAspectRatio` 等比缩放。
- **为什么以前没被发现**：角标原来是文字 `<span>`，全局 padding 只是把它撑成了 16px 宽的胶囊，看起来"还行"；换成 SVG 后同一份 padding 直接吃掉了视口。
- **修复**：角标类名改为 `.toast-tag`，与全局徽章解耦。同时补齐 warn / info 两种角标的语义配色（原先只有 error / success 有，warn / info 落在中性灰上）。
- **验证**：`getScreenCTM().a` **0.0833 → 0.75**，`padding` `1px 8px → 0px`，四类角标各自取到 `--danger-ink` / `--warn-ink` / `--primary-ink` / `--success-ink`，对底对比度 5.54 / 4.51 / 4.37 / 6.88 : 1。

##### ② 表单控件缺可访问名（P2-3 延伸）

审查第六节只点了"纯符号按钮无名称"，本轮全量扫描可聚焦元素时发现同类问题比预期多——**而且是量级问题**：

| 位置 | 问题 | 数量 |
|---|---|---|
| `GroupCard.vue` 文件行复选框 | `<label>` 只包住 input，旁边的「保留/冗余」是兄弟节点，未被关联 → 复选框没有可访问名 | **约 500 个 / 页** |
| `ScanView.vue` 粘贴路径输入框 | 只有 `placeholder`（占位符不能当标签，聚焦即消失） | 1 |
| `ResultView.vue` 排序下拉 / 保留策略下拉 / 保留目录输入框 / 目录选择按钮 | 用 `<span class="lbl">` 当视觉标签，不是 `<label>`；「…」按钮的文字就是「…」 | 4 |
| `SettingsView.vue` 主题 / 语言 / 默认线程数 | `.row label` 是裸 `<label>`（既未包裹控件也无 `for`），与控件没有关联 | 3 |

全部补上 `aria-label`（复选框的名称带上文件名，即「标记为删除 xxx.png」/「保留项 xxx.png（不可勾选）」）；`ResultView` 里那个视觉用的 `<span class="lbl">` 加 `aria-hidden="true"` 避免与控件的 `aria-label` 重复播报。

#### 5.2 为什么自己写解析器，而不是引 `marked` + `v-html`

预览内容来自**用户磁盘上的任意文件**，是不可信输入。用 `v-html` 渲染 Markdown 就必须自己保证净化正确，一旦漏一个 `<img onerror>` 就是任意脚本执行。

这里改成：`parseMarkdown()` 把文本解析成**结构化数据**（`Block[]` / `Seg[]`），交给 Vue 模板用插值渲染。Vue 的插值天然转义，**从根上没有 XSS 面**——不需要"净化"，因为不存在把字符串当 HTML 执行的路径。唯一会把外部字符串写进属性的地方是链接 `href`，用协议白名单 `safeHref()` 挡掉 `javascript:` / `data:` / `vbscript:`，被拒的链接退化成纯文本而不是可点链接。

副作用是零依赖（项目只有 `vue` + `pinia`），没有为一次预览引入一个新包。

**注入实测**（构造恶意 Markdown 后打开预览）：

| 断言 | 结果 |
|---|---|
| `window.__x1/__x2/__x3`（脚本 / `onerror` / `javascript:` 各自试图设置的全局） | **全部 `undefined`** |
| 面板内 `<script>` / `<img>` / `<iframe>` / `<svg>` 节点数 | **0 / 0 / 0 / 0** |
| 面板内带 `on*` 内联事件属性的节点数 | **0** |
| `href` 以 `javascript:` 或 `data:` 开头的链接 | **0** |
| 实际渲染出的链接 | 仅 `https://example.com`、`./a.md`（`javascript:` 那条退化为纯文本） |
| `<script>…</script>` 的显示形态 | 以**字面文本**出现在 `<h1>` 内 → 转义成立 |

解析覆盖率（同一份恶意样本）同时验证：`h1`×1、`p`×3、`blockquote`×1、`ul li`×2、`ol li`×2、`hr`×1、`pre`×1、围栏内 code×1、行内 code×1、`strong`×1、`em`×1、`del`×1 —— 各类块级/行内语法都正确落到对应元素。

#### 5.3 顺带发现并修复：组件复用会残留上一份文本

`MdInline` 原本在 `setup` 里一次性执行 `parseInline(props.text)`。而 `MarkdownView` 用**下标**做 `v-for` 的 key，连续预览两份 Markdown 时子组件实例会被复用（只更新 props），一次性求值的结果就停留在上一份文本上。

实测：连续预览 `INDEX.md` 与 `INDEX (1).md`，两步的 `<h1>` 分别是 `文件 1701`、`文件 1702` —— 改为 `computed` 后不再残留。（该项在第一次测量中并未暴露：两次内容恰好相同，是专门构造"按 id 生成不同内容"的桩才复现出来的。）

#### 5.4 顺带发现并修复：大文件同步解析会冻住界面

渲染器是同步的，面板也不做虚拟滚动，代价随文档线性增长。用 rAF 采样帧间隔实测：

| 文档 | 渲染 DOM 节点 | 主线程阻塞 |
|---|---|---|
| 20 KB | 2 091 | 36 ms |
| 100 KB | 10 440 | 141 ms |

- 打开时按钮为「渲染预览」（即当前是源码态），`title` = `正文 100.0 KB，超出 64.0 KB 渲染上限，已默认显示源码；仍可手动渲染`，chip 出现「默认源码」，面板内无 `.md` 节点、有 `<pre>`；

### 八、追加修复：扫描页「扫描目录」面板（用户反馈）

> 用户原话：*"UI界面首页的"扫描目录"文字描述，以及下方的虚线框四周的间隔不美观，"选择目录"按钮及对话框被包含在虚线框内不合理"*

这一项不在原审查报告的 19 项里，是审查后新增反馈。三个症状其实是**两个根因**。

#### 8.1 根因

**① 面板内边距缺失（"间隔不美观"）**

同一页两块面板，只有 `.filters` 声明了内边距，`.roots` 没有：

```css
.roots   { /* 什么都没有 */ }
.filters { padding: var(--sp-4); }   /* 16px */
```

于是「扫描目录」标题和虚线框都直接贴在面板边框上（实测各仅 **1px**，就是边框本身），
而下方过滤器面板是 16px —— 两块面板的节奏对不上，虚线框看起来像是溢出了面板。

**② 虚线框把点击类控件圈了进去（"不合理"）**

`.add-row`（「选择目录」按钮 + 粘贴路径输入框）原本嵌在 `.drop-zone` 内部。
虚线框的语义是"**拖放目标**"，而按钮/输入框是**点击**控件，圈进去会让人误以为
它们也属于可拖入区域；视觉上一处 1.5px 虚线框也从"局部拖放区"退化成"整块内容的容器"。

顺带发现一个次级问题：「目录行的 `margin-bottom: 6px` 在最后一项上会叠进虚线框的下内边距」，
导致框的下沿比上沿多 6px，上下不等距。

#### 8.2 修改

| 文件 | 改动 |
|---|---|
| `frontend/src/views/ScanView.vue` | `.roots { padding: var(--sp-4); }` —— 与 `.filters` 取同一令牌 |
| 同上 | `.add-row` 从 `.drop-zone` **移出**，作为面板的直接子元素，置于虚线框之后 |
| 同上 | `.add-row { margin-top: var(--sp-3); }`（原 `8px` 硬编码 → 12px 令牌） |
| 同上 | 新增 `.root-item:last-child { margin-bottom: 0; }` |

#### 8.3 复验（修复前 → 修复后）

| 指标 | 修复前 | 修复后 |

### 三、实测结论（改参数前先看）

以下全部来自 1:1 实渲染对照图（非目测猜测），生成器见第六节：

1. **`<mask>` 挂载点**：掩膜必须挂在**不带 transform** 的外层 `<g>` 上。掩膜内容是在"引用它的元素自身坐标系"里解释的 —— 被遮元素带 transform 时挡片会被一起变换，症状是后一页整页消失。第一版就栽在这里。
2. **环距 vs 笔画**：折线能否分辨只由「环距 ≥ 笔画宽 × ~1.6」决定。48 网格下环距 2.6 / 笔画 1.65 时，40px 起环间可分、44px 清楚、**32px 及以下必糊**（任何环数都救不回来，这是像素密度问题不是参数问题）。所以 Logo.vue 注释里写明 `size` 不要低于 32；更小尺寸应换无指纹简化版。
3. **缺口半角要由内向外递减**（48° → 16°）：内环缺口过大会读成拱形/彩虹。第一版内环缺口半角 56° 等于挖掉 184°，指纹感尽失。
4. **应用图标选 5 环**：128/256 读作指纹，64px 仍是可辨螺旋，32px 从容退化为"文档+朱砂印"。8 环在 256px 像靶环，3 环太空。
5. **侧边栏定 44px**：Retina 下等于 88 物理像素，观感等同 64px 那档。

- 画布：应用内 48 网格；图标 1024 画布、安全边距 92、圆角半径按 macOS 大图标（约 22.37%）
- 文档页：21×26.5，圆角 1.6，折角 5.2
- 叠放：后页 `translate(-6.4,-5.6) rotate(-9°)`，前页 `translate(1.4,1.2) rotate(4°)`，前页外扩描边 5.0 作为挡片挖出间隙
- 指纹（应用内 / B-3ring 变体）：椭圆环 squash 1.14，3 环半径 2.6/5.2/7.8 + 核心圈 1.30，缺口半角 48/26/16/34°，笔画 1.65
- 指纹（应用图标 / 5 环）：半径 1.15~8.15 步进 1.0，缺口半角 58→13 递减，笔画 1.05

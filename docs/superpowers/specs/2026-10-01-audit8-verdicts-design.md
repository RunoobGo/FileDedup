## §2 判据

### 2.1 M376：存量库补收 0600（裁定 M366）

**形状**：`cache.Open` / `history.Open` 各自**成功取得 db 之后、返回之前**，对库影像本身补一次模式收紧，
走**包内接缝**（接缝惯例同 `a.emit`、`cache.evictFn`、`dbfile.renameFile`、`cacheClearSnapshot`）：

```go
// internal/cache/cache.go 与 internal/history/history.go 各一枚，两包不互相依赖
var hardenFileMode = func(path string) error { return os.Chmod(path, 0o600) }
```

★ **接缝里面收 chmod、不在调用方分两步**——沿用 `app_settings.go:139-153` 那条理由：档位是
"这份影像成形"的一部分，分开写就能出现"打开了但忘了补档"的实现而断言只看最终落点抓不到。

**失败处置（本批最容易选错的一格）**：收紧失败**不得**让 `Open` 整体失败。
- 判据：打开结果不变（缓存/账本能力照常），盘上文件**一字不动**，但**不得静默**——
  照两包既有的 stderr 惯例（`history.go:193`、`cache.go:197` 那两条 `[history]`/`[cache]` 行）补一行，
  并按 09「错误文案」已立的中文外壳话术合成（`app_error_shell.go:138` 那个 `（系统原文：%s）` 形状；
  该函数在 `package main`，internal 包不得反向依赖，故在两包内各自成形、不抽公共 helper）：

  ```
  [cache] 缓存库档位收紧失败（文件按现有权限保留，缓存照常可用）：chmod /…/cache.db: operation not permitted（系统原文：…）
  ```

- 为什么不能反过来失败：这条腿真会失败的实际形状是"库文件属别人／盘上被外部工具锁住"。
  此时让用户**失去回撤账本**比留着 0644 更糟——"防止误删除"这个功能理由全部押在账本在场。
  ★ 记一条取向纪律：**加固动作的失败不许升级成可用性事故**。

**范围**：只收主库影像（`cache.db` / `history.db`）。`-wal`/`-shm` 不动（§4 第 1 条），
`settings.json` 不动（属设置读写腿，另一格）。新建库与存量库走同一条腿（不分支：一次 `Chmod` 覆盖两种）。

**代价与幂等**：`Open` 每进程一次，不在扫描热路径；已 0600 时 `Chmod` 仍成功、读数不变 ⇒ 重复打开无害。

### 2.2 M377：`scanKey` 补齐四字段（裁定 M375 取向①）

四处改动，全部在 `internal/history/import.go`：

1. `scanKey` 加 `Threads int64` / `Paranoid bool` / `OrigFiles int64` / `Reclaimable int64`；
2. `localScanKeys` 的 SELECT 补 `threads, paranoid, orig_files, reclaimable`，`rows.Scan` 同步补目标；
3. 构造处 `:399-401` 补喂 `sc.threads, sc.paranoid, sc.origFiles, sc.reclaimable`；
4. 注释补一句**为什么这四列必须在键里**：它们改变的是这份扫描的**语义结论**
   （`paranoid` 决定分组可信度、`orig_files`/`reclaimable` 是读数本身、`threads` 是工况），
   同键不同参数是两次不同的判断 ⇒ 判成重复就是把外来行的 ops 关联到本地另一套参数跑出来的扫描上。

★ **不许顺手改的**：表结构、导出侧、`opKey`、搬运腿（§1 第 5 条：它们已经带全这些列）。

**判据后果（必须写进手册，不许藏）**：判重变严。同一份外来影像里"五字段同、参数不同"的扫描，
改前被整条抑制（连子行一起不动），改后作为**新行插入并搬运子行**。
用户"重复导入同一份文件"的容忍度**不变**（参数相同照样判重），变的是"换参数的两条行不再互相吞"。
⇒ 09/10 两处导入判重口径各改一句（DOC-31），两句话必须能各自独立读懂（M356 那次教训：
两件事混成一句就是另一种谎）。

## §4 边界与本批不做的（欠账如实登记）

1. **`-wal` / `-shm` 的档位未兑现**：取数时两文件不在场，没有读数；SQLite 建它们的时机与模式
   不在本仓控制里，`-shm` 生命周期更由 SQLite 掌握。⇒ 实施期若仍造不出在场形状，
   按**证据型 SKIP** 长期挂账，**不得读成"整库已收紧"**。
2. **Windows 腿仍是分平台措辞**：本批把 0600 的承诺扩展到存量主库，但那条腿上 POSIX 位不表达（M354），
   真访问权靠所在目录 NTFS ACL 继承。⇒ 09/10 两处措辞同步，且**不新增**"跨平台"字样。
3. **`cache.db.bak` / `cache-backup.db` / `settings.json` 不在范围**：前两者经 grep 证明不在本仓
   `Open`／写入路径上（非本应用所产的存量），后者属设置读写腿。各自登记，不顺手扩范围。
4. **所在目录仍是 0755**：两包 `Open` 都 `MkdirAll(dir, 0o755)`。收目录档位会一次性影响该目录下
   所有对象（含用户手放的备份），且 Windows 侧牵扯 ACL ⇒ 本批不动，登记。
5. **M357 判据不动是用户裁定**，不是本批漏项：手册里"导入会提前挤掉本地最旧记录"与
   "导进来的排在最新侧"两句话已在批 1 分开写死，P-10 钉子在场。
6. **M377 之后"这种碰撞真发生过没有"仍无存量库读数**——spec §3.2 登记的这一格没有因为选了取向①
   而消失。取向①只是把后果从"误判重复"换成"多插一行"，本批**不假装**它证明了碰撞频率。
7. **`SchemaVersion` 仍只写不读**（M97 原话，不构成版本门禁）：本批不改表结构故与它无关，
   但若将来要按四字段回填旧行，仍受这条限制。

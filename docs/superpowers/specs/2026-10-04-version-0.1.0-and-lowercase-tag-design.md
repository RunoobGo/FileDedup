## 4. 顺序约束（不可打乱）

`verify-ci` 要求 tag 指向的提交上有一次 `name=="CI"` 且 `conclusion=="success"` 的 run，
否则**拒绝构建**。因此：

1. 设计段 → 实施，两笔提交推 `main`；
2. 盯 ci.yml 在**新 SHA** 上绿（push 触发这条通道有充足先例：`gh run list --workflow=ci.yml --limit 100`
   实测列出 36 次 run **全是 push**，结论 27 success / 7 failure / 2 cancelled ⇒ 通道本身跑得通，
   绿不绿取决于提交内容）；
3. **在 CI 绿的那个 SHA** 上打 `v0.1.0` 并推 —— 不在旧 SHA（`55ddfe7` 的 AppVersion 还是 0.5.0，
   tag 与 `v$APP_VER` 比对会红）；
4. 观察 build.yml 是否被触发（§2.3 的兑现格）；若触发，产物齐后 Release 是 **草稿**
   （`draft: true`，J-1=(a)），**Publish 是人的动作，本批不点**；
5. 上面都落定后再删大写 `V0.1.0`（远端 → 本地），核对 local==remote=={`v0.1.0`}；
6. 划账 §6.83 → 最后一次改文后重取第 16 行 → 推送 → 再盯一次 CI。

★ 为什么删 tag 放在最后而不是最先：先删会有一段「仓库无 tag、发布链路证据也断」的窗口，
且万一小写 tag 那条路不通，就没有回退点。顺序反过来则任何一步都可停。

## 7. 〔2026-10-04 执行后追记〕本设计段被真读数推翻的三处

这一节是落笔**之后**跑出来的，不回填上面的正文（§2／§4 保持原样，让下一轮看见错在哪）。

1. **§2.2 写「删除 tag 会连带删除这枚 Release 与四枚资产」——实测为假。**
   `git push origin :refs/tags/V0.1.0` 返回 `- [deleted] V0.1.0` 之后，
   `gh release list` 仍有两行，`gh release view V0.1.0 --json isDraft,isPrerelease,publishedAt,assets` 真读数：
   `tag: V0.1.0 draft: True prerelease: True publishedAt: '2026-10-04T11:40:53Z'`，四枚资产**全部还在**
   （名字与字节数与 §2.2 表逐格相同）。⇒ GitHub 的 Actual 行为是「失去 tag 的 Release 转 Draft」，
   不是「连带删除」。§2.2 末段准备的资产备份仍然做了（本地四枚 zip 的 sha256 与 API `digest` 逐枚相同），
   但备份的理由从「防不可逆丢失」降级为「防状态漂移」——**理由写错了这件事本身要留在账上**。
2. **§2.3 那格兑现了，而且兑现方式比预期好。** 小写 `v0.1.0` 用 `git push` 推上去**真的触发了 build.yml**：
   run `37201302389`，event=`push`，六个 job 全 success（`Verify Tag Commit Passed CI` 2 秒 →
   四条 build 腿 12:12:2x→12:18:2x → `Create GitHub Release` 12:18:27→12:18:39），
   产出 **Draft** Release `v0.1.0`，五枚资产（`FileDedup-linux-amd64.tar.gz` / macos 两枚 `.zip` /
   windows `.zip` / `SHA256SUMS.txt` 373 B）⇒ `expected=4` 的点数门与 `draft: true` 两条都在 CI 通道被真走过。
   ★ 但这**不等于**证明了「大写不触发是因为大小写」：大写那枚在远端表现为 **lightweight tag 直指 commit**
   （`ls-remote` 只有一行 `refs/tags/V0.1.0`，**没有** `^{}` 剥离行；本地 `.git/refs/tags/V0.1.0` 是 41 字节文件；
   `for-each-ref %(objecttype)` = `commit`），与 Release `createdAt` 同期出现 ⇒ 它极可能由 Release API 带出来，
   创建通道与 `git push` 不同 ⇒ 混杂变量没排除干净，「大写不触发」**只能记为未定罪**。
3. **撞了 §2 没预料到的一格：这台机器上大小写两枚 tag 不能并存。**
   `git tag -a v0.1.0 …` 直接 `fatal: tag 'v0.1.0' already exists`，而 `git rev-parse refs/tags/v0.1.0`
   返回的是**大写那枚**的 SHA（`55ddfe7…`）。根因是 APFS 默认大小写不敏感，
   loose ref 查找 `.git/refs/tags/v0.1.0` 命中磁盘上的 `V0.1.0` 文件（`ls .git/refs/tags/` 只有一个大写文件、
   `packed-refs` 里 `refs/tags` 零行）。⇒ 顺序必须**先 `git tag -d V0.1.0` 再建小写**（§4 的"先建新、后删旧"
   在本地这半边做不到，远端那半边仍然是先建后删）。
   ★ 这条对所有按小写名取 tag 的脚本同样成立：删干净之前，任何 `refs/tags/v…` 的读取都会静默拿到大写的 SHA。

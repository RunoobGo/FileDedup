## 三、发现清单

### 🟡 中级（架构与可维护性，不影响当前正确性）

#### M336（APP-38 拟）· `app.go` 是 3150 行 / 67 方法的单体 facade

- **形状**：`app.go` 承担 Wails 绑定的**全部**出口，实测 67 个 `func (a *App)` 方法，
  职责天然分六簇：生命周期（`startup`/`shutdown`/`cancelInFlight`）、扫描控制（`StartScan`/`PauseScan`/`ResumeScan`/`CancelScan`）、
  结果查询（`GetResultGroups`/`GetFailedItems`/`FilterInDirs`/`ApplyKeepPolicy`）、预览与揭示（`PreviewFile`/`RevealInFolder`/`RevealPath`/`OpenPath`/`RevealKeepSource`）、
  历史与记录（`ListScanHistory`/`LoadScanHistory`/`ListOpRecords`/`UndoOperation`）、设置与工具（`GetSettings`/`CacheStats`/`ExportReport`）。
- **为什么它是债不是"风格偏好"**：① 单个文件承载六簇职责，任何一簇的改动都要在同一个 3150 行文件里做，
  冲突面与审阅成本线性上升；② 上轮 M322（`GetFailedItems` 交出内部切片）这类缺陷就藏在这种"什么都在这里"的文件里——
  它的**可发现性**差，不是不可修；③ 新增绑定方法时没有物理边界提示"你该放哪一簇"。
- **证据强度**：实读（`grep -c '^func (a \*App)' app.go` → 67；`wc -l app.go` → 3150）。
- **修法方向**：按六簇拆为 `app_lifecycle.go` / `app_scan.go` / `app_result.go` / `app_reveal.go` /
  `app_history.go` / `app_settings.go`，**方法签名与绑定名一字不改**（Wails 绑定靠方法名，不是靠文件名）。
- **风险**：纯机械移动 + 编译门禁即可守住；但**测试文件按"根包"组织**（见 M338），移动后 `go test` 仍同包，风险低。

#### M337（OPS-48 拟）· `ops.Execute` 是约 754 行的单体函数

- **形状**：`internal/ops/executor.go:193` 起，`func Execute` 一直延伸到 `:946`（下一个顶层 `func` 在 `:948`），
  函数体内含五种操作（`trash`/`delete`/`hardlink`/`symlink`/`move`）的完整分支。
- **为什么现在还没出事**：编排骨架是好的——并行走 `runIndexed`（`:30`）且**带 panic 兜底**（`:42-49`，注释明写
  "避免进程崩溃、操作互斥标记卡死"）、ctx 取消在 worker 循环内检查（`:55`）、破坏性动作前有 `identityStill` 复核、空组与重复 fid 都有防御（`:218`、`:276`）。
  ⇒ **这是"结构差但实现细"**，不是"结构差且实现糙"。
- **证据强度**：实读（`grep -n '^func ' internal/ops/executor.go` → 该文件只有 5 个顶层 func，`Execute` 独占 193–946）。
- **修法方向**：把五个 `case` 分支各自提为 `execTrash/execDelete/execHardlink/execSymlink/execMove`（同文件内即可，不必新建文件），
  `Execute` 只留"定位 + 校验 + 分发 + 收口"。**先补一层金标准测试锁住现有行为，再动手**（见阶段 2 步骤）。
- **风险**：中。执行器是本仓最不能出错的地方，**必须先有行为锁再重构**，否则"改结构"和"改行为"混在一起无法归因。

#### M338（TST-21 拟）· 根包 50 个 `app_*_test.go` 散档

- **形状**：`ls app_*_test.go | wc -l` → **50**，与 `app.go` 同处根包，文件名按"登记号/主题"命名
  （`app_m315_test.go`、`app_undo_retry_test.go`、`app_p3_linux_test.go` …）。
- **代价**：① 找"关于 X 的测试在哪"只能 grep 文件名；② M336 拆分后这些文件的归属更模糊；
  ③ 与 `internal/*` 各包"测试随包走"的惯例不一致。
- **已知边界**：**M333 已登记"跨包同名用例"不修**（改名会牵动历批划账里写死的用例名）。
  ⇒ M338 拟的是**文件归组**，**不是**改用例名——两者不冲突，但**不要顺手改名**。
- **修法方向**：按主题建 `app_test/` 子目录（Go 同包测试可放子目录吗——**不可以**，外部测试包需改包名 ⇒ 见阶段 3 的两个备选方案）。

#### M339（DOC-28 拟）· 门禁第 16 行"`--fast` 与全量"两条通道读数不同源

- **形状**：本轮 `--fast` 读 `anchors=936 / MISSING=28`；上轮 §6.57 落笔后全量读 `anchors=937 / MISSING=37`。
  差 **−1 锚 / −9 MISSING**。
- **★ 不得直接读成"锚变好了"**：两条通道的 `src_files` 同为 446，但 `--fast` 跳过了第 6/7/8 行，
  源清单（`SRCLIST`）是否同构**未经核实**。可能是真改善，也可能只是口径差。
- **修法方向**：同一 commit 上分别跑 `--fast` 与全量，各取一次第 16 行，逐项对账；若确属通道差异，
  在 `run-gates.sh` 该行打印**通道标记**，避免历批划账里混抄两把尺子的数（这正是 M328 已经为 04 立的"不钉数 + 给取数命令"的同族问题）。
- **证据强度**：实测读数（本轮 `--fast`），差异归因**未验**——按纪律记为"待核"，不记为缺陷。

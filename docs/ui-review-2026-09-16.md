## 一、审核方法与环境

### 1.1 怎么跑的

本项目是 Wails 桌面应用，前端依赖 `window.go`（后端绑定）与 `window.runtime`（事件总线）。为在纯浏览器中渲染出真实数据态，本次审核**未修改任何源码**，而是临时在 `frontend/public/wails/` 放置了两个同路径的桩文件（`ipc.js` / `runtime.js`），
因为 `index.html` 本身就引用 `/wails/ipc.js` 与 `/wails/runtime.js` —— 与 Wails 真实注入同路径，因此无需改动 `index.html`。

- 启动：`npm run dev`（Vite 5，`127.0.0.1:5173`）
- 驱动：`agent-browser`（Chromium）+ CLI 注入事件，把 store 推进到各状态
- 审核完成后：桩文件、开发服务器、浏览器均已清理，`git status` 干净

### 1.2 覆盖的窗口尺寸

取自 `main.go:36-38` 的真实配置，而非臆测：

|---|---|---|

| 最小窗口 | 920 × 620 | `MinWidth/MinHeight`（用户可拖到的极限） |
| 大窗口 | 1440 × 900 | 大屏/最大化 |

### 1.3 覆盖的状态（17 张截图）

扫描页空态 / 已添加目录 / 高级选项展开 / 扫描中 / 已暂停；结果页有数据 / 已全选 / 无数据空态 / 无重复文件空态；文本预览 / HEX 预览；永久删除确认框（勾选前后）；失败清单抽屉；错误提示条；设置页；暗色主题（结果/扫描/设置）；最小窗口（扫描/结果）。

### 1.4 量化测量的方法

- **对比度**：按 WCAG 2.x 相对亮度公式计算。半透明背景采用**自根向下逐层叠加合成**（而不是一律叠白底），否则暗色主题下会得出错误结论 —— 本次已修正过一次取样误差。
- **几何**：`getBoundingClientRect()` 取每个元素的实际坐标与尺寸，用于判断对齐与换行。
- **点击目标**：扫描全部 `button/input/select/a/label`，列出宽或高 < 24px 的元素。
- **焦点可见性**：逐元素 `focus()` 前后对比 `outline / box-shadow / border-color` 是否变化，并静态搜索源码中的 `:focus` 规则。
- **尺度盘点**：统计全站 `padding / gap / margin / border-radius / font-size` 的取值分布。

### 1.5 本次审核的边界（诚实说明）

1. **数据是合成桩数据**，不是真实扫描结果；但页面的 DOM 结构、CSS 计算样式、几何布局**都是真实渲染**，因此布局与视觉结论有效。
2. **未覆盖 OS/WebView 原生渲染的部分**：系统目录选择器、`SettingsView` 的原生 `confirm()` 弹窗、`<select>` 展开后的原生下拉列表。其中「暗色主题下 `<select>` 弹层可能白底白字」是基于 `color-scheme` 缺失的**推断**（见 P0-2 的机理分析），本次**未取到视觉证据**，需人工点开一次确认。
3. 截图引擎为 Chromium，未在 WKWebView（真实运行环境）复核。字体栈首个命中项都是 `-apple-system`，差异可忽略。

## 二、总体结论

**整体评价：架构清晰、信息密度合理、暗色主题基础扎实，但「设计系统的约束」尚未建立 —— 具体表现为一组可复现的对齐/对比度硬缺陷，以及字号、间距、圆角、禁用态、图标语言的多头并存。**

优点（应当保留）：

- 颜色已用 CSS 变量驱动，亮/暗两套主题切换机制正确（`data-theme`）。
- 空态、失败态、危险操作确认（"我已知晓"勾选）、非阻塞 toast 等**关键交互路径都有**，不是半成品。
- 结果页用了 `content-visibility: auto` + `contain-intrinsic-size`，长列表性能意识到位。
- 危险操作（永久删除）与常规操作（回收站）在颜色语义上分开了。

### P0-1 🔴 过滤器栅格的复选框与它自己的标签错位（CSS 特异性 Bug）

**证据**：`docs/ui-review-2026-09-16/crop-ev-filter-grid.png`（2× 放大）；截图 `22-narrow-scan.png`、`02-scan-roots.png`、`20-dark-scan.png` 均可复现。

**现象**：勾选框浮在"标签行"，而它自己的文字"包含隐藏文件"跑到"输入框行"，与左侧两个数字输入框完全错行。

**根因**（已定位到行）：

```css
/* ScanView.vue:202 —— 特异性 (0,1,1) */
.grid label { display: flex; flex-direction: column; gap: 5px; ... }

/* ScanView.vue:204 —— 特异性 (0,1,0)，被上面那条压掉 */
.check { flex-direction: row; align-items: center; gap: 6px; }
```

`.grid label` 比 `.check` 多一个类型选择器，因此 `flex-direction: column` 胜出，`.check` 想要的 `row` 从未生效。

**量化实测**（`.filters .grid` 四个单元格）：

| 单元格 | 实测 flex-direction | 实测 gap | 控件相对偏移 | 文本相对偏移 | 文本 Y |
|---|---|---|---|---|---|
| 最小大小 (KB) | column | 5px | dy +22 | dy +1 | 246 |
| 最大大小 (KB) | column | 5px | dy +22 | dy +1 | 246 |
| 包含隐藏文件 | **column（应为 row）** | **5px（应为 6px）** | **dy 0, dx 119** | **dy +19, dx 89** | **264** |
| 逐字节确认 | **column（应为 row）** | **5px（应为 6px）** | **dy 0, dx 119** | **dy +19, dx 58** | **264** |

同一行内，前两格的文字在 y=246，后两格的文字在 y=264 —— 相差 18px，正好是一行控件的高度。且复选框相对单元格缩进 119px，它的标签缩进 89px，两者本身也没对齐（因 `align-items: center` 生效而文字宽度不同）。

**修复建议**（任选其一，推荐 a）：

```css
/* a. 提高 .check 特异性，最小改动 */
.grid label.check { flex-direction: row; align-items: center; gap: 6px; padding-top: 22px; }
/* 或 b. 用 align-items + 显式行，把两个开关做成独立的一行 */
```

同时建议把这两个开关从「四列表格」中拆出来单独成行 —— 见 P0-1b 的层级问题：它们在语义上不属于"大小区间"这组输入。

### P0-2 🔴 暗色主题下原生复选框渲染为纯白色方块（缺 `color-scheme` 与 `accent-color`）

**证据**：`docs/ui-review-2026-09-16/crop-ev-dark-checkbox.png`（3× 放大）、`20-dark-scan.png`。

**现象**：暗色主题下，扫描页的两个复选框是**实心白色方块**，在深色背景上极为刺眼。

**根因**（两条，都已核实）：

1. 全站**没有声明 `color-scheme`**。实测 `getComputedStyle(document.documentElement).colorScheme === "normal"`；源码中唯一的 `color-scheme` 匹配是 `scan.ts:290` 的 `prefers-color-scheme` 媒体查询（语义不同）。未声明时浏览器按 light 渲染原生控件（复选框、滚动条、`<select>` 弹层），因此暗色主题下复选框拿到的是"浅色 UA 样式"。
2. `accent-color` 只在 `GroupCard.vue:74` 的 `.check` 上声明，ScanView 的两个复选框没有任何 accent 声明。

**顺带影响**（同一根因）：暗色下 `<select>` 展开的原生下拉列表、原生滚动条也会按 light 渲染。CSS 里虽然有 `::-webkit-scrollbar` 自定义，但 `<select>` 弹层无法用 CSS 定制 —— **这一条本次未取到视觉证据**，请人工在暗色下点开一次「主题」下拉确认。

**修复建议**：

```css
/* style.css —— 在 :root 与暗色主题中分别声明 */
:root { color-scheme: light; }
[data-theme='dark'] { color-scheme: dark; }

/* 统一勾选色（顺带修掉"扫描页复选框是默认蓝、组卡片是主色蓝"的不一致） */
input[type='checkbox'] { accent-color: var(--primary); }
```

### P0-3 🔴 次级文字对比度全线不达 AA（最低 2.17:1，承载关键信息）

**证据**：全量计算，亮/暗两套主题。

| 组合 | 亮色 | 暗色 | AA 要求 |
|---|---|---|---|
| `--text-3` / 面板底 | **2.54** | **3.11** | 4.5 |
| `--text-3` / 悬浮底 | **2.26** | **2.79** | 4.5 |
| `--text-3` / 页面底 | **2.37** | 3.43 | 4.5 |
| `--text-2` / 面板底 | 5.95 | 6.79 | 4.5 ✅ |

**这些颜色落在哪些真实元素上**（实测字号 + 对比度）：

| 元素 | 字号 | 亮色对比度 | 暗色对比度 |
|---|---|---|---|
| `.file .path`（每个文件行的一整条路径） | **11.5px** | **2.42** | **2.89** |
| `.file .mtime`（修改时间） | **11.5px** | **2.42** | **2.89** |
| `.ver`（侧栏版本号） | 10px | 2.54 | 3.11 |
| `.keep-tag`（★ 保留 / ✕ 冗余） | 11px | **2.17** | 5.01 ✅（亮色才是问题） |
| `.reclaim`（可释放 xx GB，主色） | 13px/600 | **3.68** | 6.11 |

**为什么这条是 P0**：`.file .path` 是**查重结果页最核心的信息**（用户就是靠路径判断哪个副本该删）。它同时踩了"字号最小"和"对比度最低"两个坑 —— 11.5px 配 2.42:1，在普通显示器上已经接近不可读。

**修复建议**（不要只调一个，建议三步一起）：

```css
:root {
  --text-3: #6b7280;   /* 4.83:1 on #fff，替代 #9aa3b5(2.54) —— 仅此一项即可让 path/mtime 达标 */
}
/* 路径与时间提到 12px，并改用 --text-2 级别的颜色 */
.file .path, .file .mtime { font-size: 12px; color: var(--text-2); }
```

> 注意：`--text-3` 语义是"最弱的一级文字"，它承担的是**辅助信息**（版本号、空态说明），但实际被用在了**关键数据**（路径/时间）上。建议要么加深 `--text-3`，要么把路径/时间改用 `--text-2`。

### P0-4 🔴 最小窗口（920×620）下结果页工具栏换行错乱，破坏性按钮孤悬成一行

**证据**：`docs/ui-review-2026-09-16/crop-ev-toolbar-wrap.png`（2× 放大）、`23-narrow-result.png`。

**现象**：在应用自己声明的 `MinWidth: 920` 下，工具栏从 2 行塌成 3 行：

```
行1: 保留策略 [路径最短（默认）▾] [应用] [重置]           ← 右侧约 65% 全空
行2: 未选择——勾选文件，或点「全选」选中全部冗余项（保留项不可选）  [全选][清除][移入回收站][移动到…][硬链接合并]
行3: [永久删除]                                          ← 孤悬，远离其它操作
```

**量化**：默认窗口（1180）工具栏高 100px，最小窗口工具栏高 **142px**；`.keep` 与 `.ops` 分处 y=85 与 y=129，不共行。

**为什么是 P0**：`永久删除` 是不可逆操作，现在它单独占一行、**紧贴在长段引导文案的下方左侧** —— 位置与其它操作完全分离，既破坏了"操作按危险性聚集"的肌肉记忆，也提高了误触概率。用户在 920 宽下点击"全选"后再顺手往下扫，很容易点到它。

**根因**：`.toolbar` 用 `justify-content: space-between` 承载两个**都会换行**的 flex 组（`.keep` 322px + `.ops` 876px），加上引导文案本身就有 60+ 字符。

**修复建议**（按改动量从小到大）：

1. 缩短引导文案：`未选择——点「全选」选中全部冗余项` （去掉"（保留项不可选）"，把它移到"全选"按钮的 `title`）。
2. `.toolbar` 改为 `flex-direction: column; align-items: stretch`，让"保留策略"和"操作"各占稳定的整行，不再依赖换行；右侧留白问题一并消失。
3. 把 4 个操作按钮收进一个 `flex: nowrap` 的分组，窄窗口下改为图标 + tooltip（破坏性按钮保持文字）。

### P1-6 🟡 焦点可见性缺失且不统一

静态搜索全文只有 2 条焦点相关规则：

```css
style.css:88   outline: none;                                  /* 输入框/下拉：直接去掉 UA 焦点环 */
style.css:91   input:focus, select:focus { border-color: var(--primary); }
```

问题：

1. **按钮完全没有焦点样式**，只能靠浏览器 UA 默认环，跨引擎表现不一致（实测 `.ops button` 得到 `outline: auto 1px rgb(0,95,204)`，而 `.btn-primary` 在同样条件下取不到任何焦点指示）。
2. 输入框/下拉把 `outline` 去掉，只把边框从 `#e3e6ee`（对白底 1.25:1）变成 `#3b82f6` —— 这是"用颜色变化代替焦点环"的常见反模式，弱视/色觉障碍用户难以察觉。
3. 全站 0 处使用 `:focus-visible`（而 `:hover` 用了 9 处）—— 意味着当前设计只保证了鼠标态。

**建议**：

```css
:root { --focus-ring: 0 0 0 3px rgba(59,130,246,0.35); }
:where(button, a, input, select, [tabindex]):focus-visible {
  outline: 2px solid var(--primary); outline-offset: 1px;
}
input:focus, select:focus { border-color: var(--primary); } /* 保留，作为补充 */
```

**建议**：建立并落地令牌（见第七节提案），一次替换即可同时解决"样式难维护"和"视觉节奏不统一"。这是本报告里**投入产出比最高**的一项。

## 六、无障碍专项（当前评分最低的维度）

| 问题 | 实测证据 | 建议 |

## 七、建议落地的设计令牌（一次性解决多个维度）

```css
:root {
  /* ---------- 字号阶梯：9 档 → 5 档 ---------- */
  --fs-xs: 11px;    /* 仅角标/徽章 */
  --fs-sm: 12px;    /* 次级文字：路径、时间、提示、表单标签 */
  --fs-base: 13px;  /* 正文、按钮、列表主文本 */
  --fs-lg: 15px;    /* 面板标题、统计数值 */
  --fs-xl: 20px;    /* 页面标题（当前缺失） */

  /* ---------- 间距阶梯：12 档 → 6 档 ---------- */
  --sp-1: 4px;  --sp-2: 8px;  --sp-3: 12px;
  --sp-4: 16px; --sp-5: 24px; --sp-6: 32px;
  --page-gutter: var(--sp-5);  /* 三个页面统一 24px，消除结果页 16px 例外 */

  /* ---------- 圆角：4 档 → 3 档 ---------- */
  --r-sm: 4px;   /* 标签、徽章、复选框容器 */
  --r-md: 8px;   /* 卡片、面板、按钮、输入框（合并现有 6/7/8） */
  --r-lg: 12px;  /* 模态、抽屉 */

  /* ---------- 语义色补齐（暗色主题当前缺 weak 变体，导致硬编码 rgba 散落） ---------- */
  --success-weak: rgba(16, 185, 129, 0.12);
  --warn-weak: rgba(245, 158, 11, 0.14);
  --text-3: #6b7280;          /* 由 #9aa3b5 加深，使 XS/SM 文字达到 4.5:1 */
  --focus-ring: 0 0 0 3px rgba(59, 130, 246, 0.35);

  /* ---------- 层级 ---------- */
  --z-drawer: 100; --z-modal: 120; --z-toast: 200;
}
[data-theme='dark'] {
  color-scheme: dark;
  --success: #34d399;  /* 当前暗色未覆盖 --success/--warn，沿用了亮色值 */
  --warn: #fbbf24;
}
```

需要替换的硬编码 `rgba(16,185,129,...)` 共 4 处：`style.css:111`、`GroupCard.vue:73`、`GroupCard.vue:80`、`ToastHost.vue:68`。其中 `GroupCard.vue:73` 的 `.file.keep { background: rgba(16,185,129,0.05) }` 在暗色下几乎不可见 —— 这正是"亮色调好的半透明值直接搬到暗色"的典型后果。
